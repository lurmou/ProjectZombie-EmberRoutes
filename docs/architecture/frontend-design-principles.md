# 前端视觉与交互设计原则

> 更新：2026-11-06｜状态：active｜用户批准作为全项目的前端设计方向。
> 适用：全部面向用户的页面、面板、表格、表单、菜单、弹窗、HUD及开发工具界面；不专属于某个业务领域或技术栈。

## 1. 总原则与职责

按用户当前要做的判断和操作组织界面。业务数据提供表达原料，不能直接决定字段排列、信息密度和控件形态。视觉与交互可用性、业务正确性、工程正确性分别验收，任何一项通过都不能代替另外两项。

本文件规定表现与交互质量，不新增业务功能、不修改持久化/权限/身体控制等已批准契约。原生引擎、组件、渲染与生命周期约束仍见[UI工程契约](../ui-architecture.md)、[UI领域](../domains/ui.md)及[UI运行时规格](ui-framework-architecture-spec.md)。

## 2. 设计先从任务和场景开始

设计前明确：谁使用、何时使用、需要做什么判断、完成什么操作、失败会有什么影响。区分用户正在专注主任务、主动管理配置、深入查阅详情三类场景；不要先罗列数据库字段再设计版式。

每个常驻元素应有清晰用途：用户看到它后，会改变什么判断或操作？低频解释、完整历史、技术原因进入详情或开发诊断，不长期争夺主要视野。管理页面可以有高信息密度，不能套用HUD的极简方式隐藏必要对比数据。

## 3. 先分层，再压缩

| 使用方式 | 主要目标 | 默认表达 |
|---|---|---|
| 持续观察、短暂扫视 | 发现变化与风险 | 紧凑身份、图形指标、关键异常 |
| 快速操作 | 认清对象并作决定 | 明确目标、动作分组、选择与结果反馈 |
| 主动管理与比较 | 查找、排序、筛选、批量配置 | 合理的表格/列表/表单、数字与相关详情 |
| 深入理解 | 查精确值、原因和后续动作 | 完整说明、上下文、可展开细节 |

同一事实可以在不同层有不同表达。正常状态保持简洁，重要变化突出；关键信息不能只藏在悬停里，危险也不能被徽章数量上限遮蔽。减少重复内容与不必要层级，不通过缩小字体、堆缩写、无解释图标实现“紧凑”。

## 4. 基础交互与功能同时设计

适用功能的最小体验链是：发现入口→理解用途与目标→操作→收到反馈→能退出/取消/恢复。MVP可减少功能种类，不应把这条链路拆成后补事项。

按界面用途设计需要的选择、悬停、焦点、滚动、拖动、菜单、搜索或快捷键，不要求每种界面机械配齐全部手势。不要把右键、双击、长按、拖动作为重要功能唯一且不可发现的入口；需要时提供清晰提示或替代操作。

拖动要表达抓取区域、所选对象、有效目标、放置结果和无效恢复；点击与拖动要能区分。用户配置的显示位置和顺序应保持稳定；自动刷新不得随意抢焦点、跳滚动位置或改变当前对象。

## 5. 信息层级与视觉语言

- 主层强调当前对象、主要动作和必须立即处理的变化；次层表达行动状态与常用操作；辅助层承载解释与低频配置。
- 通过字号/字重、空间分组、对齐、对比与少量强调建立层级。不要所有内容同时高亮、粗边框或大标题；留白须服务分组和命中，而非把页面做成松散的大卡片堆。
- 选中、焦点、悬停、危险、禁用和处理中的视觉意义要一致且可区分。颜色来自统一语义体系，不能把选择色与错误色混用。
- 图标需要可辨识且含义稳定。陌生动作使用短标签或明确说明；不能用“图标更高级”代替理解测试。
- 风格服从使用环境和产品气质。不同页面可有不同密度，字体、间距、图标与状态语义应保持一致，避免组件各自创造视觉规则。

## 6. 反馈既清楚又真实

使用用户能理解的词汇；等待、处理中、成功、拒绝、失败、未知分别表达。请求接受不等于物理动作或业务效果已经完成。失败信息应尽量说明发生了什么、影响哪个对象、用户可以做什么；不要把内部状态码或日志原样堆到界面。

群体操作要说明目标范围；部分成功需能辨认，不能用一个成功提示覆盖其他失败。错误不能只在瞬间闪过，反馈不能依赖长时间装饰动画或不断闪烁。

## 7. 阅读、命中与可访问性

关键语义至少以文字、符号、形状等另一种方式辅助颜色。普通信息保持清晰可读，重要警告可快速定位；不要要求用户记忆难懂缩写或辨别细微颜色差别。

按实际输出分辨率、观看距离、输入设备和字体评估字号与命中目标，不能把网页常用字号/移动触控尺寸当作所有游戏的统一标准。交互目标留出合理间隔，关闭、危险动作与高频操作避免误触；不可用控件需能解释原因。

支持合理的布局/字体/尺寸适配。长名称、不同语言、数字变化与放大字号不能遮住关键动作；必要时采用受控滚动或渐进展开。截断内容要有完整查阅途径。个性化配置不能替代可用的默认布局，也不能成为解决坏布局的借口。

## 8. 必须放到真实使用环境评审

游戏覆盖层在明暗背景、室内外、复杂纹理、移动与其他窗口并存时评审，透明度不能牺牲可读性；网页/桌面工具同样需在实际窗口尺寸、主题、输入方式和长内容下评审。避免只在空白背景或理想数据截图上评价美观。

不要为了动画、阴影、透明层或精细装饰降低主要任务的可见性和响应。性能预算与视觉质量共同约束方案，既不能用性能口号取消必要交互，也不能用视觉包装掩盖卡顿或错误状态。

## 9. 交付与评审流程

1. 实现前给出用户任务、信息层级、主要布局及关键状态示意。数据未接入时可用明确标注的设计样例先验证表现，不能把样例成功当作业务完成。
2. 在统一组件基础上实现完整交互状态：默认/悬停/焦点/选中/禁用/等待，以及适用的失败/未知/空数据/加载/拖动状态。
3. 设计与实现同步检查正常、异常、零数据、长名称、多语言、窗口变小和字号放大，不能只看默认状态。
4. 让不了解实现的人完成代表性任务，观察寻找、理解、误触和恢复过程；收集具体失败，不只问“好不好看”。
5. 交付分别记录业务、工程、视觉交互验收。自动化截图、坐标断言、替身交互和外部预览注明覆盖范围；未做目标运行环境的视觉/输入验收，明确标为未验证。

评审必问：用户能否找到入口、认清当前对象、预判操作、收到可信反馈，并顺利退出或恢复？常驻信息是否值得占据注意力？大字号/长文本/异常状态是否仍可用？需要反复解释或读取多行技术文字才能完成常用操作时，应回到信息组织和交互设计调整。

## 10. 经验来源与适用边界

这些原则借鉴前端可用性与游戏社区经验，具体布局/阈值仍需本项目场景验证，不声称存在通用最佳样式或任意“几秒/多少像素/屏幕占比”标准。

- [NN/G：渐进披露](https://www.nngroup.com/articles/progressive-disclosure/)：低频复杂内容后置。
- [NN/G：拖放交互](https://www.nngroup.com/articles/drag-drop/)：可发现线索及全过程反馈。
- [NN/G：图标可用性](https://www.nngroup.com/articles/icon-usability/)：可识别与可理解分别评估。
- [Xbox UI上下文指南](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/114)：对象、用途和操作结果需要上下文。
- [Xbox文字显示指南](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/101)：文字阅读与观看条件。
- [Game Accessibility Guidelines](https://gameaccessibilityguidelines.com/ensure-no-essential-information-is-conveyed-by-a-fixed-colour-alone/)：关键信息不只依赖颜色。
- [Accessible Game Design：HUD](https://accessiblegamedesign.com/guidelines/HUD.html)：扫视阅读与位置/尺寸调整。其HUD经验仅用于相应界面，不推广为所有管理页面的布局模板。
