# 0.23.0 共享 Job、公共需求与优先级接入

日期：2026-10-23。基于用户已验收的 0.22.16/P1，按[切换计划](../../superpowers/plans/2026-10-23-shared-job-cutover.md)成组实现。取消旧任务存档兼容已获授权；未执行旧任务、原件或存档清理。当前为开发侧验证，游戏集中验收待用户完成。

## 运行职责

- `JobStore` / `BusinessJobs`：新根 `EmberRoutes/Work/v1.taskJobs.format=1/byId` 是持久 Job 记录。已有执行器的业务记录就是 envelope.payload；只重建内存 NPC 索引，不再双写旧 `craftProbes.byNpc` / `labor.tasks`。Job 元数据由业务状态和保存前 flush 派生，物理资源声明继续仅由 LaborStore/LaborClaims 裁决。
- `publicWork.format=1` 保存公共 Orders、逐 NPC 的 crafting/hauling 0～4 优先级及最低存量规则。新 Order 创建时没有 npcId；认领后才关联独立 jobId/npcId，不以 NPC 作为工单身份。
- `TaskDirectory` 管可重建候选和唯一认领，`WorkSelector` 按个人工种优先级选择；`PublicWork` 是唯一普通工作协调入口。旧物流 Schedule 和固定 NPC Stock 后台在新路径中不派发。身体控制仍全部经过 TaskRuntime。
- 工匠必须掌握配方且满足技能/平台要求。认领前复用只读 ProductionChain 进行材料/工具/前置配方评估，缺料不创建 Job、不占身体；真正启动仍重验和认领原件。不会用 2 秒自学替代原版配方知识。
- 新鲜普通工作不能抢占当前执行。载货及原件义务先恢复；保存导致的自有搬运恢复不进入公共抢单，手动暂停/未知效果不自动恢复。
- 最低存量按仓内实物件数判断，不扣未取走的预留物；低于阈值创建固定成品件数的补货 Order，单个活动 Order 防重。盘点未知或同物料仓储范围重叠时不触发；关闭界面仍有后台观察者。

当前预算：每 200ms 轮转一名 NPC；最多检查三个制作需求，最多推进该 NPC 一个只读制作评估（32 步），全局最多保留四个评估；搬运发现使用既有 64 步预算。认领冲突至多尝试三个候选。上述是代码预算，不是规模/帧率验收。

## 可见入口

- 工单监控：公共委托 / 最低存量弹窗、工作优先级弹窗；未认领 Order、已绑定 Job、原件及暂停/恢复/取消。
- 仓储物品详情：带入产物打开同一个弹窗；真实制作平台右键：带入已登记平台。
- 安装版原版 `ISCraftRecipePanel`：包装原 createDynamicChildren，在已有 rootTable 中追加委托按钮，带入当前受支持配方。依据当前安装 Lua 的布局接口；未替换整份原版文件，不修改即时制作行为。真实游戏/其他 UI 模组组合仍待验。
- 旧指定 NPC 下单、直接传授配方不再作为正常新下单路径；恢复已有新 Job 的命令继续可用。旧页面源码仍保留，未宣称整套人员/防御/最终视觉已完成。
- 未认领 Order 的命令代次使用 `ORDER:<revision>`，执行 Job 使用业务 generation；同一 Order 认领前的旧按钮不能误操作认领后的 Job，即使两者数值相同。

## 存档和边界

新 Job 与 publicWork 均在既有工作根表，由原版 ModData 保存；保存屏障、成功回执核对、原件恢复继续使用既有 P1 流程。遇旧任务/旧固定 NPC 存量规则明确拒绝初始化并保留数据，显示 `LEGACY_TASK_RESET_REQUIRED` / `LEGACY_STOCK_RESET_REQUIRED`。测试应使用干净任务存档；既有世界先在旧版本完成收尾，不能直接把取消兼容理解为自动擦除。

Job 记录上限 512、Order 记录上限 256、规则上限 64；达到上限明确拒绝新增，历史和原件保留。自动审批曾拒绝自动删除完成搬运历史，理由是用户未授权永久删除；已放弃该方案，未加入自动清理。历史归档策略须另行明确，不暗中绕过删除限制。

当前普通认领仅制作/搬运，沿用这两类业务的未收尾任务准入限制；不表示小型生活行为树、自理、专业工种、跨 NPC 分段生产或完整人员矩阵已实现。清洁空间目标、守卫持续岗位仅检查通用候选/义务协议，无游戏动作。单人限定，MP 未实现。
