## 1. 总体裁定

**有条件可行，值得重新立项；当前需求文档不能直接当作实现规格执行。**

经济、据点账本、后台生产、虚拟商队、升级和事件调度都有可用的引擎基础。真正需要攻坚的是：没有真实玩家连接的人类 NPC 联机行为；NPC 与普通玩家、僵尸之间的伤害同步；原版物品/车辆存档与模组账本跨存储的一致性；覆盖全部世界交互的领地权限。

评审后的三类结论：

| 分类 | 含义 | 本项目对应内容 |
|---|---|---|
| A：有明确实现基础 | 原版已有必要原语；业务规则仍须自行实现和测试 | 交易面板、供需定价、虚拟商队、后台库存、角色权限表、升级、核心失联状态 |
| B：必须调整方案 | 原目标可保留，文档所写技术路径或承诺不成立 | 虚实生产交接、全局存储权威、交易锁、无线电保密、离线计时、尸潮规模、找零 |
| C：关键原型未通过 | 静态源码证明有扩展路径，但不能据此承诺完整效果 | MP 人类 NPC、完整 TimedAction 兼容、真实车辆脱壳复原、跨原版存档的崩溃一致性、完整防破坏 |

**不采用 Fake Connection 作为主路线；不把 IsoSurvivor 当成熟替代骨架；不把“只有动画”记作劳动岗位完成；不把保存了 ModData 记作已解决掉物和复制。**

## 4. NPC 专项裁定

### 4.1 无硬件输入并非无路可走

当前引擎明确提供：`IsoPlayer.setNpc(true)` 挂载 `AIComponent`；`IsoGameCharacter.isNpc()` 检查该组件；`IsoPlayer.updateMovementFromInput` 在 NPC 分支返回；`postUpdatePlayer` 消费 running/justMoved 等变量，IsoPlayer 继续读取 strafeX/Y。AIComponent 的 `update()` 是空的，因此**控制接入口存在，决策 AI 仍须自行实现**。E02/E03。

`PathFindBehavior2` 持有角色并能请求路径，`moveToPoint` 从角色动画取得 deferred movement，再调用 `moveUnmodded`。这不是“写了目标点就自动完成整个行为”的高级 NPC API。角色状态、动画根位移、碰撞提交、路径跟随仍需完整配合。E05。

当前 `IsoGameCharacter.doDeferredMovement` 在 path2 非空且不是特定翻越状态时有早退；MP 客户端对非本地 IsoPlayer 也有专门早退。**直接改 setnx/setny 或 setNextX/Y，不能证明已经解决动画、碰撞、转向和联机一致性。** E04。

技术建议是先验证 IsoPlayer 子类，明确每一时刻由路径跟随还是自定义控制提交位移；同一时刻只允许一个驱动者。旧资料“每帧必须清 path2”只能在其对应自驱分支成立，不能升级为所有 NPC/路径场景的通用铁律。

### 4.2 不用假连接填原版玩家槽位

当前 PlayerID 会从连接的玩家索引或 GameServer/GameClient 的玩家表解析对象；AntiCheatPlayer 校验已登记 playerId 是否属于发送连接；动作管理器又会按角色查真实连接。E07/E08/E10。

因此，伪造连接并非源码证明的不可能，但它会把 NPC 问题扩展成原版登录、玩家槽位、存档、断线和反作弊的兼容工程。ZombieBuddy 能注入方法，**不意味着这些身份关系自动建立**。不推荐这一主路线，也不推荐通过关闭全服反作弊来让 NPC 工作。

还有比包校验更直接的障碍：当前 `IsoPlayer.updateInternal2` 先走 `updateRemotePlayer()`；若没有走该分支，后面有 `assert(!GameServer.server)`、`IsoCamera.setCameraCharacter(this)` 和本地玩家状态更新。远程分支在专服则从 NetworkPlayerAI/realx/realy 等同步状态落位。**因此在专服直接照搬 SP 子类的 super.update() 并写输入变量，不能当作已存在的服务端 NPC 驱动器。** 即使未启用 Java assert，后续客户端假设仍然存在，需要单独确定服务器模拟适配方案。E31。

建议独立 NPC ID 与注册表，服务端驱动权威状态，客户端只持表现代理；自行同步创建/销毁、位置、动作事件和关键身体状态。无需把 NPC 登记为真实联网玩家。此路线仍需验证 NPC 对原版僵尸的仇恨、命中和死亡同步，不能仅通过自定义坐标快照宣称 MP 完成。

客户端渲染也应按当前引擎核查：FBORenderCell 对精确 IsoPlayer 类直接返回，子类进入后续移动对象分支；不能沿用旧资料中“NPC 渲染必需 patch”作为无条件要求。能进入渲染分支仍不等于模型、动画和区块注册均已就绪。E32。

### 4.3 IsoGameCharacter 与 IsoSurvivor 都不是免费退路

IsoSurvivor 在当前 JAR 中是 **final**，不能继承。它有构造与旧式幸存者字段，但不能据此推断拥有生产、战斗或 MP 系统。E06。

直接扩展 IsoGameCharacter 可以减少一部分玩家专用逻辑，却会失去 IsoPlayer 的成熟动作和控制路径；同时也碰上下一节的向下转型。只能作为需要明确取舍的候选，不宜宣称它天然更稳定。

### 4.4 TimedAction 的确存在独占向下转型

`ISBaseTimedAction` 将 character 传给 `LuaTimedActionNew`，后者构造参数是 IsoGameCharacter。**但同一个 Java 类的 start() 在普通 MP 客户端通路中明确调用 `createNetTimedAction((IsoPlayer)this.chr, table)`。** E09。

当前引擎还提供 custom remote timed action sync 标志；这为适配提供入口，不代表绕过标准同步后仍会自动同步。E09/E11。`ISTimedActionQueue` 位于 client 目录；`NetTimedAction` 服务端执行 complete 的链路则是另一套机制，不能把专服上的 NPC 动作当作本地玩家入队处理。E10/E11、L02。

搬运动作还调用 `getPlayerLoot(character:getPlayerNum())` 等玩家 UI；种植会写玩家 OnlineID/playerNum 所有者；砍树区分 animEvent 与 serverStart 模拟动画事件。L03–L05。这些说明“有正确动画”与“物品、伤害只结算一次”必须分别验收。

**裁定：按动作白名单复用，不承诺全部动作无修改可用。** 每个动作列出执行端、真实效果提交点、消耗、失败恢复、中断和网络表现；先吃喝/搬运等小集合，再扩大到岗位。

## 5. 劳动生产与虚实转换

### 5.1 宽泛岗位只解决配置复杂度

四大岗位分类适合作为玩家界面，但每类内部仍应有独立任务：搬到工位、领取材料、加工、存货、失败释放。NPC 走到箱子边并循环动画，不能计作已完成搬运；据点有工人数就固定加产，也不能描述成真实执行原版劳动。

工匠还需区分原版普通制作、B42 entity processor 与自定义配方。原版 ISCraftAction 存在，不证明所有 B42 加工机都能由它完成。第一版限制白名单，明确输出物品 ID、品质、工具和容器契约。

### 5.2 生产必须只有一个真值

两种选择均可行，但不可混用同一生产对象：

| 选择 | 优点 | 代价与边界 |
|---|---|---|
| 抽象营地生产 | 远处结算简单；可优先完成经济循环 | NPC 近处是明确的表现代理；不能声称真在耕种原版地块 |
| 原版世界劳动 | 玩家能观察真实植物、物品移动与治疗 | 任务适配与虚实交接复杂，须逐岗位验证 |

需求同时追求两者，建议保留目标，但每个任务显式拥有结算者：实体执行或虚拟结算。交接保存 taskId、输入预留、进度、产出状态和 `settledUntil`，同一时段不能两个层各结一次。

原版 SFarmingSystem 本身遍历持久化植物并按游戏时间维护水分、生长等，部分检查才依赖已加载格子。L06。因此“玩家离开后原版田地完全停摆，宏观层可以再产一份”是假设错误。对原版农田的补水、收获等操作应接入其状态；自建抽象农场则必须与原版植物分开。

### 5.3 未加载区块是数据边界

不对空的 GridSquare、没加载的容器、火炉、发电机执行物理动作；也不为后台生产强制加载整个据点。后台账本结算到待交付库存，实物生成/移交等区块可用后执行。

有任意相关玩家观察、交互或执行未完事务时，不能立即全清实体。需要进入/退出滞回、任务交接和多个玩家观察集合。NPC 的稳定身份、背包与身体状态必须先存在于可恢复模型中，再派生实体。

### 5.4 “离线”需定义三种时钟

玩家离线但服务器继续运行，可以按游戏小时结算；服务器进程关闭或世界暂停时，GameTime 事件不会替业务继续推进。若需现实离线补算，要另存现实时间并限定补算窗口，不可默认在重启后补整个现实跨度。E23。

阵营全员离线 24 游戏小时后降到 10% 消耗可以自建，但需记录最后在线时间和分段结算边界；24 小时阈值跨过时不能把整段都按同一倍率算。空服暂停时门槛是否推进需要明确服务器配置。

## 6. 交易、供需与防刷

### 6.1 定价模型可行，原公式方向需要统一

原文“玩家提供物品”与“据点索取物品”语义重叠。应明确为：

`可成交余额 = 商人付给玩家的收购总值 − 玩家购买商人商品的售价总值`。

余额非负才可交换。以整数最小价值单位计算并限定数量和总额；收购价与出售价分开。食物新鲜度、剩余弹药、液体含量、耐久、嵌套容器、模组物品未知价格都需要策略。不能把旧物品删掉，再按 fullType 重建一个“等价品”。

需求衰减应按**成交累计量**计算，批量交易跨阈值时分段计价。否则一笔先套用旧价，仍可绕过衰减；拆成多笔也应得到相近结果。每日恢复要保留最后结算日，防止重复登录或重启再恢复一次。

硬通货找零只能来自商人库存：按优先级分配不超过余额的数量，剩余差额明示确认；不存在无限找零、把不足一发子弹的余额向上取整或以找零物品立即反卖获利的默认许可。

### 6.2 独占窗口不是防复制事务

据点锁作为第一版简化可保留，但必须增加：持有者与 sessionId、租约和断线清理、距离/权限重验、报价库存版本、唯一 transactionId 与提交去重、数量合法性检查。锁到期或世界状态变化后，应重新报价，不能继续提交旧快照。

原版 ItemTransactionPacket 使用 itemId、源/目标 ContainerID、Request/Accept/Done/Reject 等事务状态。E22。可以复用其物品运输与校验思路，但不能直接等同于具有买卖金额、市场库存和崩溃日志的交易服务。

建议交易提交按“服务端报价→预留真实物品→验证全部输入→提交交换→记录结果→同步表现”处理；中途失败按明确补偿规则恢复，重复提交返回同一结果。多人玩家背包与物理容器如何挂接原版事务，仍要两客户端实测，不能仅在服务端调用 AddItem/Remove 就宣称联机可靠。

### 6.3 ModData 不会自动提供权威和跨系统原子性

GlobalModData 是可存取、可同步的表；当前实现也允许客户端 transmit，接收处触发 `OnReceiveGlobalModData`。E13/E14。**不是数据挂进 GlobalModData 就获得服务端信任。** 权威账本只能由服务端规则变更；客户端发意图，不接受其完整账本覆盖。

SGlobalObjects 适合格子锚定记录，有保存/同步字段白名单；GlobalModData 适合世界级索引、路线、商队和阵营业务表。两者都可用，不必把所有移动商队强行做成坐标对象，也不能因为对象 modData 风险就判定全部 GlobalModData 不可用。E13–E15。

当前 GlobalModData 保存路径先写临时文件，再复制到正式文件；它与车辆 DB、区块容器、玩家存档没有一个共同事务。E13/E17/E22。主线程内无交错与断电后原子恢复是两回事。要满足原文的崩溃保护，需要版本化事务日志、幂等恢复和故障注入验收；尚不能承诺任意断电零损失。

## 7. 商队与遭遇战

### 7.1 虚拟路线是正确的主架构

预设公路节点图、路径长度、速度、载重和口粮账本可自行实现；不需要给每支后台商队生成物理实体。地图标记有可用接口，但 WorldMarkers 的屏幕引导点与世界地图符号是两套系统，大地图用地图 API/叠加绘制，不可混称一个接口包办。E25/E29。

节点应有路线图版本、路段 ID、路段进度；不能每次回到最近节点就丢弃已消耗时间或货物变动。PREPARING、TRADING、UNLOADING 也要有提交编号，而不只是一个枚举字符串。

### 7.2 实体遭遇必须和后台结算互斥

每次遭遇有 encounterId、随机种子、截止游戏时间、已生成状态、事件威胁 ID、胜负提交版本。两名玩家同时进入不能各刷一份车辆和敌人。救援完成与倒计时到期只允许一个结果提交，重登重启不得重抽战果。

“击杀全部威胁”应跟踪本次事件参与者，不把附近所有僵尸都作为无限延长的目标；参与者卸载也不算已被杀死。玩家带走货物、拆车、杀死护卫后，账本必须反映真实损失。

后台胜率公式应改为 clamp 到 [0,1]，显式处理威胁≤0。护卫战力、车辆防御、损失骰子和救援状态在同一事件版本内确定。该概率公式是可实现的游戏规则，不是引擎自带战斗模拟。

### 7.3 电台不是阵营私信

原版 ZomboidRadio.SendTransmission 有频道、范围和信号传播，并在服务端发送网络广播。E24。相同频道的外人可能监听；默认通信也不保证同阵营每位玩家正在收听。

要区分“设备真实收到的公开广播”和“授权成员界面的私密通知”。秘密商队位置只给授权客户端下发；让客户端隐藏无权限标记不能防止其他客户端已收到坐标。

## 8. 真实车辆虚实转换：单列高风险模块

BaseVehicle 有二进制 save/load，VehiclesDB2 还会保存 worldVersion、sqlId 并把操作交给 worldStreamer 队列。E16/E17。保存方法存在，不等于“车辆对象可直接放进 Kahlua 表后复活”。

需要显式保存/恢复车辆脚本、原身份关联、零件、耐久、油液、容器物品实例、钥匙、拖挂和乘员。脱壳时须先处理真人乘员和正在交互的玩家。物理移除、网络销毁、数据库删除或保留策略必须一致，避免区块加载时旧车再次出现。

只调用 removeFromWorld 不应当被当成完整的持久脱壳协议；当前 permanent removal 路径还处理 square/chunk 和 VehiclesDB2。E16/E17。即使完整调用了原版删除路径，模组账本提交与车辆数据库队列之间仍非共同原子事务。

返程时，停车点必须已加载并通过车辆体积、朝向、地面、碰撞、拖挂和占用检查；检查一个空格不能证明整辆车能安全放下。没有安全位置就保持“待提车”数据状态，不能先生成再尝试挤开。

**推荐早期商队使用独立的抽象运力资产**，实物车辆转换作为后续独立可验收能力。这保留货物往返与遭遇玩法，但属于对需求的阶段性降级，不能悄悄声称实现了玩家真实皮卡脱壳。

## 9. 领地、保护与继承

原版 Faction 存 owner 与用户名成员列表，缺少需求中的 Leader/Officer/Resident/Visitor 完整权限模型。E18。建议独立稳定 factionId + membership/role，原版阵营只做可选映射；删除重建同名阵营不能自动继承旧资产。

SafeHouse 有 loot/interact/trespass 的规则，但不是任意 mod 领地的通用授权层。E19。当前大锤包路径有服务器全局选项判断；起火包的基本一致性检查也没有为本模组的宣战/权限表自动裁决。E20/E21。

所以隐藏右键选项不足以防破坏。开箱、物品转移、门窗破坏、建造、拆除、点火、火势从界外蔓延、车辆撞击等须建立覆盖表，逐条定位权威处理点。外部模组可引入新破坏路径；完整保护不能在没有兼容范围的情况下宣称完成。ZombieBuddy 方法注入可参与服务端拒绝，但每个补丁需按当前签名和原方法副作用验证，不能假设入口取消后客户端预测一定正确。

核心物体只持 coreId/territoryId 关联，领地和账户数据独立保存；烧毁后状态变 CORE_LOST，三游戏天期限可恢复。OnInitGlobalModData 适合读恢复数据，不适合立即对尚未加载的核心或停车点强行生成实体。

领袖死亡重生后的授权应依据**服务器认证后的账户身份**。Steam 模式可关联服务器可信的 SteamID64，非 Steam 服务器需有账户回退；OnlineID、playerIndex 和一次角色生命周期都不稳定。阵营共享口令不宜直接拥有重置领袖的权限，要限制失败次数并提供管理员恢复途径。

离线“商队继续跑完”与“安全自动卸货”还需定规则：若离线后免疫所有遭遇，玩家可能主动下线规避风险。可以作为服务器选项，但不能既称硬核风险又无条件豁免。

## 10. 升级、热度与规模

等级、蓝图门槛、投入材料、NPC 工位、商队并发可由自建规则表达。需求中的“防空木墙”“工业水塔”“载重+300%”目前是设计描述，需要精确脚本 ID、配方/实体定义与 UI 解释，不能从原生 API 存在推导为内容已具备。

“无衰减大锅饭”与消耗长期过剩资源的目标存在张力：必须定义储量上限、每日需求、饱腹计算和特殊食物属性。+300% 容量也需明确是虚拟商队容量，还是实际车辆后备箱；后者牵涉实际容器能力和改装兼容。

热度事件计时可行；引擎声音和附近僵尸可参与。当前 LuaManager 也有 spawnHorde、addZombiesInOutfit 等生成原语（E33）。**不能把巨大声音半径当作让所有未加载地区僵尸真实跨图围城的保证。** 若需要固定规模袭击，采用可控事件生成，并规定服务器配置允许的规模、可见范围、生成批次、事件上限和清理条件。

本轮没有压测，因此不承诺“几十/几百 NPC、超大尸潮仍不卡”。四大岗位聚合只减轻玩家配置，不自动降低每个 NPC 的感知、路径、动画与同步成本。

## 11. 技术路线比较与接受条件

| 路线 | 判断 |
|---|---|
| 纯 Lua 完成经济与后台商队 | 可作为第一版核心；无法凭此交付自定义人类 Java 实体的完整目标 |
| ZombieBuddy + 自研 IsoPlayer 子类 + 独立协议 | 推荐候选；控制通路可证，MP 动作、战斗与代理生命周期需先过原型 |
| 伪造玩家连接并复用全套玩家协议 | 不推荐，牵涉面太大；本轮没有验证可安全兼容 |
| 改继承 IsoGameCharacter 或 IsoSurvivor | 前者需要额外适配，后者 final；不能作为天然稳定的降级捷径 |

原需求“先经济、再经营、最后实体 NPC”的玩家功能交付顺序可以保留。**但是最终产品以 MP 人类 NPC 为硬要求，技术可行性探针必须提前。** 若探针不通过，要在大规模内容制作前明确选择：先交付纯后台经济版、先 SP、缩小实体交互范围，或接受更大的引擎适配工程。

以下是认定原需求可正式实现所需的证据，不是本轮已完成事项：

| 验证对象 | 必须看见的结果 |
|---|---|
| NPC 载体 | SP 和专服+两客户端：可见、移动、绕障、上下楼、卸载重现；不占真实玩家槽位 |
| NPC 战斗 | 双端一致的伤害/弹药/死亡；僵尸正确追击；不依赖全局关闭反作弊 |
| 动作适配 | 每个白名单动作动画与权威结果一致；受惊中断、丢材料、断线和重登不重复产出 |
| 宏微交接 | 两名玩家跨边界、加速/暂停/重启后，同一小时只消费与生产一次 |
| 交易事务 | 并发、重放、超时、过期报价、物品中途消失、提交各阶段强退均有确定恢复结果 |
| 真实车辆 | 同一车辆身份、零件、钥匙、物品状态正确往返；堵位、拖挂、乘员与重启无复制 |
| 领地保护 | 专服上针对每个受保护入口进行未授权实测，包括火势与世界对象破坏 |
| 负载预算 | 事先固定 NPC/据点/商队/僵尸数量，再测路径请求、主线程耗时、同步量和内存 |

旧项目保留作材料，不沿用“版本号增加=验收完成”的进度方式。旧工作岗位、少量字段重建 NPC、删除后按类型重造物品等实现不能直接搬入新核心。

## 12. AGENTS.md 是否每次会话必读

**应该有精简版必读 AGENTS.md；不建议把现在这份全文继续作为新项目每次会话必读。** 旧文件保留为历史资料，技术结论按任务和版本查证。

本机旧文件约 43.5 KB，混合了跨模组导航、工具安装史、旧版引擎结论、业务决策和工作纪律。这里的问题不只是长度：例如同一文件同时存在 API 检索入口禁用与要求使用的说法；NPC 和游戏版本基线已落后；“没检索到=不存在”不区分索引覆盖与继承；历史 UI/移动约定被写成无条件规则，容易把旧项目的问题继续带入新项目。

官方说明 AGENTS.md 按项目根至当前目录合并，更深层指导优先，但仍受总字节上限约束；默认上限为 32 KiB，可配置。旧文档所写的 DSH 64 KB 注入预算不能直接视为当前 Codex 配置。[OpenAI 官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

如果新模组仍处于同一个 Workshop Git 根下，只增加子目录的短 AGENTS.md，**不等于祖先长文从上下文中消失**。应先检查实际根和加载链，再考虑精简共享父文件或采用独立项目根；本轮没有改动任何 AGENTS.md，也没有替用户创建新模组或改仓库边界。

建议必读只保留以下稳定约束（建议规模约 1–2 页，属于本报告建议而非平台限制）：

1. 项目目标和本阶段边界：后台经济先可交付，MP NPC 等未证实能力明确标记；旧代码默认未验收。
2. 证据纪律：关键 API 查当前本机原版与当前 JAR；报告记录版本/哈希；查不到先核覆盖、继承和暴露面，不凭记忆编方法。
3. 权威边界：客户端发意图，服务端重查并提交资产变化；账本、实物、实体代理的唯一所有者必须明确。
4. 一致性红线：稳定 ID、幂等事务、虚实互斥；禁止用删除重造冒充完整物品/角色/车辆转移。
5. 验收纪律：静态检查、纯逻辑测试、SP、MP、故障恢复分别记录，不能相互替代；没有运行就写未验证。
6. 编辑与交付规范：保留用户改动，CN/EN 翻译成对，发布清理调试内容，执行当前可用且适用的检查。
7. 极少量导航：需求原文、当前批准设计、基线、待办/验证证据的入口；只按任务读取相关细节。

不建议每次加载其他模组的开发史、已完成任务流水、固定行号/API 数量、工具事故经过、未经复核的旧结论。也不应把本报告全文塞进 AGENTS.md；给一个按需阅读指针即可。

工作区 `OnClientCommand` 约定还存在可具体纠正的错误：当前服务端实际触发顺序是 `(module, command, player, args)`，player 是第 **3** 项，不是第 4 项；项目旧 instructions 又有收发事件方向写反的表述。E12。这类事实应修正后再入精简规则，而非因为文件名是 AGENTS.md 就继续传播。

## 13. 最终结论与范围声明

**同意“独立重建核心”的方向；建议在修订上述技术假设后立项。** 交易、抽象库存、虚拟商队与升级循环可以优先形成完整可玩闭环；MP 人类 NPC、真实车辆转换和完整防破坏应各自视作带通过条件的技术模块。

本报告已经完成需求覆盖、当前 JAR 核查和主要调用链审阅，未完成实机证明。风险项的“待验证”是明确的项目边界，不应在后续文档中被省略成“全部可行”。

本轮产物只包含需求快照、评审与证据，不改变旧模组运行行为、不部署 JAR、不更改 AGENTS.md。
