# 当前仓储/物流的Java下沉评估

日期2026-10-21；状态：只读代码评估，未迁移代码、未做游戏CPU对比。基于0.15.1/PZ42.21.0/ZombieBuddy2.3.4；已重读唯一在线正文，哈希仍为3A179F1907B8971E0DD13F8FC2FFA300F0661E6F68C7AA0E7EC3E37202499834。

## 优先级与依据

1. **原容器批量读取/物品ID定位，优先。** shared/InventoryView.scan由WorkAgent.nextStep反复建立源箱/NPC库存/目标箱索引，每步32件切片，总体仍扫描每个容器；每件动作推进后重建会重复遍历同一大箱。Java批量读取ID/位置/重复ID/必要属性，可减少Kahlua循环、桥接调用与临时表。建议先下沉读操作，返回小批结果或稳定句柄，不迁移任务账本/物品认领；Java同样保留时间/数量预算和结束校验。
2. **物流候选读取与原生容器查验，次优先。** LogisticsPlanner在每个ROUTE步骤重复sourceValid、getItems/size、contains(item)、resolve/revalidate；反向规则索引已减少目标数，但对大箱反复contains及每候选原生属性调用仍有额外成本。先合并同切片的物理查询、缓存只读候选，减少重复工作，再评估Java；不能仅把原有重复扫描改写为Java循环。
3. **脏箱仓储盘点/去重汇总，后续同一接口的消费者。** WarehouseIndex已有全局128单位切片、脏箱缓存、最多20000件/2048类型和分片归并。Java可承担原生读取和批量聚合，Lua继续规则分类注册及呈现。不能把全部原件先逐项搬到Lua再排序，抵消收益。
4. **搜索/排序，条件性。** WarehouseQuery按快照/搜索/分类/排序缓存，分页60行，非递归归并避免Kahlua递归排序溢栈；目前不是每帧全量排序。若实际输入/大库存延迟明显，再考虑Java持有不可变标量快照，返回分页ID/计数。无需先迁移此项。

## 应保留的分工

Lua：用途/过滤规则、第三方分类注册、任务意图与状态转换、持久账本命令、界面与翻译、小名单/空间桶/公平轮转。Java：大批原生对象读取、连续数值/集合工作、引擎角色/运动/检查点序列化。现有真实路径跟随/人物物理更新和原版物品动作本身已经由Java引擎执行，不是Lua重写了寻路或搬运动画。

Java不是后台线程许可。IsoCell/ItemContainer/人物等活对象读写仍按游戏主线程边界处理；只有脱离引擎对象的不可变纯数据计算才可评估后台执行。迁移后仍需脏标记、分片预算、权限/对象/物品ID/容量最终复验；第三方或玩家改变物品不一定都能被本模组通知覆盖，不能只信缓存代次。JS/Lua与Java间应批量交接，避免每件/每字段额外调用。

## 当前建议

下一个可批准切片是**Java批量库存读取/定位适配器**，先由原物品定位消费，再复用到盘点/物流。接口保持业务权威在现有执行层，不改物品身份或删除重造。性能采样应覆盖scan/resolve/contains/route与桥接次数，避免只看UI帧耗时。已有WarehouseMetrics覆盖index.slice、ui.query等，但尚未覆盖物流定位核心，也没有本轮实机样本；以上是候选优先级，不是已证明的瓶颈或帧率收益。
