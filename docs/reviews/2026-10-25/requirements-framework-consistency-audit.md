### 4.2 后续需求前必须收口的接缝（真正的冲突风险点）

1. **工种 Provider 注册契约**（0.24.2 审计#4）：PublicWork 仍硬编码 crafting/hauling，新增农夫（架构P4）/医疗/哨卫（架构P5）都要改公共协调器——直接违背 §0"新增内容 0 侵入"与 §8 注册表目标。BACKLOG 已排"最小 Provider 注册契约"，须在接入第三工种前完成。
2. **派工吞吐与规模**（0.24.2 审计#1 + 0.26.0 性能热点）：§3.3"人口无硬上限"与当前"每200ms单 NPC 轮转+预检绑定轮转"存在规模张力；Job512/Order256/容器256 是记录上限不是容量承诺。按 BACKLOG P1 先测 1/5/10/20 NPC 再谈容量。
3. **三大公共注册 API**（§8 registerReliefAction/registerTown、§4.5 registerActivity）：尚未创建。已有 PageRegistry/LaborProducers 注册先例，届时应统一注册表模式，避免三套风格各异。
4. **材料匹配真实预算**（0.24.2 审计#2）：重叠可选材料+大批量的递归匹配未按操作计费，§5.3 批量线性场景会放大。
5. **结清清理遍历预算**（0.24.2 审计#5）：接近记录上限时的后台重复扫描峰值。

### 4.3 无设计覆盖的需求块（启动前需先做从属设计+在线逐节核对）

- **经济/以物易物/商队**（§6 全部）：仅可行性 A 类裁定 + A-Life 参考；SP-first 下维持后置（BACKLOG"后续范围"已列）。

### 4.4 结论

**无架构级冲突**：已确认框架（稳定 UUID 身份、意图-校验-会话-证据链、唯一结算者、版本化持久化与防重放、纯逻辑 shared 层、组件化状态驱动 UI）与在线需求后续全部方向兼容，不需要推翻或重写。需求侧所有已知冲突都有明确权威裁决（用户决定/唯一架构/v3.3 待粘贴稿），无一悬而未决；风险集中在扩展接缝收口、规模实测、注册 API 统一三点，均已有审计建议与 BACKLOG 排序承接。
