## Six ambiguity decisions

1. **Terminal CANCELLED uses Store.cancelJob; SETTLING stays a separate mutate.** Participant `:91–103` checks KNOWN, empty obligations and stopped-if-started, invokes releasePlacement, re-peeks, writes SETTLED/SETTLING if needed, re-peeks, then terminal. finishActivity `:194–197` has already committed empty claims. JobStore (`shared/JobStore.lua:210–220`) requires a CANCELLED patch, matching revision, KNOWN, no obligations and no proposed claims. All guards are met at the terminal write. SETTLING is observable through JobStore notifications (`:125–130,200–205`), so its revision is preserved, not used as a reason to bypass cancel. Forced settlement checks scene closing/withdrawn, absent Runtime ownership, absent participant handle, absent personal pending cleanup and empty obligations (`Participant:67–89`). Adapter `:174–180` first commits stopped=true, empty claims, SETTLING/KNOWN; the tail then sets step SETTLED and uses the same cancel entry. No explicit activity cancel API was invented; DONE remains mutate.
2. **Step-wise revisions preserved.** Submit writes point/sequence/single tile, then acquires the activity token. Failed acquisition still clears through a second mutation (`:237–241`). Main chain revisions are 1 INVITED, 2 point/claim, 3 WAITING/RUNNING, 4 LEAVING/STOPPING with claim, 5 STOPPING with empty claims, 6 SUSPENDED, 7 SETTLED/SETTLING, 8 DONE or CANCELLED. Wedged SETTLING retains its existing step until the terminal tail. No write was collapsed and no token was moved into a payload.
3. **Write-then-release preserved.** `client/LaborJobCommit.lua:52–72` dispatches the existing bridge. Java `java/src/main/java/emberroutes/probe/LaborCommitKernel.java:75–99,137–180` checks revision/token/ownership, extends, applies capacity, shrinks, then CAS; terminal release/cleanup is after CAS. Nonterminal finishActivity and wedged adapters perform full release/clean only after successful mutate (`:178–180,195–197`). removeKeys is a transactional shrink, not an early full token release. A failed CAS restores ownership in the host model and leaves the original declared tile/token intact. No Lua recovery fallback, retry, quarantine state machine, Java contract change or TaskRuntime redesign was added.
4. **Shared identity remains OPEN.** claimActivity `:103` uses `ensureEntityClaimId`. `client/LaborStore.lua:30–39` allocates and writes missing/invalid identity for all domains; no ACTIVITY-only allocation branch exists. Creation now allocates inside the existing kernel create transaction (`LaborCommitKernel.java:186–224`), but that does not migrate shared repair. Global candidate scan includes ACTIVITY (`LaborStore:98–100,118`), collision repair directly changes claimId/state/effects (`:147–161`) and quarantine metadata (`:168–188`). These shared pre-publication writes remain explicitly external and untouched.
5. **Recovery timing differs.** `client/BuiltinLaborRecovery.lua:10` registers ActivityJobRecovery.restore. LaborStore `:296` calls recovery before publishing root/claims/domain caches at `:331–339`. The `current.taskJobs.byId` Jobs are aliases, not detached staging copies: ActivityJobRecovery `:9–23` directly writes RECONCILE_REQUIRED/UNKNOWN on conflict or acquire failure, without a revision increment. These two failure-write branches are **retained OPEN, queued for a future publication-boundary adaptation**, not actually enqueued in this segment and not forced through Store.data recursively. Success only rebuilds an index (`:25`) and is not a Job commit. Its pre-existing unconditional true return / ignored observation-write failure (`Participant:372–382`) remains unchanged; this is not proof that all recovery writes succeeded.
6. **SELF_CARE is read-only dependency here.** Participant reads peekPersonal and Responsibilities (`:21–25,167–172,344–357`); `client/ActivityResponsibilities.lua:53–72` determines associated pending cleanup and actual participation.
