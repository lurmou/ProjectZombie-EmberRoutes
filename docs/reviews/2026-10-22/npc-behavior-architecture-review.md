# NPC 行为架构调研与推荐方案

> 日期：2026-10-22｜状态：调研归档；最终架构已获用户确认、未实施｜范围：当前单人实体 NPC，保留未来权威适配接口。

后续统一参照[已确认架构设计 v1](../../superpowers/specs/2026-10-22-npc-behavior-architecture-design.md)。本报告保留调研事实和比较，不作为并行实施设计。用户已澄清在线第 10 节是技术推荐，不是必须采用的约束；最终选择小型行为树基于工程判断及用户确认。

## 1. 结论

推荐采用：**宏观 HFSM → 分级效用仲裁 → 每 NPC 当前任务控制器 → 小型微观行为树 → 原版动作适配**。任务恢复点、原件托管和持续设施义务保存在业务记录中，不依赖行为树节点的运行现场。

这是本轮针对当前需求和代码比较后的明确选型，不是“所有游戏中的最优算法”或实机验收结论。批准后可以据此细化实施设计；原生动作停止、部分效果核对和保存交接仍需实现与实机验证。

修正此前“先采用步骤执行器、暂不建设行为树”的建议：复杂生活行为需要替代选择与子流程，小型行为树有长期组合价值。在线第 10 节为技术建议，不将它作为强制选型理由。保留步骤的明确契约，将它们作为树的可复用动作叶，而不是再建立与树并行的第二套流程运行器。现有制作和物流状态机先以适配叶接入，逐步迁移。

不推荐继续靠各模块互相取消来协调；也不推荐现在建设全局 GOAP/HTN 搜索器、通用图编辑器或重写全部已实现任务。

## 3. 当前代码核查

| 入口 | 实际实现 | 对选型的影响 |
|---|---|---|
| `shared/EmberRoutesProbe/Boot.lua` 的 `tick/cancelAll/cancelEvery` | 顺序调用制作续工、动作、搬运、Work、Companion、物流等；取消是多模块调用，没有统一交接返回值 | 启动、自动唤醒和保存恢复都必须经过同一当前任务控制器 |
| `Work.lua` 的 `registerExecutor/nativeExecutor/retained` | 已有注册与门禁；以执行器 `busy` 和 `retains` 判断冲突 | 复用注册方式，但不能把托管资产当作身体占用；不能依赖 `pairs` 找到首个 busy 来处理双重拥有者 |
| `Work.lua` 与 `Companion.lua` | 各自 `Schedule.new()`、每轮至多 4 个 NPC | 已有预算；还缺跨行为的共享预算分配，不能声称完全没有调度 |
| `WorkAgent.lua` | 每 NPC context、`start/poll` 步骤、原件 ID 核对、100ms 轮询；暂停先失效代次再清队列 | 适合作为首批适配流程，保留物理后置核验 |
| `CompanionAgent.lua` | 跟随/返家直接调用 Driver；命令时调用 `cancelAll` | 转为控制器下的跟随任务，不能保持独立发指令的权限 |
| `Driver.lua`、Java `ProbeRuntime.commandFor` | 校验载体身份和本地执行条件，没有行为会话令牌参数 | 第一阶段需覆盖实际指令入口；仅在高层添加 busy 标志不足以防止绕行 |
| Java `ProbeNpc.stopProbe/moveTo` | stop 同时停止动作与寻路；moveTo 先调用 stopProbe | 不能只包装 Lua 动作队列；移动请求本身也会中断动作 |
| `Production.pause/execute/tickPending` | 清动作、停移动、释放自占平台；保存/补料可直接重启；提交不明确时阻断 | 保留提交保护，自动重启必须变成候选请求，禁止绕过仲裁抢占身体 |
| `CraftProbe.lua` | 为 Work 注册制作执行器，委派格式 3 给 Production；`retains` 按未释放记录判断 | 暂停制作不等于解除原件托管，也不应阻止独立生活任务 |
| `LaborStore/LaborClaims/CraftRecord` | 已有声明、容量预留、任务代次、格式迁移；现有结构禁止同 NPC 同时存在未完物流和制作记录 | 多任务挂起需要显式 schema 迁移；不能仅加列表后继续沿用旧互斥校验 |
| `LogisticsService.advance` | 结合 Work 门禁、随从 HOLD、原生队列与健康条件分配/恢复任务 | 后续由仲裁统一判断可用性，服务只产生工作候选 |
| `Persistence.captureOnSave` | 保存随从意图、取消执行、逐 NPC 检查点，随后恢复随从并安排制作续工 | 必须增加保存屏障和单一恢复入口，避免多条恢复路径争抢控制 |

这些发现是静态结构事实，不表示已经复现双重控制或重复物品的实机缺陷。

## 4. 原版动作为什么要求独立执行契约

本轮实际安装 Lua 中：

1. `ISTimedActionQueue.add` 对空队列立即调用动作 `begin`；动作的启动副作用可能发生在入队调用内，不能假设下一 tick 才开始。
2. `ISTimedActionQueue.clear` 会调用角色 `StopAllActionQueue`，并处理未开始动作的取消；“当前动作正在增加子动作”还有专门分支。单纯看到某个动作不在 Lua 队列里，不足以证明角色已静止或效果未发生。
3. `ISHandcraftAction.stop` 调用取消回调，也调用完成回调；完成回调不能直接当作成功证据。
4. `ISEatFoodAction.stop` 在单人调用 `serverStop`，符合条件时按进度进食；取消可能已经消耗部分食物并改变角色属性。
5. `ISDrinkFluidAction.update` 在非客户端逐步调用 `updateEat`；消耗并不只发生在最后提交。
6. `ISBaseTimedAction.stop` 重置 Lua 队列；`perform` 推进下一动作。清理和回调存在重入可能，控制交接不能在清理尚未返回时授予新任务。

因此动作叶需要明确三类效果语义：尚无物理效果、渐进效果、一次提交效果。动作开始也可能有独立副作用。中止时观察实际原件/流体/角色状态，而不是通用回滚；不伪造补回物品，也不盲目重演。

## 5. 参考案例：借鉴什么、不推导什么

### MineColonies

核查官方仓库提交 `d1573f78af389c66d3d673343e86ff3a32868561` 的 `CitizenAI`、`AbstractAISkeleton`、`TickRateStateMachine`、`EntityAIEatTask`。高层选择生活/工作状态；职业内部状态机带更新间隔和中断条件。借鉴分层与有界更新，不照搬职业绑定，也不能推导其具备本项目所需的原件恢复协议。[官方源码](https://github.com/ldtteam/minecolonies/blob/d1573f78af389c66d3d673343e86ff3a32868561/src/main/java/com/minecolonies/core/entity/ai/workers/CitizenAI.java)

### RimWorld

读取可访问的旧公开反编译稿中的 `Pawn_JobTracker`、`JobDriver`、`Toil`、`ThinkNode_Priority`：任务选择与执行分开，每角色有当前任务/执行器，任务内部由步骤推进并清理；可挂起的任务能重新排队。它不证明任意步骤可无损恢复。较新反编译仓库本次返回访问封锁，未继续取该仓库内容，不能宣称核查当前最新版。[旧任务管理源码](https://raw.githubusercontent.com/josh-m/RW-Decompile/master/Verse.AI/Pawn_JobTracker.cs)、[旧执行器源码](https://raw.githubusercontent.com/josh-m/RW-Decompile/master/Verse.AI/JobDriver.cs)

### Stonehearth

官方文档描述规划、执行及停止生命周期。其 AI 运行现场不写入存档，任务须在加载时重建；这支持区分运行现场与业务记录，不能当作 PZ 原件恢复已解决的证据。[官方 AI 文档](https://stonehearth.github.io/modding_guide/modding_guide/advanced/ai/index.html)

### 行为树、StateTree、设施槽位

Chris Simpson 的文章说明可记忆运行节点、组合子树；UE 官方行为树说明事件驱动实现。行为树并非必然每帧全树遍历。StateTree 展示层级状态与过渡，Smart Objects 展示设施能力和槽位声明。分别借鉴组合、唤醒和设施边界，不照搬其并发或持久化机制。[PZ 作者文章](https://www.gamedeveloper.com/programming/behavior-trees-for-ai-how-they-work)、[UE 行为树](https://dev.epicgames.com/documentation/en-us/unreal-engine/behavior-tree-in-unreal-engine---overview)、[StateTree](https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-state-tree-in-unreal-engine)、[Smart Objects](https://dev.epicgames.com/documentation/en-us/unreal-engine/smart-objects-in-unreal-engine---overview)

## 6. 方案比较与裁定

以下为基于需求与源码的工程判断，不是性能基准结果。所有方案都必须另有资产核对、恢复与动作白名单。

| 方案 | 优势 | 主要代价 | 裁定 |
|---|---|---|---|
| A：宏观状态＋效用＋手写步骤/状态机 | 现有流程接入直接，原件核对易定位 | 随行为扩展重复编写选择、等待、退出和嵌套；须自行建立组合约定 | 保留为既有流程适配，不作为长期统一编排方式 |
| B：宏观状态＋效用＋当前任务控制器＋小型微观 BT | 符合需求；组合可复用；控制与资产契约不依赖树形状 | 需要少量节点运行时及严格中止契约；必须防止树和业务状态重复维护 | **推荐** |
| C：统一大型反应式 BT，或全局 GOAP/HTN 搜索 | 复杂替代计划和跨领域推导表达力强 | 全域决策/规划、失效和搜索预算更复杂；原件提交问题仍在；迁移面大 | 当前不选；生产配方链继续独立规划 |

选择 B 不仅因为迁移便宜：现有及后续需求横跨进食、设施、医疗、协作，组合节点有长期价值；同时本项目最敏感的是引擎副作用和真实资产，必须让它们具有独立于树的业务契约。

## 7. 推荐架构的具体边界

### 7.1 宏观上下文和分级仲裁

HFSM 仅保存据点生活、队伍跟随、驻守、未来远征等上下文；岗位、技能、知识、健康是独立数据。先过滤权限、可达性、上下文和可观察条件，再按即时致命危险、自卫、安全条件下急救、紧急自理、常规工单、闲暇分级；同级内才使用效用和 0～4 工作优先级。

在线第 5.1 节的医疗优先简表与第 10 节存在表面冲突，采用第 10 节明确的自卫/救治条件规则：先脱离即时致命威胁，再优先急救。无逐小时排班；黄色战备不自动中断所有平民生产。加入切换滞后、失败冷却和最长等待诊断；紧急危险绕过普通切换滞后。

### 7.2 当前任务控制器独立于 Work

每个 NPC 有一个逻辑控制器，但不创建独立线程或定时器。控制器记录 `activeJobId`、运行会话代次及交接状态，统一授予冲突身体动作的执行权。工作、随从和自理均为消费者；Work 保留劳动服务与兼容入口，不能膨胀为包含全部生活策略的总模块。

分清需求、工单、执行任务与会话：需求可以产生工单；工单可有多个执行任务；一个任务可历经多次会话。任务、声明代次与会话代次分别管理。每 NPC 可有暂停任务和持续义务，但同一时刻只有一个主动身体执行者。

统一动作出口覆盖移动、停止、加/清动作队列以及保存恢复路径。不能只约束 UI 入口；旧诊断 Actions/Haul 和 Java 命令路径也须进入协议或被明确限制。未来一个战斗任务可在内部协调移动和攻击；不能让两个独立拥有者同时写同一角色。

### 7.3 微观行为树的最小范围

初期节点只提供记忆式 Sequence、Fallback、Condition、Action 和有深度上限的 Subtree。等待、限次重试和超时可通过动作叶表达。条件和候选评估不改变世界；动作叶通过控制器持有的会话发起真实效果。

普通节点结果保持 Success/Failure/Running。动作中止另设 `requestStop → 停止中 → 已静止/需核对` 协议，不把清理中误当成功或普通失败。Fallback 只有在上一分支的效果和清理状态允许时才能启动替代分支；有未核对效果时进入任务恢复，不能自动换材料或再次消费。

当前流程示例：进食可依次尝试自身可用食物、允许访问的分类库存；任务内部组合选择、接近、领取、进食和核对。生产配方链仍由 ProductionChainPlan 计算依赖，不交给行为树穷举。

不增加树编辑器、任意表达式 DSL、无界 Retry、任意 Parallel 或整个运行树序列化。世界观察和炉具监管是独立预算服务，不能随子树退出自动丢失。以后新增节点也必须遵守同一中止与动作出口契约。

### 7.4 身体交接与效果核对

普通切换等待有时限的安全边界；紧急需求按动作类别停止并登记恢复点；即时危险立即请求停止，达到原生静止条件后授予撤离任务，不等待无关的物品归还完成。

交接期间禁止旧流程派发下一动作。原生 stop/回调允许上报其所属动作已经发生的效果，不能因执行代次过期而丢账；但旧回调无权重新制作、清新任务队列或释放新会话的设施。使用世界身份、任务 ID、动作尝试 ID 定位核对记录；重复通知只更新同一事实。

不将所有“未知结果”都变成身体永久冻结：原生动作已停止且安全移动可确认时，允许撤离，相关资产继续隔离；身体状态本身不明则保持交接阻塞并诊断。这里是契约要求，原生停稳识别需原型验证。

### 7.5 持久任务、原件声明和设施义务

持久记录保存稳定步骤名、流程版本、原件 ID、效果状态和待清理义务；不保存 Lua 闭包或 userdata 队列。加载后重建观察、声明和流程，从业务恢复点重新验证。未知提交保留人工核对入口，不自动执行第二次。

继续使用 LaborStore/LaborClaims 的唯一资源协调，扩展任务索引而不另建库存账本。允许暂停生产与当前自理分别声明不同原件；共享分类箱过滤、隐私和最终资产验证。NPC 已持有物品不能因租约到期释放；无持有且无待提交效果的预留才按明确策略释放。

工具、材料、目标容量和设施槽位分别定义生命周期。资源申请使用固定顺序或有界批量尝试，失败撤销本次尚未生效的申请，避免双方长期各持一半资源；已持有原件的托管不能被这种撤销误释放。预留不保证未来目标容量不被玩家改变。

炉具监管记录包含设备身份、相关食物、启动归属、下一检查条件、责任人/接管状态。可在 NPC 离开后继续存在；需要实际取出或关火时产生任务。玩家使用和设备归属不明确时禁止擅自关闭。医疗协作未来通过稳定协作任务协调多个 NPC，不建立多个身体控制者。

### 7.6 调度和观察

复用轮转机制，增加全局预算协调：候选评估、库存扫描、寻路请求、配方规划和设施检查分桶计费；限制一次 tick 中立即完成节点及子树深度，防止 Sequence/Fallback 同帧无界推进。预算不足返回 Running/等待，不能视作目标不存在。

危险信号有快速通道；饥渴疲劳采用分散的低频采样和阈值唤醒，因原版状态并非都有可靠事件，不能承诺纯事件驱动。服务合并脏通知，保留已知可用、已知不存在、未加载未知、观察过期四类结果。

Lua 承担上下文、策略、树编排与业务恢复；Java 维持现有载体/移动边界。库存批量读取等经测量后再下沉 Java，不能预先给出“Java 一定更快”的结论。记录预算耗用、候选拒绝原因、交接耗时、扫描/寻路次数及有上限的决策轨迹。

## 8. 场景推演

以下是设计推演，未执行测试。

| 场景 | 推荐处理 | 必须防止 |
|---|---|---|
| 制作取料后口渴 | 停止制作身体执行；保留材料托管；饮水任务使用独立资源；结束后重新验证并续工 | 托管阻止喝水，或制作原件被再分配 |
| 制作提交时遇敌 | 当前同步提交返回后核对已发生效果；不能把逻辑原子性当成可阻塞主线程的锁；之后撤离 | 重做产物、无限等待原子区 |
| 吃到一半被打断 | 记录实际剩余食物和需求状态；下一次按当前状态选份量 | 从原份量重放或凭空补回 |
| 工具/箱子被玩家改变 | 旧候选失效，重验实际资产；需要时等待并说明 | 使用汇总数量代替真实资产 |
| 保存后随从与制作都想恢复 | 保存屏障后统一产生候选，由控制器只授予一个；意图仍保留 | 恢复路径互相 cancel 或同 tick 抢权 |
| 炉具工作时 NPC 去休息 | 监管义务仍存在，可指派其他 NPC；实际交接成功后转责任 | 子树退出导致无人监管 |
| 双 NPC 协作被危险打断 | 各自控制器独立撤离，协作记录保留阶段和资源；重新凑齐条件后恢复 | 任一 NPC 回调驱动另一人的身体或重复结算 |
| 目标箱未加载 | 保留未知并等待观察条件，不生成零库存结论 | 重复生产、盲目重建或双重宏观结算 |

## 9. 分阶段落地与验证门槛

1. **控制权和兼容迁移**：独立控制器、停止/效果协议、Work/Companion/Production/诊断/保存入口接入；既有流程先作为适配叶。相关最小宿主回归验证独占、重入、过期通知、保存候选；双 NPC 实机验证无双重控制及原件一致。
2. **生活闭环与小型 BT**：用统一节点跑工作→吃喝→恢复，再加休息；不同时重写全部生产。重点实机验证渐进消费、中断和正常保存恢复。必要的多任务索引版本迁移随本阶段前置完成，不能绕过旧冲突校验。
3. **人员管理**：0～4 工作优先级、岗位/区域、独立知识查看和批量传授；每人独立校验玩家知识、NPC 技能及结果。不做全部解锁或逐小时排班。
4. **烹饪和设施监管**：分别适配固定配方、加料与温度过程；验证关火归属、中断接管和冷藏交付。
5. **协作/医疗/守卫/远征**：复用任务、槽位、义务和控制协议，分别通过动作与性能关口。远距离实体/宏观执行仍须唯一交接。

必须测量后才能承诺的事项：原生停止确认时延、快速危险响应、保存中止/部分效果、规模下预算公平性及主线程耗时。本轮不提供未经测试的 NPC 数量或毫秒保证。

## 10. 决策范围

可以据本轮调研确定采用 B，并固定“控制/选择/组合/效果/持久记录分离”的边界。实现中允许调整节点名称和数据布局，但不得删掉独占执行、部分效果核对、资产托管和版本化恢复。

如果原型证明某类原生动作无法可靠停止或核对，应暂停该动作的自主适配并报告，不以更换行为树/状态机名称掩盖问题。当前最重要的验证不是比较几个空节点的 tick 性能，而是验证原版副作用在交接和保存中仍可解释。

用户已确认总体架构，后续以正式设计为准；本轮未进入代码实施。本报告不记为功能完成，也不修改在线需求。
