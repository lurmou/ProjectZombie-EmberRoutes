# 业务链架构收敛实施计划

范围由用户授权：在现有单人世界、唯一身体授权和 Java 提交边界内收敛已有业务；不增加兼容路径。已存在的并行工作及联机适配保留。

1. 固定搬运、制作、自理的创建认领、正常结清、未知效果与读档恢复边界；只运行直接覆盖这些边界的宿主检查。静态、宿主、真实磁盘和游戏内证据分别记录。
2. 维护提交职责：Lua 校验入口形状和领域规则；Java 同步重验修订、认领与资源并执行唯一提交。业务结清证据仍归具体领域，不让身体停止冒充资产结清。
3. 将 LaborStore 内搬运领域操作迁至 HaulJobs，调用方直接使用领域入口；共享 Claims、容量和提交内核维持原职责。按实际依赖拆恢复与工具托管，保证冷恢复发布和失败顺序不变。
4. 领域元数据统一声明 ID、契约、候选 Provider 与退休谓词；处理 FIELD_WORK 多 Provider、无 Job 的工具归还，保持候选枚举、恢复顺序及调度优先级现状。shared 契约不能直接加载 client 模块；恢复与监视装配不混入领域执行框架。
5. 独立义务账本只保存责任及生命周期事实，类型处理器判定业务证据；Claims 保持独立。逐条梳理工具托管、持货、炉火监管和配送返仓的创建、变更、结清、转移、失败与重载。账本变更和对应 Job/资源变更必须由同一提交序列裁决；先完成原子发布及失败恢复契约，再整体切换生产者与消费者，不写双轨镜像，不因缺记录释放。
6. 核查身体停止的各观察信号与具体残留，保留身体交接和资产责任的独立结果；仅在参考项目和安装版原生实现提供依据时增加针对性恢复。未知效果继续留责。
7. 合并后集中执行相关边界回归、架构与国际化检查、构建；记录未运行的磁盘恢复、实机和性能验证。无 UI 改动时不扩展 UI 范围。

检查点：该计划不改变需求文档，也不证明各项已实现；实际持久格式及原子恢复方案须以完整实现和失败路径检查为准。

## 切换前审计边界（历史，不作为当前入口）

- 领域注册表为新建的启动期元数据表：内置声明完成后封存，客户端只按声明的固定路径装配。封存是本轮新契约，不称等价重构；既有 `PublicWorkProviders.register` 未改。契约注册顺序、分类枚举顺序和恢复顺序分别保持原值。
- `FIELD_WORK.work` 是未完成业务的终态守卫；退出前还要检查现场资产、效果和目录，不能只看 Job 存在。`CRAFT/HAUL.business` 是领域业务未结标记，迁移后必须继续验证原件、真实交付和未知效果。
- `SELF_CARE.RETURN_ORIGINALS` 记录来源和原件 ID，属于真实返还义务。原件仍在源容器、实际返源及 UNKNOWN 恢复各有不同证明路径；缺失或无法识别不能视为结清。
- 烹饪的 `water`、`storage`、`station` 与对应 payload 中的水源、容量、工位和 claims 一致性相连，迁移时改为明确的资源谓词并保留全部释放条件；`furnace` 另有停火、食物离站和关火回执要求，是真实监管义务。
- 工具托管跨 Job 存续，认领及释放由 `LaborStore` 的工具托管路径管理；真实入仓证明是归还结清条件。配送 UNCOLLECTED 是认领而非持有；CARRIED/RECONCILE 责任待处理，DELIVERED 必须有回执，WITHDRAWN 只允许尚未取走且不在活动尝试中的原件。返仓标志本身不证明送达。
- 所有现行 Job 的终态、取消与转移在切换后同时校验业务前置、资源事实与独立账本；账本缺失、未知记录或错误版本均拒绝而非清空。已有旧根必须在任何模板填充和数据修改前识别拒绝并保留；工具托管的独立修改也进入 Java 唯一提交内核。
- JobStore 当前保存载体和运行时权威分离（`JobStore.open` 的 data/carrier），Job 发布后再通知；`LaborCommitKernel` 在 CAS 前恢复资源、CAS 后异常要求重载。新增独立义务时须先构造并校验全部候选，在受控且不可重入的发布段同步发布后通知；既有 `Persistence.save` 明确不能取消引擎世界文件写。同步发布不等于经验证的磁盘事务。
