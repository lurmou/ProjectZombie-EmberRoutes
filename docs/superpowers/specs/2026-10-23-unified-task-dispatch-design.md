# 所有NPC任务的统一发现、仲裁与认领设计

日期：2026-10-23。状态：用户已同意收口，职责契约已纳入[唯一NPC架构v1.1](2026-10-22-npc-behavior-architecture-design.md)；未实现、未实测。本文是唯一架构第2、3、5、6节的从属细化，不是第二个权威架构。本轮只确认设计并核查迁移，不授权自动启动代码迁移。批量单位、视觉布局等明确保留的业务细节仍须对应设计细化。

## 1. 依据与问题

依据本轮已读取的[最新在线需求及差异](../../reviews/2026-10-23/requirements-update.md)，全文快照SHA256为1E802DFE03A43437C77DC8EF5D04A2E38EC9AE9970A71D349B302B9EFE2EFB08。公共任务由NPC依据工种权限、技能和0～4优先级认领，禁止在普通生产下单时指定人员。用户进一步明确：架构须覆盖清洁、烹饪、守卫等所有任务，不能为制作临时选一套调度。

本稿不重新选择框架：继续使用宏观HFSM → 分级效用仲裁 → 统一任务控制器 → 小型BT → 原版动作适配。补齐的是所有业务如何接入同一个任务系统。

当前生产记录按NPC保存、Production入口要求npcId、统一会话运行入口未接通。这是待迁移基线，不作为新架构的永久约束。现有最低存量固定NPC设计不得继续扩展成另一个自动派工器。

## 2. 方案与决定

比较三种方案：每工种独立任务池/调度器会重复实现抢占、去重和恢复且相互争抢；一个全局FIFO大队列无法体现逐NPC工作偏好与个人任务；统一任务协议加共享索引可复用协调机制，并保留业务差异。本稿选择第三种。

“公共任务池”是可领取工作的统一逻辑视图，按据点、工种、区域、状态建立索引，不要求全部存在一个数组里。每工种可以维护业务记录和候选缓存，但不得拥有独立选人、身体授权、跨业务资源账本或自动恢复入口。

## 3. 对象分层：不把所有事情都叫工单

| 对象 | 内容及归属 |
|---|---|
| Demand需求/Policy策略 | 维持库存、清洁指定区、哨位常驻等长期目标；只生成或撤销工作需求 |
| Order工单 | 持久业务安排，记录数量、条件和已确认效果；制作需要，清扫一个污物不必先造生产工单 |
| WorkOffer工作候选 | 一段现在可以申请的工作，含稳定业务键、工种、目标、版本、可领取槽位；不绑定具体NPC |
| Job执行任务 | 某NPC获领的具体工作，关联候选、父工单/策略、恢复点、效果和资产义务 |
| Session执行会话 | 当前控制身体的唯一许可，代次独立于Job；暂停Job不等于销毁它 |
| Claim资源声明 | 原件、设施、槽位、容量等协调，沿LaborStore/LaborClaims唯一权威扩展 |
| Obligation持续义务 | 炉具监管、携货交付、归还、哨位待接替等，不随树退出或候选过期消失 |

同一个工单可以先后有多个Job，但数量分配必须互斥。首版同一生产链只允许一个活动执行分段，后续跨NPC协作须显式增加可分配分段及额度，不能简单把maxWorkers改大。Job可以被暂停并再次获得Session，不因此重新认领相同工作。

## 4. 三类候选，共用仲裁与执行

| 类别 | 例子 | 选择约束 |
|---|---|---|
| 公共工作PUBLIC | 制作、做饭、清洁、搬运、农业、守卫岗位 | 合适NPC竞争槽位；创建时不指定具体人 |
| 个人候选PERSONAL | 自己吃喝、睡眠、治疗自己、玩家指定该随从的跟随/移动 | 仅对应NPC可选，不进公共竞争；仍须经过优先级及Session控制 |
| 责任候选RESPONSIBILITY | 自己携带材料的归还、已启动炉具的监管、已有任务恢复 | 绑定现有责任人；转交须明确业务交接，不能普通超时重新领取 |

医疗他人可以是公共工作，患者是目标而非执行者；自己急救是个人候选。玩家直接命令是输入来源，不自动获得压倒一切的最高优先级；不能强迫NPC忽略即时危险或原生动作尚未停稳。生产下单禁止指定人，不影响跟随指令本身必须知道跟随的是谁。

## 5. 业务提供者：各工种只负责业务

每个Provider注册typeId、workCategory、schemaVersion及以下协议：

- discover(change,budget)：根据已知世界与业务状态，增量提交/失效候选，不在每次NPC决策时全地图扫描。
- evaluate(npc,offer,observations)：纯评估，返回允许/阻断/未知和分数要素，不扣料、不移动、不隐式学习配方。
- prepare(job,grant)：权威重验，取得必要资源并构造业务恢复点；只能通过共享声明权威申请资源。
- createBehavior(job)：构造现有执行器适配叶或小型行为子树，不能直接越过Session发动作。
- requestStop/observeStop/recover/settle：按动作效果和原件状态中止、恢复及结算；未能确认停止不能假报完成。

候选记录只含稳定ID和标量描述：offerId、dedupKey、scopeId、visibility、ownerNpcId（非PUBLIC才允许）、providerType、targetId、workCategory、revision、state、slotCount、业务记录引用。工单/Job/原件是持久事实；派生候选索引可重建，不保存userdata或闭包。

| 业务 | 候选来源与去重单位 | 完成或持续责任 |
|---|---|---|
| 制作/烹饪固定配方 | 玩家Order或最低存量Demand；orderId+可分配分段 | 实际制作并交付；依赖未就绪不公开可执行根分段 |
| 温度烹饪 | 已登记设施、食材/配方任务 | 准备/加热/取出分别为工作阶段，监管独立为Obligation，不长时间霸占身体等待 |
| 清洁 | 指定范围及可观察污物事件/有界巡检；位置+污物类别+目标版本 | 原版清理后置核验；同一污物不会被多人重复清理，新增污物产生新版本 |
| 搬运/分拣 | 容器标签、实际物品变化、任务交付需求；原件ID+去向+需求归属 | 真实取放及交付；无独立玩家物流调度页 |
| 守卫/巡逻 | 哨位/路线策略；postId+slotId | 值守持续到安全交班；轮换是业务协议，不因候选不断重建而离岗 |
| 农业/修理/医疗 | 对应策略及地块/设备/患者当前可观察需要 | 各自白名单动作、资源、效果和安全边界 |
| 吃喝休息/跟随 | 个人观察及直接命令 | 私有候选，仍复用任务控制、恢复和资源协议 |

运输既可以是制作Job内部的取料叶，也可以是独立搬运Job；同一份运输工作必须有唯一owner，不能同时公开给搬运工又由制作NPC执行。跨NPC运输未通过明确交接协议前，保持现有单Job内部取料。不是因为有搬运工种就必须把每次取料拆成公共单。

## 6. 共享TaskDirectory与任务生命期

一个世界运行服务管理目录，按scope/category/area/visibility/availability建索引。据点是权限与查询分区，不是不同调度实现。单人与未来服务端适配复用命令边界；当前MP不启用。

Provider按dedupKey幂等upsert候选，同一需要的重复事件只更新revision。候选状态为AVAILABLE、BLOCKED、ALLOCATED、WITHDRAWN；Job状态为PREPARING、RUNNING、STOPPING、SUSPENDED、SETTLING、DONE、CANCELLED、RECONCILE_REQUIRED。候选不是Job状态的副本：目标仍在但暂缺工具可以BLOCKED，已领取则ALLOCATED，Job自理暂停时仍保留分配。

Job按jobId存储；byNpc是活动/挂起任务ID索引，不能继续用npcId作为业务记录主键。Order与Job保留双向关系，NPC仅是已分配执行者。旧byNpc单任务及物流/制作互斥校验必须版本化迁移，不能删掉校验后继续写老格式。

Job终结不自动代表Order全部完成；只有业务结算确认数量、效果和义务后，才释放相应分段额度。取消Offer只禁止新领，不删除正在执行的Job。业务目标消失时，活动Job进入安全停止/收尾。

## 7. NPC如何决定做什么

决策不是所有任务共享一个总分后抢最大值。先按既有架构的紧迫等级分组：即时致命危险 → 自卫 → 安全急救 → 紧急个人需求 → 常规工作 → 闲暇。上级不能被距离、工作分或排队年龄抵消。

每NPC先依据HFSM上下文、岗位/区域、工种权限、身体能力、技能、配方条件、可观察资源、任务责任及当前交接状态过滤候选。0表示该常规工种禁用，1最高、4最低；不将0解释为最高优先级。自理和生存紧急性不由普通工作矩阵禁用。

常规工作按本NPC的工种优先级先分组；同级再比较业务紧迫性、恢复连续性、技能适配、粗略距离和等待时间，最后稳定ID打破平局。等待加成有界且不跨越玩家设定的优先级。不会为了给禁用/低优先级任务“公平”而违背设置；UI可说明长期无人接单的原因。

先用缓存坐标估距离，只有选中少量候选才请求有界寻路。未知权限、资源或未加载目标不是“可用”，也不是“不存在”；记录待观察，不能凭未知领了再反复失败。

NPC只有到决策点才重新选工作：新任务、当前安全边界、危险、需求越阈值、条件变更或分散低频复验。普通更高分候选不每tick打断当前工作；切换须滞后和最短有效区间。危险可请求立即停止，仍按原生停止与效果核对协议授权下一个动作。

## 8. “自主认领”与唯一权威如何兼容

NPC决策器提出候选偏好，不直接修改共享记录。世界级DispatchCoordinator只处理公共工作分配，重验offerRevision、权限、当前任务及资源；普通同级申请轮转处理NPC，不由最低ID永远先抢。个人自理直接进入本NPC分级仲裁和TaskController，恢复已有Job也不重新领取公共槽位；二者仍须申请Session及必要资源声明。危急自理不得排在普通公共申请预算之后，亦不得绕过原生停止确认。无需用中心算法穷举全员全任务最佳匹配。

认领逻辑事务：复验候选 → 占用唯一分段/岗位槽 → 建立Job及双向链接 → 申请当前执行会话 → 通过共享权威准备必要资源 → 授权真实行为。提交前再次核查目标和库存，缓存评估不是执行授权。

准备失败：只撤销本次无效果且可释放的分配/资源；有携货、已开始动作或未知效果则保留Job与义务进入恢复/核对，不重新公开原额度。认领和启动可能同步重入，先发布完整关联，再允许动作开始。

所有推进命令包含world身份、jobId、offer/分段代次、session代次和attemptId。重复认领或提交命令幂等返回已有结果。租约只可回收能确认从未启动、无原件托管、无效果的准备槽位；不能用超时回收NPC背包里的材料或正在提交的任务。

临时自理：旧Job挂起保留分配和资产 → 释放身体会话 → 执行私有自理Job → 核对原件及义务后选择恢复。仍有生产材料/工具托管时，不领取无关普通公共工作；先恢复、交付、归还或明确交接。危险/急救等更高等级需求不受此限制。工作台损毁、仓库不可达时进入有原因和复验条件的恢复/归还等待，不能永久冻结身体，也不能携货不断领新单。NPC离线/死亡不自动把其携货额度再给别人，先定位真实物资和交接责任。

换人：先停稳旧执行者，核对效果和原件，确定可交接恢复点，提交责任与声明转移，再向新NPC创建/关联后继Job。身体已停但资产结果不明可以允许安全撤离，但该业务额度隔离。多人协作只通过不同分段/槽位的协调任务，不能两人共享同一个动作恢复点。

## 9. 长期工作、设施监管与工作轮换

守卫不是完成一次移动便DONE，也不能永久占据最高工作分。策略描述岗位数及值守条件；每岗位槽记录唯一在岗责任人和至多一个替班预约者，替班预约不是第二个正式岗位。疲劳派生独立handover候选，接班者领取预约、确认到岗且旧人可交接后，按岗位版本原子替换责任人。预约失败/过期仅释放无效果预约，不清在岗者责任；重复到岗回调不得二次交接。紧急撤离可先离岗，明确显示无人值守。无合适替班者显示缺人，禁止伪造交接；不假定原版存在专用交班动作。

炉具加热期间NPC可做别的工作，但炉具义务仍有责任人、检查期限及告警；到期生成受紧迫性规则约束的责任候选，危险优先。监管可交接但不能因为Job结束自动无人负责。玩家设备归属不明仍沿原架构禁止擅自关闭。

持续任务须声明安全工作片段/检查点/复验时刻。无需把所有行为强制转成固定秒数小任务；具体值由相应业务按风险验证，不在通用调度器硬编码“所有工作30秒”。

## 10. 生产与最低存量的位置

单次制作：玩家提交据点Order → Provider按依赖生成可执行Offer → NPC按矩阵认领 → 创建Job → 复用现有Production/BT适配执行。原版配方菜单只提供快捷入口，不直接指定NPC启动。

最低存量：只检查已确认的仓内实物P与阈值M；P<M时按配置的单次补货量创建一个幂等Order；活动周期/未完成订单抑制重复触发。生产Order照常进入公共目录，规则不选人、不调用Production.execute、不拥有身体或资产。固定补货量的单位与达到阈值是否继续完成该批次须在最低存量修订稿明确，不能继续默认旧的D=M-P提前收束语义。

配方链仍由业务规划器负责，不交给全局调度器穷举。配方掌握严格回归原版机制：NPC必须通过阅读实体配方杂志（调用原版ISReadABook整本读完）或技能升级将配方写入character:getKnownRecipes()后方可认领制作，彻底废除在制作工序前强插“2秒研读”的形式主义机制。书籍为据点书架中的耐用物理资产（传阅不消耗）；若工单暂无熟练工掌握，工单挂起显示缺配方，并可驱动对应工匠在闲暇/研习时段去书架借阅杂志学习，读完学会后再行认领开工。根单创建与NPC执行条件分开验证，无平台要求配方不能虚构工作台需求。不同前置步骤需不同工种时，未来按分段依赖派发，当前不承诺跨工种链已实现。

## 11. 模块与扩展边界

| 通用模块（目标职责，非已实现） | 负责 | 不负责 |
|---|---|---|
| TaskDirectory | 持久Job引用、派生候选索引、去重和版本 | 世界扫描、业务完成判定 |
| TaskProviders | 类型注册与标准协议检查 | 各工种独立派工循环 |
| WorkSelector | 逐NPC过滤、分级和排序，输出申请 | 偷改世界或持久账本 |
| DispatchCoordinator | 唯一分配事务、申请轮转及分段额度 | 替代效用层或控制身体 |
| TaskController/ExecutionSessions | 当前身体、挂起任务、停止交接和恢复授权 | 独立库存账本 |
| LaborStore/LaborClaims | 统一资源协调及恢复声明 | 按超时删除真实货物 |
| Behavior/Action adapters | 子树及逐动作效果/停止协议 | 全局选工、重新领取订单 |
| 各业务Provider | 工作发现、业务恢复与后置条件 | 另建调度器或直接cancelAll |

逻辑职责不要求一开始创建七个框架目录；先按实际依赖实现小模块，不建脚本DSL/通用插件平台。新增清洁等业务主要增加Provider、动作适配、业务记录及验收，不复制认领/恢复/抢占逻辑。新增状态或抢占语义须评审共享契约，不能用注册接口掩盖跨层改动。

## 12. 性能与生命周期

共享调度器轮转推进Provider发现、脏NPC评估、认领提交及行为节点；分别设置全局预算，不能每NPC各自扫全池或寻路所有目标。预算不足保留游标，下轮继续，不当作缺料/失败。危险通知有独立快速通道，业务仍需停止确认；主线程不阻塞等待。

事件只置脏，按索引失效到有关区域/目标/工种，不每次库存事件唤醒所有NPC。没有可靠事件的观察分散低频采样。候选有数量上限、观察版本、阻断原因与条件变化唤醒；具体初始预算在实施计划中给值并用样本测量，不宣传任意NPC规模或零开销。

后台服务不依赖UI订阅存在。UI只投影Order/Job/候选拒绝原因，关窗不停止工作。普通玩家无需维护“每种任务一张任务池页面”；生产有工单监控，人员有工作矩阵，守卫有岗位策略，清洁有范围设置，物流状态内嵌相关业务。

## 13. 保存与兼容迁移

保存时序以唯一架构第5.1节新增的双路径约束为准：提前准备可跨tick，原生OnSave只能同步捕获事实，不能等待异步停稳。OnPostSave不是落盘成功凭据，未停稳/效果未知记录UNKNOWN并阻止自动重放。安装JAR证据见[保存生命周期核查](../../reviews/2026-10-23/p1-save-lifecycle.md)。

保存屏障顺序：停止新分配和交接 → 控制器核对原生动作与效果 → 保存Order/Job/Claim/Obligation及关联 → 保存成功后只生成恢复候选。读档先迁移并恢复持久事实与声明，再重建候选，最后重验并授予Session；禁止Provider自己的OnLoad直接run。

持久ID按world/scope区分，不保存闭包、userdata、动作队列或整棵树。2026-10-23用户明确取消旧任务存档兼容，覆盖此前转换旧单为适配Job的决定：新格式不导入旧任务，检测到旧记录须明确拒绝自动启用，不自动清除或补造原件。切换前使用旧版本收尾或干净测试存档，实际清理另按用户指令。新格式自身的正常保存恢复、原件义务和防重放仍保留。失败保存不清关联、不派替代单，不承诺强退跨文件事务安全。逐步接线见[切换计划](../plans/2026-10-23-shared-job-cutover.md)。

旧物流、Production、随从、诊断入口需逐项接统一控制器；过渡适配器只能服务已有旧单，不能继续扩展固定人员普通派单。旧UI移除前保留未结束任务的查看/取消/恢复入口，禁止因取消物流页而让货物恢复失去入口。

## 14. 实施顺序：一个架构，多业务验证

1. 完成现有P1：统一身体控制和保存/恢复入口；保留生产/物流的业务执行器作为适配叶。
2. 建立共享任务记录、Provider协议、去重与认领。以制作、清洁、守卫三种不同模型验证接口：有限数量、空间目标、持续岗位。清洁/守卫未具备原生适配时可先做契约夹具，不冒充可用功能。
3. 接通最小逐NPC仲裁：工种0～4设置、能力过滤、公共/个人/责任候选及工作恢复。无需等完整人员UI或所有生活动作完成，语义不能由先到先得替代。
4. 用真实制作与至少一种其他业务完成端到端验证；再按已确认架构P2扩大吃喝/休息与小型BT、P3完善人员矩阵。对原P2/P3的最小优先级前移属于已纳入唯一架构v1.1的阶段细化，不静默宣称旧阶段已完成。
5. 最低存量、自动清洁/烹饪/守卫策略分别接需求端，复用同一领取和执行协议；不再为每业务写临时自动派工器。各原生动作仍逐项白名单验收。

## 15. 验收与禁止退化

- 同一公共工作两个合格NPC竞争：只取得允许的槽位/数量；一个工种禁用者不领取。
- 两NPC具有不同矩阵：各自按自己的优先级选工；高分普通工作不能压过即时危险或紧急自理。
- 制作、清洁、守卫同时存在：共享仲裁，实际完成证据由各Provider定义，无跨业务cancelAll。
- 持料自理后恢复：不重复领单、不丢原件、不把“暂时不工作”当任务释放。
- 清洁目标已被玩家清除、岗位被删除、设备失效：重验撤销新派发，活动工作安全收束。
- 炉火继续加热、守卫疲劳交接：义务不丢，超时不复制责任或假定接班成功。
- 认领后准备失败、同步回调重入、旧回调迟到：不双领、不清新队列，实际效果仍归账。
- NPC死亡/离线、保存失败、正常读档：隔离未知，按声明与真实原件恢复；不重新生产已提交结果。
- 限额/预算耗尽、关闭UI、持续大量事件：有界推进、轮转不饥饿，关窗业务继续，实测记录规模与耗时。

禁止以“先每工种各写一个派工循环，以后合并”“先指定NPC，再自动填一个NPC”“先去掉资产门禁让挂起任务共存”代替上述闭环。测试夹具通过只证明协议逻辑，原生行为/界面/性能必须分开记录未验证项。

2026-10-23：0.23.0已按本设计接制作/搬运公共目录、逐NPC优先级和独立Job保存，见[本轮证据](../../reviews/2026-10-23/shared-public-work.md)。仅上述工种开发侧通过，新路径实机未验；不表示全工种、生活行为树或完整人员界面已实现。

## 16. 与唯一架构及需求界面的对接核查

2026-10-23补充：设计层面可对接，但不是已完成兼容验证。HFSM限定上下文、效用层选择、TaskController控制身体、BT编排动作的分工不变。TaskDirectory提供候选，DispatchCoordinator只裁决分配，两者不得成为第二套效用决策器或身体控制器。

唯一架构中需要明确修订的两处：P3“批量传授”与新需求禁止要求手动传授冲突，改为实体书架借阅与原版ISReadABook研习机制；最小工作矩阵配置须在自主领单闭环时提供，完整P3人员界面可后续完善。这些修订已随用户同意的设计收口纳入唯一架构v1.1，尚未落实为运行行为。

后续UI必须按需求11、11.1～11.4修改，不能只替换后端而保留指定NPC下单/独立物流页。下表限定页面责任和数据边界，不强制固定像素布局或最终页签数量。

| 需求位置/界面 | 提交命令 | 订阅的只读投影及约束 |
|---|---|---|
| 11.1 仓储快捷下单（物料驱动） | 仓储网格点击物品/可制作项弹出轻量弹窗，提交创建据点Order（不传执行者npcId） | 物料库存、配方与平台有效性、单次下单量/最低存量；零库存可制作项虚影 |
| 11.1 原版制作快捷下单（配方驱动） | 原版制作菜单点击“委托制作”弹出轻量弹窗，传参创建据点Order | 原版配方参数、工作台就绪度；不改变原版即时制作，不另建独立配方黄页 |

| 11.2 仓储增强 | 收藏设置、点击物品呼出快捷下单/最低存量设置弹窗 | 紧凑图标网格及角标数量、收藏置顶、零库存可制作项；液体类型/容量用独立读取字段，不能混入实例件数 |
| 11.2 最低存量快捷设置 | 修改同一规则的阈值与单次发派量 | 库存口径、规则版本、活动补货Order；原版页面快捷弹窗和据点面板共用命令，不各存一份规则 |
| 11.3 人员详情/全员矩阵 | 修改同一份逐NPC工作策略，支持列批量更新 | 人员状态、健康/已确诊告警、技能、疲劳/Buff、床位及宏观上下文；单人设置与全员矩阵互相同步 |
| 11.4 防御/岗位策略 | 警报等级、世界点选岗位/路线、常驻及装备策略 | 热度、岗位占用/缺岗、疲劳与交接、军械库存及装备就绪度；策略不等于向具体NPC直接派守卫动作 |

后端按稳定Order/Job/NPC/策略ID提供投影与版本化命令。修改工作优先级只使有关候选/人员置脏，并在安全决策点生效；不能由UI事件直接清动作队列。技能按选择/升级事件更新，隐藏页面释放订阅；业务继续运行。随从装备/武器缩略栏属于战术UI，不塞进据点人员页。

进度契约：总体数量进度与当前动作进度分开；移动、寻路、备料只显示离散阶段，不预测ETA。只在原生制作动作实际运行且时间字段/单位已验证时提供“当前制作动作”剩余时间，不能把它标成整条BOM完成倒计时。暂停、停止、动作切换或来源失效即撤下旧倒计时；“零开销”不得当实测结论。原生读数由执行适配器构造只读动作状态，视图不绕过服务直接持有动作userdata。

下发前的玩家图纸/必要平台校验与领取时NPC技能/工种/状态校验必须分开，避免界面以“当前没有熟练工”阻止形成合法待领Order。无法支持的动作或未知条件明确提示，不假装满足。无平台配方不增加虚构家具前置。

[据点UI实施设计](2026-10-23-settlement-ui-design.md)已细化四页布局、共用快捷编辑器、填参确认、取消收尾及收藏首段多行规则，作为本节的从属实施说明。0.23.0已接共用轻量编辑器，补货量固定以成品件数保存、显示配方次数换算；固定批次不因中途库存上升提前收束。其他页面与最终视觉仍未完成。后续视觉逐项映射本表，与原版暗色风格、缩放及键盘/手柄契约一起验收。

## 17. 评审吸收与补充验收（2026-10-23）

用户已授权吸收评审。第8、9节已明确自理/恢复不走公共认领、携货普通工作准入及哨位双角色交班，另固定：

- PERSONAL和RESPONSIBILITY是统一仲裁的私有候选，不要求发布到公共TaskDirectory。私有恢复引用原Job，不造新公共Offer；责任转交才走明确交接协议。
- 未加载/观察失效空间目标进入非活跃索引，不出现在日常可领取集合；保留稳定目标引用而非引擎对象。加载事件或有界分散复验重新激活，不假定所有目标都有可靠加载通知；缓存有界，派生记录可淘汰重建但持久责任不能删除。
- 每NPC一次提交最多3个有序公共候选；认领冲突后在本轮剩余预算内尝试下一候选，耗尽则保留游标及失败版本，下轮轮转继续。每次仍重验候选，防止Top-K成为过期授权；不承诺找出全局最优匹配。
- 配方与技能学习全面回归原版实体书籍与ISReadABook引擎契约：彻底废除“制作开工前插播2秒研读动画”。书籍与配方杂志存放在据点书架/图书箱，作为耐用物理资产（读完不消失，全据点学徒可轮流借阅传阅）。NPC在闲暇时段或受工单缺配方驱动时借书研读，调用原版ISReadABook；配方杂志读完整本（alreadyReadPages>=numberOfPages）原版引擎才写入character:getKnownRecipes()，中途打断进度原生保留但不提前解锁；技能书按已读页数线性增加经验获取倍率；天然联动快速阅读/阅读障碍/文盲等原版特质。公共工单直接按KnownRecipes与技能等级核验资格，缺配方工单显示挂起待研习，不产生时序悬挂。
- 固定补货量与提前收束仍由最低存量修订统一定义：既不全面禁止提前收束，也不默认高价值物品采用另一套策略。0.22.4宿主记录不是充分实机验证。
- 取消独立配方浏览下单大界面（判定为功能与工程冗余）：避免与PZ原版制作菜单（B键）重叠及维持庞大自定义配方UI的开销。下单入口收敛为两类轻量弹窗：①仓储网格点击物品/可制作项弹出快捷下单/最低存量弹窗（物料驱动，Tom's Simple Storage/AE2风格）；②原版制作菜单注入“委托据点制作”按钮弹出快捷下单弹窗（配方驱动，JEI风格）。据点面板中的任务页签纯粹聚焦为【工单监控面板】（全据点活工单队列、认领人、制作倒计时、BOM流转树与暂停/取消），不承担全局配方黄页职责。
- P1真实接线、原生停止/效果和正常保存恢复验收先于自主领单上线。清洁/守卫契约夹具只检查抽象，不提前搭建真实工种，也不当作P1通过。

增加定向用例：公共队列耗尽时危急自理仍进入停止流程；持料自理后拒绝无关普通单且不可达时不冻结安全撤离；哨位预约冲突/旧版本到岗；未加载候选不耗日常选择预算；三NPC竞争后有界回退；研读完成前后保存/中断。所有原生效果另做实机验收。
