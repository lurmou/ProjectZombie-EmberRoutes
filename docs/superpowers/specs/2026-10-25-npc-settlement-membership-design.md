### 1.1 需求核对与阶段差额

| 快照条款 | 本设计对齐方式与限制 |
|---|---|
| §3.1 同阵营据点允许重叠/合并 | 显式settlementId消除重叠区域的成员歧义；不以几何匹配数量改籍，不实现据点合并流程 |
| §3.5 Account-Bound Succession | 归属绑定稳定阵营/NPC身份，不绑定队长角色或运行时玩家索引；队长死亡不丢成员。单人新角色继承权限和跟随目标重新绑定须分开处理，见§3.1 |

## 2. 三个独立维度

| 维度 | 权威事实 | 边界 |
|---|---|---|
| 据点归属 | 稳定npcId关联settlementId，可为空 | 跟随、越界、存档重进不改变归属 |
| 宏观命令 | SETTLEMENT（驻扎生活）、FOLLOW（跟随）、WAIT（原地等待）、RETURN（返回据点） | 决定允许的候选集合，不直接执行动作 |
| 当前执行 | TaskRuntime与现有Job/Session | UI读取投影，不另存一份可写“当前活动” |

归属和宏观命令在NPC业务记录中各有唯一来源；Companion运动模式继续作为底层执行状态，不允许业务反向用HOLD猜测宏观命令。命令不改变职业、健康或技能。

首版存储固定挂在`ContainerRegistry.data().npcMembership`，随既有`EmberRoutes/Work/v1`世界根保存；子store独立`format=1`、`byNpc[npcId]`。每行保存factionId、可选settlementId、context、revision、可选pendingCommand（requestId、目标归属、目标上下文、申请时revision）及FOLLOW目标的标量身份引用。阵营身份与据点身份分开：解除据点归属不等于退出阵营。

唯一业务写入者为MembershipService的命令交接协议；UI、候选Provider、Companion回调不能直接改表。创建初始化、加载反序列化和最终清理通过该服务受限入口；运行事件提交带版本的内部意图，仍由同一协议裁决。其读接口提供受控只读内部视图/对外副本。复用Registry.data不等于授予所有消费者写权限；不另建第二份持久化成员索引。

pending保存可恢复意图，不代表交接成功。无归属使用缺省字段；派生错误原因不作为新的身份状态保存。子store未知format拒绝恢复，不清空或重建原数据。

现有hasHome/坐标若为载体检查点恢复所需可保留在底层，仅用于恢复锚点/Debug诊断，不能据此推导成员资格或普通生活目标。普通玩家入口移除“设家/sethome”，统一提供“设置据点返回点”；“回家/home”统一解释为返回所属据点。HOME_SET不进入新宏观状态；旧命令仅可作为显式Debug诊断入口，不与产品命令并列。

### 2.1 驻扎与闲暇共享接口（首版固定）

所有接口定义在client/EmberRoutesProbe/MembershipService.lua。调用方不写store，不通过Companion.exportState推断资格。生产运行不保留HOLD/几何推导身份的隐式回退；旧测试夹具显式建立新成员记录或注入契约替身。

| 函数 | 返回与责任 |
|---|---|
| view(npcId) | detached成员DTO：npcId、factionId、settlementId、context、revision、pending、reason、obligations；不存在返回nil与NO_MEMBERSHIP |
| check(npcId,purpose,observation,expectedRevision) | 资格DTO：allowed、reason、revision、settlementId、context、entryRevision；purpose为WORK/LEISURE/STUDY/SELF_CARE/RECOVERY/RETURN。observation为本轮NPC的x/y/z及可选scopeId；禁止以玩家位置代替。expectedRevision可省，携带旧候选时必填 |
| entry(npcId,scopeId) | 内部只读据点条目、原因、成员revision；核对阵营/归属，不调用要求玩家在圈内的Ledger.view。只读条目不得交给UI或原地修改 |
| request(actor,npcId,command) | 命令DTO包含requestId、expectedRevision、kind和可选settlementId；kind为SETTLE/FOLLOW/WAIT/RETURN/TRANSFER/UNASSIGN。返回回执state/requestId/revision/reason及义务明细，不将PENDING当完成 |
| cancel(actor,npcId,requestId,expectedRevision) | 取消对应pending，原context/归属不变；停止中不直接重启旧身体；取消本身产生新revision并使旧候选失效 |
| setReturnPoint(actor,settlementId,point,expectedEntryRevision) | 校验并提交据点返回点；只改变据点版本，不能直接改NPC命令或启动移动 |

check是资格层，不替代身体、健康、原件、目标占用及动作前置条件。SELF_CARE/RECOVERY不因WAIT/FOLLOW、无归属、pending或圈外一概拒绝，但返回allow仅表示宏观门禁允许；现有需求紧迫性、个人/共享物资范围及身体交接仍由原流程核验。RETURN要求有效归属和可返回上下文，目标加载/路径成本由返回执行适配器检查。

WORK/LEISURE/STUDY要求SETTLEMENT、无pending、有效且匹配的归属、NPC实际在该据点范围；判定顺序固定为旧revision失效→无记录/归属→上下文→pending→据点/阵营→范围。理由包括STALE_MEMBERSHIP、NO_MEMBERSHIP、CONTEXT_WAIT、CONTEXT_FOLLOW、CONTEXT_RETURN、COMMAND_PENDING、TARGET_LOST、ACCESS_DENIED、OUTSIDE_SETTLEMENT。身体、资源或预算失败沿用各消费者原因，不覆盖为身份错误。

revision在接受/替换/撤销命令、正式提交context/归属及使资格变化的生命周期事件时递增；未生效pending阶段仍展示旧context/归属，但立即禁止新普通候选。纯位置变化不递增成员revision：check每次用当前观察重验；据点改界/返回点变更以entryRevision单独重验。恢复自理只持有先前意图，不能覆盖其后新revision。

闲暇/研习offer、社交advertise和待启动候选记录membershipRevision与settlementId；接受邀请、启动活动和继续执行资格检查时重验，不以缓存TTL代替。命令接受后定向清offer、withdraw旧邀请并请求既有任务安全停止；已生效声明必须等停止及原件核对后释放，不随失效缓存删除。驻扎侧只接此资格/失效边界，闲暇侧随后负责发现、选择、冷却、姿态和社交表现重构。

## 3. 命令与玩家语义

| 命令 | 归属变化 | 生效后行为 |
|---|---|---|
| 驻扎于X | 设置为X | 在X内进入生活；在外先返回，再开始生活 |
| 跟随我 | 保留 | 停止领取据点普通工作，跟随；允许必要个人自理 |
| 原地等待 | 保留 | 不领普通工作、闲暇与主动研习；允许危险撤离、紧急自理及不能遗弃的责任处理 |
| 返回据点 | 保留，要求有效归属 | 返回成功后进入SETTLEMENT；目标无效/不可达则显示原因并等待，不假报到达 |
| 调驻到Y | 安全交接后改为Y | 返回Y并进入生活，不按当前位置自动选Y |
| 解除归属 | 安全交接后清空 | 转WAIT；不是解雇，不删除NPC或物品 |

首版没有自动随玩家迁基地或进入新矩形自动改籍。玩家可以从人员列表批量驻扎/调驻；逐NPC给出成功、处理中或失败结果，不承诺批量全有或全无。

无归属或目标据点失效时，“驻扎”“返回”必须显式选有效目标或被拒绝。命令由当前本地世界执行者核验受管载体、玩家权限、目标阵营及版本；为未来服务端意图保留同一命令边界，不宣称实现联机。

### 3.1 上下文转换与事件权限

下表穷举首版可修改context的来源；“任意”包含四种已有context。所有转换都由MembershipService校验版本并经§6协议提交。失败/预算不足只更新派生原因，不伪造转换成功。

| 来源 | 原context | 新context | 归属/执行结果 |
|---|---|---|---|
| 新NPC登记 | 无记录 | WAIT | 同阵营、无据点，等待显式驻扎/跟随；不读取旧HOLD |
| 玩家驻扎X/调驻Y | 任意 | SETTLEMENT | 旧责任结清后提交目标归属；圈外由返回候选推进 |
| 玩家跟随 | 任意 | FOLLOW | 保留归属，记录被授权目标身份；不继承旧角色对象引用 |
| 玩家原地等待 | 任意 | WAIT | 保留归属；等待位置仅为命令目标，危险撤离不改籍 |
| 玩家返回据点 | 任意 | RETURN | 要求有效归属，提出返回候选；已经在有效范围且返回执行已确认安全结束可立即完成 |
| 玩家解除归属 | 任意 | WAIT | 旧责任结清后清空settlementId，保留factionId |
| 返回任务成功事件 | RETURN | SETTLEMENT | 核验任务/Session代次、当前位置在所属范围及身体交接，不能仅凭移动回调 |
| 圈外返回候选推进/完成 | SETTLEMENT | SETTLEMENT | 只改当前执行任务，不是宏观context转换 |
| 跟随目标死亡/永久移除/失去授权 | FOLLOW | RETURN或WAIT | 安全停止后，有有效所属据点则RETURN，否则WAIT；无返回点/不可达可保留RETURN并显示原因。归属不丢，不自动追逐新角色 |
| 玩家换角色 | FOLLOW | RETURN或WAIT | 与目标失效同一规则；若死亡事件未送达，目标身份复验必须拦截旧会话 |
| 据点删除/阵营权限失效 | 任意 | 保留 | 派生TARGET_LOST/ACCESS_DENIED，挂起普通据点行为；跟随及安全自救按各自权限运行，不由失效事件自动换籍 |
| 加载当前格式存档 | 已保存context | 保留或上述目标失效转换 | 恢复责任后重验；禁止将底层HOLD当WAIT或驻扎的恢复依据 |
| NPC死亡/永久移除 | 任意 | 不再生成新context | 停派并处理§7终止清理；临时未加载不按死亡处理 |

暂时找不到跟随目标与确认死亡/换角色分开：目标未加载保持FOLLOW并有界等待，不因为一次缺失样本改RETURN。角色替换使用角色生命周期身份/代次验证，不能以玩家槽位相同判断是同一角色；FOLLOW目标只保存标量身份引用，原生actor/handle不入档。实施时如现有身份桥接不足，必须补角色生命周期识别与定向验证，不能用名字/索引猜测。

单人新角色获得同一世界阵营权限，既有factionId、成员和据点不重建；在其身份授权建立前暂停玩家管理命令，NPC仍由本地世界执行者负责安全停止与已有责任。新角色继承权限不自动重发FOLLOW；明确跟随命令才建立新目标。该身份接线须列入实施计划和游戏验收，不声称现有Ledger.authorized已实现账户继承。

## 4. 资格、位置与资源

业务统一读取Membership/Context服务，不在PublicWork、Leisure、Study、人员页各自维护成员判断。服务返回可诊断的结果与原因，而非仅一个bool。

现有Ledger.view还要求玩家actor站在据点内，不能直接作为居民自主生活的常驻权限查询。新增内部按世界执行者、factionId、npcId、settlementId及版本核验的只读访问边界，避免玩家离开基地或死亡让全体居民失去资格；玩家修改据点/容器的原有位置与权限约束不因此放宽。资源实际取用仍重验NPC位置及对象。

普通据点工作的新候选要求：有效归属且匹配工单据点、宏观上下文为SETTLEMENT、当前处于该据点范围、原有身体/健康/任务/资源前置条件成立。在外由RETURN候选经同一仲裁器推进；不得从另一基地领取本地普通工单。

闲暇、非紧急研习、床和共享设施发现以归属据点为范围；活动启动及目标执行仍校验位置、加载、可达性、占用、权限和原对象。几何不再产生或撤销成员身份，但仍参与实际活动安全判断。紧急自理沿用现有规则，不因无归属或圈外失去自救资格。

越界不清归属、不换籍；无任务责任且处于SETTLEMENT时提出返回候选。已进行的工作允许其经验证的据点外路径/步骤，不用瞬时越界打断。携货、借书、设施监管优先按现有责任恢复，不能被新资格门禁永久卡住。

共享社交要求同一有效归属并在活动地点实际到达；有居民身份不等于已到场。预算不足、未加载和不可达分别显示，未知不当不存在。

## 5. 返回目标与失效

据点登记仍然必要：提供稳定ID、边界、权限和资源范围。每据点持久化一个可由玩家设置的返回点（x/y/z、版本），设置时校验点在范围内且当前加载、可站立；不承诺未来永远可达。

已有据点没有返回点时，不使用矩形中心或旧home盲走；显示“未设置返回点”，允许玩家在据点内设置。NPC已在范围内可直接进入生活，无须为此强制返回点存在。被阻挡/未加载的目标有界退避，事件或低频复验唤醒，不逐tick重寻路、不默认传送。

据点改名不影响归属；改界只更新位置与目标有效性，不改成员。删除据点或丢失权限时保留原settlementId以便诊断，禁止新普通认领，显示“所属据点失效”并将正常生活挂起；原件义务进入恢复路径。权限恢复时重新核验，不自动重放旧动作。不能复用已删除据点ID给新据点继承成员。

这里是v3.3 §3.7完整解散流程的失效保护接缝，尚不实现转游荡者或标签注销；后续解散服务必须经本命令协议收编/解除据点归属，不能删除账本后假定NPC生命周期已处理完毕。旧容器标签注销不能抹除携货/借书的原对象与归还事实；无法归还时显示待处置责任，不自动清账。

## 6. 命令交接与保存

命令顺序：核验并记录pending → 阻止旧普通候选继续派发 → 经TaskRuntime请求停止 → 核对身体与效果 → 保存旧据点责任及恢复点 → 提交新归属/宏观命令及revision → 允许新候选。处理中展示目标，正式归属仍读旧值；失败保留可解释结果，不伪装命令完成。

调驻/解除归属首版仅在旧责任已结清后提交；未归还材料、借书、未知效果或未完成设施交接时，返回“等待旧责任处理”。投影从既有Job/声明/恢复记录读取明细（如未还书×1、携货中、效果待核对、设施待交接），可观察时带物品名及目标；未知不编数量或位置，不另建义务账本。允许继续原责任恢复；允许撤销pending。跟随/等待仍遵守既有停止及危险例外，不以归属命令绕开恢复协议。此限制是首版成本控制，不实现跨基地责任自动转移。

重复requestId且参数相同返回原结果；参数不同拒绝。请求携带expectedRevision，过期拒绝；待处理命令每NPC最多一条，新命令明确替换/撤销旧pending，不能排成无界队列。当前与近期已结命令回执有界保留；过期请求拒绝自动重放。

正常保存通过现有统一屏障捕获成员事实、宏观意图、pending与任务责任；读档先恢复责任，再重验归属/目标/命令，最后经仲裁申请身体。不得直接按保存坐标瞬移或无条件启动动作；不承诺跨文件崩溃原子性。

## 7. 新档边界与成员清理
