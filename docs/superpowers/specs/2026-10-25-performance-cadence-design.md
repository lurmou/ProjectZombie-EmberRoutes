# 全模组分级降频与性能验收方案

> 2026-10-25｜状态：用户已要求开始实施；0.28.4完成首轮降频，性能目标未实机验证。上位契约：[唯一NPC架构](2026-10-22-npc-behavior-architecture-design.md)第6节；不新建身体控制器或资产权威。

## 目标与测量口径

用户报告Lua监控器约200ms，要求降至50ms以下，允许优化架构，并明确以降低各方法检测频率为主方向。该数字尚无本轮场景采样，不能写成已复现单次200ms卡顿。

本机ZBLuaPerfMon默认osdWindowMS=3000；PerfRenderer.getTopCalls显示WindowStats.getTotalSumMs，未除窗口秒数。因此默认面板200ms是近3秒累计，约66.7ms/秒；面板50ms目标约16.7ms/秒。实际窗口可配置，必须记录面板标题/设置。显示按调用条目归因，不能不核查重叠就把所有行相加当模组独占总成本。

验收同时保留：监控器原窗口目标、模组独立计时ms/秒、单次P95/P99/最大值、发现/领单等待、有效产出和可见帧停顿。固定负载后才宣称达标；不靠隐藏监控器、改变窗口或丢弃慢调用过关。

## 已核查事实和证据限制

- 工作区0.28.0包含大量未提交及未跟踪的既有修改；本轮不重置、不整库提交。
- PublicWork已有200ms发现、有限轮转、PrecheckQueue切片及2ms软预算；SelfCare已有200ms轮转；TaskRuntime业务tick已有18ms墙钟门限。不能把这些重复算为新增优化。
- MembershipRuntime.tick在200ms门限前读Registry.data；SelfCare每tick到达设施推进，且取RuntimeMetrics的require处于热路径；TaskRetirement每200ms进入公共单/Job结清扫描。它们是静态优化候选，尚无本轮耗时排名。
- EvenPaused每三次回调运行一次内部handlers，不会减少引擎调用dispatch的次数。旧报告中“因此入口调用数降至三分之一/监控值必降”的推论不成立。
- ZBLuaPerfMon的Patch_LuaCaller先测调用耗时，再recordTime；不能从读数差额推出每次有0.3～0.4ms固定记账成本。嵌套计时、UI与原生动作入口、采样窗口、倍速、事件风暴均需分别检查。
- 当前console.txt尾部无新RUNTIME_PERF结果；旧报告的低于50ms不能代表当前场景。旧报告的推测不当本轮定案证据。
- 在线唯一需求本轮已成功重新读取，标题v3.3；单人优先按用户决定覆盖旧MP优先条款。
- PZwiki [Mod optimization](https://pzwiki.net/wiki/Mod_optimization)正文及raw入口本轮受限（403/抓取失败），尚未核对正文，不把下述建议冒充其逐项原文。

## 三种路线

1. 统一扩大所有间隔：改动少，但危险、取消、交付确认延迟，且多服务同相位可能形成集中尖峰，不推荐。
2. **分级降频+变化唤醒+错峰切片（推荐）**：保留现有唯一Runtime/Claims，按业务容忍度调度；空闲少做、发生变化及时做，控制总预算和最大等待。
3. 全面Java迁移或宏观虚拟化：成本与回归范围大，Java同主线程并不免成本；实体/宏观交接另需原件与唯一结算原型，不作为第一阶段手段。

## 推荐设计

在Boot已有统一入口内增加小型瞬态到期调度；复用已有轮转/预算设施，不创建每工种调度器或第二套任务运行器。周期、下次到期、dirty版本、游标均为运行期数据，世界切换清空。deadline用now+interval，卡顿后不追补积压心跳。每轮取一次时钟下传，热路径require提升至模块缓存（避免循环加载，必要时惰性缓存）。

下表为待测初值，不是已证实最优参数；“空闲”必须由显式状态判断，不能跳过未知效果或尚未停止的会话。

| 路径 | 推荐节奏 | 约束 |
|---|---|---|
| 身体停止/保存屏障/状态回调 | 保持及时推进，命令触发即时唤醒 | 禁止让资产责任跨执行者重叠；资产提交前真实校验不缓存 |
| 活跃业务状态观察 | 50～100ms；具体动作可保留18ms | 逐适配器评估完成/超时/效果契约；原生TimedAction、移动/动画由引擎正常推进 |
| 普通公共派工 | 活跃500ms，长期无工作1000ms | 新工单、资格/库存版本变化提前唤醒；预检仍切片，不把500ms等待累积到每人 |
| 需求与成员资格发现 | 普通500～1000ms，静态归属2s | 危急需求/命令/死亡快通道；健康轮询的最坏响应独立测量 |
| 闲暇/研习候选 | 1～3s，失败2/4/8秒有界退避 | 条件变化唤醒；已持货/借书归还及取消不进入新候选冷却 |
| 设施/库存观察 | dirty时50～100ms切片；干净时停止扫描，2～5s到期复核 | 事件只标脏、去重，不在回调内全扫；TTL覆盖无事件物品变化；未知不当空 |
| 工单结清清理 | 有待清队列时250ms，兜底2～5s | 有界游标，不每次全量排序；仅已满足原件/效果/身体/恢复结清条件可删 |
| UI投影 | 数据版本改变时重建，可见页250～500ms兜底 | 关闭释放观察请求；render只画缓存，可交互响应不节流 |

周期错开相位，按稳定NPC ID/既有轮转均摊，禁止所有服务在整秒同时扫。公共规划共享预算：初值每游戏tick最多1～2ms软预算，并保留操作数/容器/寻路次数上限；原生单次调用可能超过软预算，必须另计最长切片，必要时拆分/批读。负载过大时优先延后普通发现/闲暇扫描，不能延后保存与停止责任；记录最长队列等待防止饥饿。

缓存按world+业务revision+观察有效期失效。调度快照只用于候选读取，认领/消费/交付重新核验权限、原件、规则、容量和执行权。对未知/否定状态采用专门退避协议，不沿用曾造成PERSONAL_AUTHORITY_LOST的安全判断缓存。

仅在量出瓶颈后把库存/设施批读取放Java；禁止在后台线程访问活动世界对象，禁止为降低Lua监控值而转移同等主线程成本。

## 执行切片与验收

1. 补齐测量边界：Boot、EvenPaused、模组事件、可见UI、原生适配回调分开计量；嵌套桶不相加。记录实际监控窗口/JAR和采样器开关，测空计时基线。采样直方图改有界存储，避免高频采样分配污染结果。
2. 先优化空闲/发现路径：Membership早期门限、SelfCare设施调度、闲暇/研习退避、结清dirty队列、热路径模块缓存。保留原语义金样本，测版本变化唤醒与未变化不扫描。
3. 对活跃业务按动作声明周期，补停止、完成、保存恢复、携货交付和预算饥饿回归；再按证据处理全量拷贝/排序/原生跨桥接。
4. Lua修改跑项目preflight及luals；Java修改构建并跑相关测试。只执行与风险有关的宿主回归，不把替身耗时当游戏性能。
5. 同存档预热后覆盖空闲、搬运、制作、生活切换、UI开/关，1/5/10/20NPC分档并记录箱子/物品数。每场景至少3轮60秒，监控开/关对照；1×/倍速分别记录，不能仅靠空闲结果验收。
6. 若实际窗口为3s，以监控同口径50ms/3s为目标，独立预算约16.7ms/s；报告超限窗口比例、P95/P99/max和最大派工/危急响应等待，不承诺所有规模硬上限。未达标继续依新热点处理，不提前宣布完成。

## 本轮交付边界

初稿完成只读核查；用户随后要求开始实施，0.28.4首轮实现见[证据](../../reviews/2026-10-25/performance-cadence.md)。尚未运行游戏性能验收，不宣称完整候选清单全部落地或50ms达标。任何超出现有第6节性能策略、涉及实体/宏观切换的架构变更须单独提出契约和证据。
