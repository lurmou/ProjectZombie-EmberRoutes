# 委托制作首条闭环设计草案

> 2026-10-21｜按用户明确纠正更新｜[分类仓储修正](../../reviews/2026-10-21/probe-0.17.1-classified-crafting.md)｜[技术核查与证据](../../reviews/2026-10-21/commissioned-crafting-review.md)

## 范围与交付顺序

本设计服务于单人据点的首条委托制作链路：玩家指定配方/数量/工人，系统依照配方选择制作位置，并复用现有分类规则寻找材料、交付及工具归还箱，NPC真实取料、逐件制作、原件入库。一个父生产工单管理全过程，进度区分已制作、已入库及阻塞原因。原型单NPC验收，正式结构按稳定npcId/orderId隔离，允许多NPC共用同一资源仲裁。

先验证原版动作兼容，再实施首条产品闭环。第一个原型只接白名单木叉配方与原版允许的通用制作表面，固定SmallHandle耗材分支，单件串行；单次目标量为正整数，按有界批次规划，不承诺一次性扫描/锁定任意规模。完整递归BOM、定额补库、工具前置生产、跨NPC运输交接、未加载区域生产和MP不进入该原型。

未来完整BOM仍须满足在线需求：耗材随数量增长、催化工具恒1、依赖环路阻断、展开最多4层、缺工具前置单及检查点恢复。首个白名单样本验证其资产与执行基础，不标记完整BOM验收完成。

## 方案比较

| 方案 | 好处 | 代价与选择 |
| --- | --- | --- |
| 同一NPC取料→制作→交付，父单持续持有资源 | 无工人间交接；可复用当前真实搬运；先集中验证原版动作 | 工人也花时间运输。推荐首条闭环采用。 |
| 父生产单派独立物流子单，其他NPC补给 | 后续可分工并行 | 当前任务没有跨owner授权/移交，也不支持直接以另一NPC背包作为普通搬运终点；需要缓冲位置、交接与恢复协议。后续扩展。 |

不为缩短开发另写类型扣料/生成产物流程。物理效果走原版动作和真实原件搬运；资产归属、计划和恢复由本模组定义。

## 下单与执行门槛

下单权威核对玩家在有权限的当前据点、配方要求的制作条件仍存在且属于据点（木叉为原版认可的通用表面，专用配方才要求对应工作台）、玩家严格知识判定通过。选择工人后逐项核对NPC真实技能和独立知识，未达技能不允许用书本在手收益绕过；知识缺失且玩家已知、NPC技能达标时，玩家可显式传授单一配方，调用原版学习后重新核验。

工作台扫描只遍历据点已加载实体，以稳定台ID映射位置和实体引用；引用失效需重新解析并核对身份，不能用同格新家具悄悄替代。物理台不是“管理终端”，面板无需另造家具。未加载/被拆除/被占用时显示具体等待或暂停原因。

选择原料只使用同据点、已登记、分类匹配且有权限的共享STORAGE箱，按原件ID认领；产物与工具按现有过滤索引、精确匹配优先/距离/稳定ID规则选择分类箱，不新增平行的生产箱配置。玩家背包不作为来源或默认交付目标。阶段切换和实际效果前再次检查权限、角色、工作台、原件归属、有效代次与容量。只读仓储数量只能找候选，不能作为扣料依据。工人背包以外的材料必须先搬到工人。

## 资产认领与工人仲裁

1. 生产orderId是稳定owner，npcId是可分派执行者，operationId标识每次单件制作，generation隔离过期动作。取料/制作/交付共享owner，自动分拣通过同一权威读取认领并跳过。
2. 复用并扩展现有LaborClaims，建立统一持有者入口；不能另起仅生产看得见的claim表。现有不可变资源集合不够用，首个单件闭环先原子追加实际产物ID，旧输入/工具认领持续保留至交付及归还完成，失败不部分追加。多件有界生产后续再扩展集合替换，不把旧输入释放与新产物认领之间留出空窗。
3. 生产记录独立版本化。加载时先校验生产/搬运全部owner与npc占用冲突，再一次发布公共认领快照；冲突双方停止，不能按加载顺序把同一原件分给两单。
4. Work统一负责每NPC的busy/暂停/人工接管/删除/保存入口，并按任务种类派发；每NPC最多一个执行者。物流、制作和随从命令必须遵守这个仲裁，暂停后持货归属不随busy=false消失。
5. 取料完成不释放生产原料。取消有携货时先归还/移交已知原件；若位置不明则保留恢复记录与认领，暂停自动化，不能清表后宣称取消成功。单件首版在产物交付和工具分类归还全部闭合后统一释放；期间持续保护原件。

认领扩展须保留现有搬运工单语义和代次隔离。工具数量恒1按父单计算，不按制作目标倍增；可用性每件复验，磨损/变钝/损坏时暂停，后续完整BOM再接缺工具前置单。

## 原版动作适配

配方是当前安装脚本的`Base.CarveWoodenFork`，标记`AnySurfaceCraft`；按原版`isGenericCraftingSurface`与NPC的`canUseAsGenericCraftingSurface`判定普通有效表面，移除`Base.Chopping_Block`和CraftBench组件硬限制。手持/通用表面/专用工作台是不同条件，不统一强制专用台。注册时从实际脚本对象核对完整标识、标签、技能和IO，发生版本差异拒绝适配；不把推导ID当成已经运行验证。

每件新建ISHandcraftAction及其HandcraftLogic，沿原版队列执行。manualInputs按实际IO索引明确填入选中SmallHandle和同一把sharpknife原件，containers限制为工人合法库存；拒绝force和自动替料。start填充后、最终performRecipe前分别核对实际input集合与归属，不凭构造时的计划推定执行时仍正确。

工作台持有业务独占租约，同时校验原版usingPlayer。只在空闲且权威许可时设置NPC占用；释放前确认仍是本NPC。玩家使用、实体卸载或身份变化则暂停，不能清别人的占用。当前ProbeNpc为IsoPlayer子类可满足静态签名，但原生制作历史、动画及玩家UI冲突必须先实机验证，不注册真实玩家槽位。

使用每动作实例适配，不全局替换原版ISHandcraftAction。调用原版performRecipe保留原生消耗、XP、磨损及产物处理。记录实际输入前态，收集该logic的真实输出原件，检查预期消耗、刀具及输出位置。不能凭onComplete或nil返回判成功；stop同时调用完成回调，按终止原因与单件核对结果处理，重复/过期回调不再结算。

原版输出可能落地。预检负重与交付容量；若实际输出未在预期背包，按已取得ID核对已知局部位置并暂停，不按类型重造、不再次消耗材料。输出收集与认领在同一提交路径内完成，通知/下一任务在之后发布；本模组规划器不得在COMMITTING期间重入领单。其他模组钩子仍可能改变资产，异常进入待核对状态，不声称对任意钩子完全隔离。

## 状态、进度与恢复

| 状态 | 可执行效果与退出条件 |
| --- | --- |
| WAITING_INPUTS | 无消耗；缺料/工具/台/权限/技能等给出原因；等待相关事件或显式重试。 |
| RESERVED / COLLECTING | 父单持有原件，沿现有搬运原语取料；中断保留位置与归属。 |
| READY | 单件原件在NPC、工具/台/门槛/容量均通过最终检查。 |
| COMMITTING | 先记录operationId、输入ID/状态和意图，再允许一次原版效果。禁止自动再次调用。 |
| OUTPUT_CONFIRMED | 实际输入消耗、保留工具和新输出ID核对通过，已制作数加1；输出认领进入父单。 |
| RETURNING | 将输出原件交付；已入库数仅在转移核对后增加。仍持有其余货物和工具。 |
| DONE | 目标产物全部交付、工具归还、无未决携货，才释放剩余认领并结束。 |
| PAUSED / RECONCILE_REQUIRED | 普通阻塞可复验后继续；COMMITTING异常或无法证明结果必须待核对，禁止按旧计数自动重做。 |

多件按单件循环READY→COMMITTING→OUTPUT_CONFIRMED；根据真实负重分批RETURNING，再继续剩余目标。页面同时显示“制作x/N、入库y/N”和当前阶段/原因，保留父单ID，不把物流批次0/4显示成生产目标缩水。已入库≤已制作≤目标；出现不一致先停工。

正常保存前统一停止新派发、取消尚未提交动作、核对已有效果，再保存工单和NPC原件检查点。恢复须验证世界/owner/npc/工作台/输入与产物ID，未解决携货继续保护；重试前失效旧generation。仅在能证实效果尚未发生时重试同件。

强制退出可能发生于原版consume与create之间，也可能发生于多个文件落盘之间。ModData脏标记不证明持久事务；本方案先采取无法判定则停工的边界。完整崩溃无损/自动幂等仍是未解决的验收项，不能把保守阻断称作已满足在线恢复硬契约。

## 职责与性能边界

- 配方适配注册表：白名单、原生IO/门槛/结果核对，不处理UI或全局调度。
- 生产记录：版本化父单/单件检查点/进度与原件位置；不直接改变世界资产。
- 公共认领与Work仲裁：全任务owner、代次、容量、NPC执行权；在现有内核上最小扩展。
- 制作执行器：阶段推进、调用原版动作、效果核对及搬运原语复用；不重写物流策略。
- 后续制作页：接既有据点窗口与PageLifecycle，以脱离持久表的DTO读取、命令写入、事件置脏/局部setState；隐藏释放订阅，后台工单继续。原型阶段不先堆完整BOM界面。

工作台索引只在相关实体/区域变化或显式刷新时有界更新，配方元信息缓存按版本失效。规划用登记来源、库存候选与变更事件，最终效果仍逐原件复验。全局共享调度预算，不每帧全箱/全配方扫描，不为每个工单新增独立tick；没有性能数据前不承诺规模与吞吐，也不先把整个系统迁到Java。

## 下一步原型验收

原型仅放原版Debug诊断子菜单，使用现有NPC和玩家已准备的合法样本，不自动治疗、升级技能、复制配方书或造终端。先核对native IO、知识/实际技能拒绝与传授，再在有效通用表面执行1件/连续少量木叉，记录输入/工具/输出ID、磨损与位置。

一次集中实机覆盖：正常制作及原件交付；取消/占用变化不误计完成；缺料或刀钝阻断；正常保存重进后不重做已确认单件。资产不确定分支用定向逻辑故障检查确认不自动重试；强退崩溃一致性单独研究，不能用正常存档测试代替。

通过这一步才推进父单、共享认领、正式页面与自动物流共存验收。必要检查随实际代码变更运行：Lua preflight、Java相关构建、针对性逻辑回归和文档链接检查；不重跑历史全套测试，也不追加冗长人工清单。
