# 搬运原件责任与可变交付路线设计（评审稿）

> 日期：2026-10-26｜状态：用户已确认实施R1及当前有效任务有界升级；R2与人工核销延期｜设计版本：0.2；实现与验证状态见BACKLOG。

## 1. 结论、地位与本次授权

建议局部重构自主搬运的业务记录、交付选箱和恢复入口，保留统一任务控制、原版转移动作及唯一资源权威。不重写整个搬运系统，不另建物流调度器。

本稿从属于[NPC 唯一架构 v1.2](2026-10-22-npc-behavior-architecture-design.md)第 3.4、3.5、4、5、6 节及[统一任务协议](2026-10-23-unified-task-dispatch-design.md)第 5、9、13、17 节。只细化自主整理的“原件责任不变、交付路线可变”，不成为第二架构入口。R1已获实施确认；参数仍须测量，不能按设计本文直接宣称实现或实机验收通过。

用户先授权设计及独立AI评审，随后在0.2修订后明确“开始吧”，批准实施R1及§9限定的当前有效共享Job升级。R2、人工核销、其他交付语义未获本轮实施授权；当前实现与验证按BACKLOG及专题证据维护，设计本身不证明验收通过。

## 2. 问题证据与基线

用户在 NPC 已取货并开始向冰箱交付时，将冰箱改成全部拒收。截图显示入库 1/6、`FILTER_REJECTED item=454789034`，继续不能推进。

### 2.2 当前实现的具体约束

| 位置 | 源码事实 | 对重构的影响 |
|---|---|---|
| LogisticsPlanner.new / step | 新批次同源、同目的地；跳过 Claims.owner 已认领物品，取货受 freeCarry 限制 | 不能原样用于已持货的重规划 |
| WorkBatch.choose | 在源箱、NPC、单个目标箱中查原件；目标箱位置计入 delivered；只选择首个持货候选 | 换箱后会丢失旧目标中的完成判断；首件阻塞也可能挡住其余货物 |
| WorkAgent.launch / nextStep | record.destination 是整批单端点；恢复启动仍解析旧目标 | 不仅正常 tick，恢复入口也必须允许目标失效后的重新规划 |
| WorkAgent.stopAdapter.effects | 重验当前两端政策并在三容器内查整批 ID | 政策拒绝、已交付历史与效果未知当前耦合，不能仅修选箱 |
| WorkAgent 的 transferred 闭包 | 捕获启动时的 destination，用它决定容量释放 | 直接改 context.destination 会留下旧目标闭包 |
| LaborClaims.reserve / reserveMany | 每个 token 仅允许一个 capacityKey | 不支持同一 token 同时预约多个目的地 |
| PublicWork.decide | 当前自动恢复分支只接受 SAVE / LOAD_RECOVERY | 路由等待必须显式接入责任恢复，不能只增加一个暂停原因 |

首轮评审后补充两项源码辨析：`Registry.revalidate` 经 resolve 检查对象、范围及 Filter.access；分类“全部拒收”使 Filter.matches/Registry.accepts 失败，但在 enabled=true、private=false 且格式有效时，不使 Filter.access 自动失败。因此“本次全部拒收必然令 stopAdapter 返回 UNKNOWN”不是源码结论。私人、禁用、端点失效或找不到原件等情况仍可能触发现有 UNKNOWN，必须拆分观察与执行政策，但不能据此绕过隐私读取。

旧 LogisticsService.advance 也并非只在 SAVE 时首次恢复：`ctx.attempts[npcId]==nil` 时允许一次尝试，后续才受 SAVE 与代次限制。其与 PublicWork 的问题是未建立完整、条件驱动的路由责任恢复协议；不能把两处实现简化成完全相同的原因白名单。

## 3. 先反对扩大重构：方案与取舍

| 方案 | 好处 | 代价与结论 |
|---|---|---|
| A：保持整批单箱，拒收时直接替换 destination | 改动少，容易演示 | 破坏已交付核对、容量预约、旧回调和保存语义；不采纳直接字段替换 |
| B：原件清单独立于可变路线，分站串行交付 | 保留既有执行权威，覆盖部分交付、拒收换箱及后续混装 | 须改业务记录、停止观察和恢复接线；推荐分两阶段实施 |
| C：全面重写为全局多 NPC 多源多站最优配送系统 | 理论上可能减少行走 | 没有测量证明收益，需要协作、交接与复杂规划，增加恢复成本；当前不采纳 |

默认继续有效的当前路线；不因另一个箱子稍近就反复改道。目标不合法、容量不足或实际路径失败时才对受影响原件重规划。一次寻路失败只退避该 NPC 与该端点/接近点组合，不证明整个箱子永久不可达。

## 4. 分阶段范围

| 阶段 | 交付能力 | 范围外 |
|---|---|---|
| R1：修复与责任记录收口 | 初次仍按现有同源同目标成批拿取；目标变化后，剩余原件可改送不同容器；可以先完成可交付部分再等待 | 不主动为凑载新增其他目标或其他源箱货物 |
| R2：主动多目的地混装 | 同一源箱的一批物品允许初始就有不同目的地；一个 Job、一个 NPC、逐站执行 | 多源顺路取货、多个 NPC 分段协作、全局最短路、跨据点配送 |

本稿完整定义 R1 所需责任与交接，并给出 R2 的边界；R2 是待审后续范围，不因数据结构容得下便随 R1 自动上线。R1 因规则变化产生的分站数最多为原件数，不受 R2 初始混装站数限制。

仅自主 LOGISTICS 的“归库/整理”语义允许自由换箱。显式端点搬运、制作取料/归还/成品交付、借书和未来商队交付仍由各自业务契约决定，不统一改成自由入库。

## 5. 核心模型与不变量

### 5.1 三种记录分开

1. **原件责任清单**：稳定 jobId、npcId、itemId、原来源、业务约束、取放尝试、已核验效果与未结责任。仍存于现有 Job.payload，不建立第二库存账本。
2. **交付计划**：某原件拟送的容器、路线版本、当前站点及候选观察依赖。计划允许失效；它不是物理位置和执行授权。
3. **物理效果记录**：对某次尝试核验后的取货/交付事实，包含 itemId、from/to 稳定身份和 attemptId。完成事实不能靠改 destination 重新计算。

JobId 和 NPC 责任不因改道变化。Session 仍由 TaskRuntime 授予；路线版本、动作尝试序号和 Session 代次分别维护，不拿路线失效冒充身体停稳。

### 5.2 待审持久化字段

新自主搬运 payload 使用明确的新流程版本（提案 format=2）；保留 Job 信封及共享权威。下面为字段契约，不是可直接执行的 Lua 实现：

| 对象 | 必需数据 |
|---|---|
| Job | format、id、npcId、settlementId、producer、generation、routeRevision、业务状态、settlementOutcome |
| items / plannedCount | 创建时的完整数字 itemId 数组及原计划总数，整个 Job 生命周期不因交付或撤回缩减 |
| manifest（最多 30 条） | itemId、sourceId、sourceMode、deliveryPolicy、custodyState、plannedDestinationId、deliveryReceipt |
| activeAttempt（最多 1 条） | attemptId、itemId、TAKE/PUT、fromId、toId、routeRevision、sessionGeneration、效果核验状态 |
| activeStop（最多 1 个） | destinationId、该站 itemIds、预约引用与观察依赖 |
| routingWait | 类型化原因、受影响 itemIds、观察依赖、下一次有界复验条件 |

manifest 的 itemId 必须唯一；attemptId 用稳定 Job 身份及持久序号组成，不能用每次恢复重新归零的计数。回执最多每原件一条终结交付事实；取货/当前尝试信息原位更新，不积累无界事件历史。持久化只保存标量与普通表，不保存物品对象、路径器、闭包或队列。

`record.items` 保留完整、唯一、有限数字 ID 数组，manifest 与 items 必须一一对应，`plannedCount=#items`。不采纳把 items 改成“剩余责任数组”的建议：当前 UI、完成摘要等以 #items 作分母，缩减会让 1/6 变成 1/5，最终分母归零；通用查询含义也会静默变化。

新增唯一入口 `HaulManifest.claimItemIds(record)`，按 manifest 派生 UNCOLLECTED、CARRIED、RECONCILE 对应的未结 ID；format=2 的 LaborStore.resources、恢复声明、hasCargo 及业务义务判断消费该派生集合。items 只回答原计划包含什么，不能再直接当 format=2 的当前声明。派生集合不另存一份可变权威索引；format=1 沿用旧语义。UI、完成摘要、回收及格式校验均显式按版本适配，不能以“字段还在”声称原调用已经兼容。

`deliveryPolicy` 首版只启用 `AUTO_STORAGE`；为固定目标/冷藏等语义保留明确的业务区分，未知 policy 拒绝执行，不默认放宽为 AUTO_STORAGE。冷藏检测及烹饪规则不在本轮凭空接入。

### 5.3 原件状态与效果

| custodyState | 含义 | 允许行为 |
|---|---|---|
| UNCOLLECTED | 未经本 Job 核验取走的计划原件 | 规则允许时取货；需求撤销且无在途尝试时可撤回此行 |
| CARRIED | 核验原件由本 NPC 持有 | 优先交付；无目标则保留责任等待；不当新公共物品再认领 |
| DELIVERED | 已核验某次交付到合法端点 | 保留已交付数，不因旧箱随后改策略而重搬 |
| WITHDRAWN | 本 Job 未取走且已撤回的计划行 | 释放对应无效果声明，不能计入交付数 |
| RECONCILE | 当前取放结果或原件身份存在实际不确定 | 保留相关声明与义务，不重放该原件动作 |

另存观察状态 KNOWN/UNLOADED/STALE 和身体状态，不能把“目标未加载”“筛选拒绝”直接设成效果 UNKNOWN。若确有未决原生尝试，且无法通过允许访问的物理证据核验，才隔离该尝试。

隔离粒度沿用当前安全边界：R1 一旦存在真实未决效果，暂停整个搬运 Job 的新物理提交，不顺便承诺“同 Job 的其他原件仍可执行”；允许已确认安全的独立撤离/自理仍按唯一架构处理。上文逐行状态是责任事实，不代表已经授权细粒度并行恢复。一件物品只是没有合格目标、效果仍已知时，才允许继续交付其他原件。

历史 DELIVERED 回执证明本 Job 曾正确交付，不承诺物品永远留在原箱。玩家随后拿走或物品自然变化，不撤销已完成交付，也不要求继续读取已经变私人的旧容器。运行中直接观察到同一 ID 冲突等反证时进入核对，不能用历史回执掩盖冲突或给旧动作再次发放执行权。

### 5.4 效果观察与执行许可的接口边界

候选选择、TAKE/PUT 提交仍调用有访问权限与业务筛选的端点验证；不移除 WorkTransfer.isValid 的目标接受条件。停止后的 `observeAttempt(record, attemptSnapshot)` 则返回身体观察、效果 KNOWN/UNKNOWN、证据类型及可观察性，不以“现在是否还允许下一次存入”作为历史效果是否已知的判断。

效果观察按原尝试快照核对实例归属、容器身份及可用后置证据，不直接把带业务准入的 Registry.revalidate 返回值当成效果判定。核对不要求角色仍站在旧交付点，也不要求当前容器仍接受该物品；物理可接近、业务可访问及效果可证明是不同条件。

但物理对象仍可遍历，不等于业务有权读取。私人/未配置容器不因核对而获得全量盘点例外：优先用此前已核验的回执、当次合法观察、NPC 自身持货及获准读取端点核对。若证据不足，仅保留该尝试 UNKNOWN 与受控恢复等待；不得透过旧 userdata 偷读私人库存。对象存在、三处找到同一 ID 或 perform 名称本身都不足以证明特定尝试已完成，仍要排除重复身份、关联错误和物理后置不符。

## 6. 初次取货、改道与分站交付

### 6.1 取货边界

R1 保留当前同源同初始目标批次和物理负重限制。每次 TAKE 前重验源箱访问、整理模式、原件可搬性、声明、NPC 容量及目标现时可用条件；初始候选不保证稍后还有空间。

一旦携货时发生目标失效，关闭本 Job 后续取货，转入仅处理已持货责任的交付阶段；未取行在无未决 TAKE 时撤回，显示撤回数量。后续公共发现可另建新批次，但同一 NPC 必须先结清本批持货。这样不让 NPC 边找新箱边继续把背包装满。

R2 才允许初始混装。建议初始最多 3 个目的地、总计最多 30 原件，参数须经评审和测量；后续站点的容量仅是观察，不作长期保证。其成本是中途箱满时可能持货等待；若实际收益不足，维持 R1，不为混装本身扩大原件与容量协议。

### 6.2 目标变化时的顺序

1. 容器事件仅置脏；已有动作提交前仍权威重验，不依赖事件必达。
2. 禁止旧路线继续派发。若动作/移动在执行，经现有控制器请求停止，保留原路线、原 attempt 与身体票据，直到停止和效果被观察。
3. 核验当次原件：已合法交付则只记一次；仍在 NPC 则继续承担交付；未取走则不虚增持货；结果不明则隔离，不换箱重放。
4. 旧 Session 正常闭合后，按原件结果提交新路线版本、处理旧站点容量；不能先递增业务 generation 令旧停止适配器失效。
5. 经责任恢复取得新 Session，再向新的当前站点移动及交付。旧回调只能为匹配 attempt 归账，不能清新队列、释放新预约或启动后继。

已确认安全步骤边界、尚未有动作/移动时可以只更新计划；一旦存在原生执行或停稳不明，不走这个快捷分支。不在 Registry 事件回调里清队列、改路径或执行新转移。

### 6.3 为持货选目标

独立的持货候选评估消费现有据点容器查询、StorageFilter、SortPolicy 和 LaborStore；不原样复用新货规划器中“排除已认领物品”和“要求新增负重空间”的门。

硬条件为所属业务允许的据点/区域、已配置且非私人、当前 STORAGE 角色、原对象与容器身份匹配、接受该原件、原生 hasRoomFor、扣除其他任务预约后的容量，以及本 NPC 当前可承担的业务上下文。固定交付及冷藏等约束不能被距离抵消。

先保持仍合法的已有目标；失效后沿现有分类特异性→距离→稳定 ID 排序候选。距离从 NPC 当前地点估算，不继续从原源箱估算持货路线。几何距离不是已证实可达，只对选中的少量目标寻路；失败按目标组合退避再尝试其他候选。

同一目标合并为一个站点，逐站串行执行；一件物品无目标不挡住其他可合法交付原件。每次 PUT 前再验规则、原件、距离、真实容量及预约；选箱缓存不是提交许可。

### 6.4 已交付事实的签发

原生 perform 回调返回不直接等于已交付。必须按本次 attempt 的精确 from/to，核验原实例在 to、to 包含它、from 已不包含它、任务及尝试归属一致，才发布该原件的回执并释放相应容量和已结原件声明。

若动作没有效果但原件仍由 NPC 持有，回到 CARRIED；若转移已发生但通知重复，只返回同一事实。旧路线关闭后到达的效果通知不直接丢弃，也不能修改新路线的容量；交由原 attempt 的核对入口归账。相关旧 attempt 未决时，不向同一原件授权新尝试。

### 6.5 执行上下文与闭包生命周期

Work.context 只表达当前 Session 与当前站点；通过 `installStop(expectedRouteRevision, stopPlan)` 在无旧动作/移动、身体边界已确认时安装新的站点执行上下文。安装时重解稳定容器 ID、重验对象身份、建立对应容量引用，并替换整份站点上下文；禁止只改 record.destination 或对现有 activeStop 原地改容器。

规划和未启动动作可以读取当前 activeStop；**已经创建的动作回调必须捕获不可变 attemptSnapshot**，至少含 world、jobId、itemId、attemptId、routeRevision、sessionGeneration、from/to 精确实例引用及原预约身份。持久化只存其中标量，实例引用仅留运行期。eligible 根据本次快照重验当前政策与会话，不能把旧动作动态解释为新站点动作。

transferred/poll/stopAdapter 用同一快照向效果入口提交证据；效果入口幂等归账后，仅释放该旧尝试所对应且仍归本任务所有的资源。不得从动态 activeStop 取新箱地址、新 token 来释放旧动作容量。旧会话无当前执行权时禁止继续原生提交，但已发生效果的通知仍须进入原尝试核对。这同时解决静态捕获旧 destination 的问题和“所有回调一律动态读取 activeStop”会误伤新站点的问题。

## 7. 容量与声明：首版保持一次一个目标

不把 LaborClaims 改造成多目标预留系统。一个 Job 同一时间只持有当前站点的容量预约；其他站点只是可重建计划。多个不同目标的物品可以一起携带，不等于要同时锁住所有目的地容量。

当前 token 的单 capacityKey 限制保留。换站必须由 LaborStore 提供受控入口：验证旧站点对应尝试已核对且不会再写入 → 解除旧站点尚未生效容量 → 在共享权威内尝试预约新站点可交付子集 → 发布站点及对应持久预约。不是直接改 capacityKey，也不能调用释放整个 token 来换箱。

身体交接与原件效果核验已完成后，可以撤回暂时未使用的目标容量；它不是持货所有权。USER 暂停、自理暂停和加载重建均须采用同一规则，不能因保留 Job 而无限锁住旧站空间；恢复时重新申请。已存在但尚未核对的 PUT 所关联容量不能提前按“没有效果”释放。

该更新在同一主线程业务调用内完成，不跨 tick 持半更新、不触发观察者回调；申请失败可进入无容量预约的明确等待，原件声明始终保留。共享账本更新与 payload 预约镜像需成组更新后才发通知，异常时禁止继续派发并核对；不宣称这一 Lua 逻辑步骤具备磁盘 ACID。

新箱只够放部分物品时，按清单稳定顺序预约能放下的子集，不要求整批一次装下。当前站点交付结束后再为下一站预约。玩家可能占用空间，物理提交仍要复验。

已核验 DELIVERED 行的原件声明按权威逐行释放，不因 Job 其他货物等待而长期锁住已入库物资。需要增加同 token 的安全子集缩减能力：只允许移除有已知结算证据的行，并同步对应容量及持久声明；现有 replace 拒绝带容量 token，不能直接绕过保护。CARRIED/RECONCILE 原件绝不因改道或超时释放。

### 7.1 声明缩减与镜像提交契约（拟新增）

上层唯一入口建议为 `LaborStore.settleHaulLines(record, token, expectedGeneration, settlements)`，底层为 `Claims:shrink(token, releasedKeys)`；名称为提案，语义不得省略：

1. Store 先验证世界、活动 Job 身份、当前 token/代次及 settlements 的逐行证据。只接受合法 DELIVERED、无在途 TAKE 的 WITHDRAWN；重复且完全相同的已结算请求幂等返回，不重新释放已被别的任务取得的原件。
2. shrink 先对释放集合去重并验证全部 key 确为该 token 所有，校验 token.resources 与 owners 一致，涉及的容量条目也必须引用同 token。失败零变更；底层只做协调校验，不能代替 Store 判断某件物品是否已交付。
3. 提交时同步移除 owners key、从 token.resources 删除相应 key，并扣除这些原件在唯一 capacityKey 下的条目、计数和总额；无剩余容量才清 capacityKey。保留的原件和容量不受影响。不直接写 owners，不调用被 capacityKey 门禁拒绝的 replace。
4. Store 在同一无回调、无跨 tick 的受控提交段内同步 manifest 终结态/回执、reservation 镜像与派生声明结果，最后才通知观察者。需预先构造并校验提交数据；异常后禁止新派发并进入核对，不把一部分成功包装成全部成功。
5. Store.pause/claim 和加载重建都从相同的 claimItemIds 推导集合；下一代 acquire 比较的是缩减后的 token.resources 与派生集合，而不是完整 record.items。必须覆盖“逐行结算→暂停换代→继续”和“逐行结算→保存重进”。

最后一个原件结清是特殊边界：无容量且剩余资源为空时，先把该代 token 从 Store 的活动索引退役，代次仍由 record 维护；不得继续把空 token 当有原件的所有权凭证。此时 Job 可能仍要等待身体/回调关闭后才能回收，但不再进行 acquire 空集合或重建货物声明。保留或移除技术 token 不得成为第二个任务误取未结物品的理由。

## 8. 等待、唤醒与身体交接

路由结果至少区分：READY、SCAN_PENDING、NO_ACCEPTING_TARGET、NO_CAPACITY、TARGET_UNOBSERVED、PATH_BACKOFF。SCAN_PENDING 不等于找不到箱；RECONCILE_REQUIRED 单独表示实际效果/身份不确定，不属于普通路由重试。

无可执行站点时经停止协议结束 Session，保留 Job、持货声明和类型化等待原因，不永久占用身体。危险、自救、自理和玩家命令仍走现有仲裁；不能顺便领取无关普通生产任务。暂停/跟随不使持货自动转成闲暇可消费库存。

复用 PlanningWake 的依赖观察和现有共享调度，在规则、容器库存/容量、据点范围变化及相关路径退避到期时生成本 NPC 的责任恢复候选；再补错峰低频兜底。不得只依赖 PublicWork.decide 的普通工作资格入口，否则 FOLLOW/WAIT 下可能根本到不了恢复分支。

### 8.1 责任恢复的具体接线（拟新增）

由现有共享任务推进路径在普通公共候选发现之前，按全局预算调用 `LogisticsService.advanceRecovery(actor, npcId, now, budget)`。该入口观察 format=2 的暂停/等待 Job，调用 `HaulRouting.recoveryStatus` 返回 BLOCKED_UNKNOWN、MANUAL_PAUSED、CONTEXT_WAIT、OBSERVING、NOT_DUE 或 READY；不靠在 PublicWork 追加几个 reason 字符串来推断全部许可。

只有系统路由等待、保存恢复或合法自理恢复关系才可申请恢复；还须验证效果已知、没有其他 Session/待交接、世界及 Job 代次一致、当前命令允许、保存屏障开放。READY 才调用同一个 Work 的获授启动入口；所有兼容旧物流入口也委托它，不各自增加重试器。USER 暂停、controlUncertain、已覆盖的玩家意图或未完成自理一律不自动启动。

PublicWork.decide 遇到已有 Job 时不再承担唯一恢复职责，只阻止领取无关公共单；LogisticsService.advance 对新版本不再用 ctx.attempts 的“一次尝试/SAVE”逻辑管理路由等待。TaskResume 通过相同恢复许可恢复原 Job，不得绕过 USER/上下文门禁。

容器事件使依赖命中的 routingWait 到期并把 NPC 标为待评估，清理相应发现休眠；新配置容器也必须通过据点成员集合版本/范围失效被发现，不能仅监听原失败箱子的 ID。这里“唤醒”是下一次预算允许时重新评估，**不是事件回调立即移动**。容量的逻辑释放也需经共享权威发失效提示，不能只等原生库存事件。退避失败、无匹配依赖或没有可靠事件时仍由有界错峰兜底覆盖。

区分玩家 USER 暂停与系统 ROUTING 等待：只有后者允许条件变化自动恢复。跟随/停留时可以保持等待及必要自理，普通入库移动不得违背当前命令；重新驻扎或明确继续后，再评估持货责任。进食/睡眠后的 TaskResume 恢复原 Job 时允许重新选箱，不要求旧目的地先恢复合法。

建议首版全局每轮最多评估 32 个“原件×目标”组合、最多推进 2 个路由恢复候选，沿现有调度轮转；全无目标的兜底起点为 5 秒现实时间加稳定 NPC 错峰。所有数值为未实测提案，应接入现有预算入口，不能每 NPC 各自获得全额预算或新建定时器。失败路径候选最多保留原件数×每件 3 项，过期清理；单轮候选耗尽进入等待，不无界换箱。

## 9. 保存、恢复与当前卡住任务的版本边界

复用统一保存屏障；先停派和收集停止/效果事实，再保存业务记录。保存 activeAttempt、路线版本、持货/交付/撤回状态及容量镜像，不保存 Session 或引擎引用。

加载后先验证记录并重建尚未结清原件声明，再恢复可保守重建的当前站点容量，最后开放责任候选。计划端点一律重新解析及重验，失效不阻止已确认持货进入重规划。已签发交付回执不能因为旧箱未加载/变私人而被撤销；存在未决尝试且证据不足时，保留核对状态，不用交付计数猜测结果。

格式升级必须显式决定，不能将本稿当作重新授权兼容所有旧档：

- 新建任务使用新 payload 版本；旧 CommunityTrade、共享 Job 切换前记录及未知格式继续按既有决定拒绝自动导入，保留数据与原物。
- **用户本轮已批准仅对当前有效共享 Job 内的搬运 format=1 做一次有界升级**，以便处理眼下这张未结任务。只限效果已知、旧身体已停止、现有记录与声明验证通过的 Job；逐原件核验后构造新清单，同 jobId/npcId，不重新领取货物。
- 当前可访问旧目标中的原件可记为“升级时核验已交付”；NPC 持有记 CARRIED；源箱原件记 UNCOLLECTED；数量计数、TAKE 日志、物品类型不能代替逐 ID 证据。缺失、重复、私有/未加载导致证据不足或 controlUncertain 的任务不自动升级。
- 升级先在临时结构中完整验证，再替换 Job payload 并重建声明；不改世界物品，不删除旧 Job 后新建。升级失败保留旧 payload 和责任，不进行半升级。
- 这是用户本轮确认的有限格式演进例外；不扩大到更早旧格式，也不保证证据不完整的现场可升级。必须说明升级失败的原件证据原因，不能宣称所有卡住任务都会自动恢复。

正常保存重进、强退、跨文件崩溃分别验证；没有引擎持久化证据，不承诺崩溃原子性或零损失。提交与保存之间的异常以保留事实和核对为边界。

## 10. 完成、部分撤回与界面

只有所有行均为 DELIVERED 或合法 WITHDRAWN，且无未决尝试、持货、容量、身体和恢复关系责任时，Job 才可结清。DELIVERED 数量只来自回执，WITHDRAWN 另计，不能把“结清”写成“全部入库”。建议保留 `settlementOutcome=DELIVERED/PARTIAL_WITHDRAWN/WITHDRAWN` 区分原因，顶层 Job 结清及回收仍服从既有协议。

人工取消也不能删除 CARRIED/RECONCILE。R1 不新增自由丢弃或自动绕过筛选归还原箱的操作；需要放弃持货责任时须另走明确业务交接，不纳入本次修复。

### 10.1 丢失嫌疑与管理裁决的延期边界

采纳“真实丢失长期未决会影响可用性”的风险提醒，但不采纳“扫描背包、周围地面和关联箱子即可证明原件不存在于物理世界”。PZ 未加载区域、玩家/其他 NPC 库存、其他容器及外部模组都可能持有原件，当前没有查证过的全世界原件存亡判据。局部未找到只能报告 `ITEM_NOT_LOCATED`，不能签发 `PHYSICAL_INSTANCE_LOST` 或假造 DELIVERED。

R1 对此保持业务隔离、显示原因和已检查范围，在已确认停稳后开放既有安全撤离/自理；普通新搬运/生产仍按未结责任门禁处理。因此 R1 不承诺修复所有外部销毁、作弊删除或身份损坏引起的业务阻塞。

如以后用户确需人工裁决，可另行设计需明确确认的 `WRITTEN_OFF` 责任核销：这是玩家承担风险的业务决定，不是“物理证实丢失”，交付计数不增加；需记录原件 ID、未决 attempt、裁决身份/原因与幂等命令，并处理原件再次出现时的冲突及技术回执回收。核销不得恢复旧动作执行权、重新制造同 ID 物品或自动计为成功。此能力不属于已批准架构或本轮 R1 默认实现，不能借首轮评审建议直接新增产品按钮。

工单监控复用现有页面：显示已交付/原计划、已撤回、仍持货、当前交付站以及“正在重新选择容器/没有允许存放的容器/容量不足/等待区域加载/等待核对”。多站时允许详情显示各原件拟送/已送位置，不能只留一个旧冰箱坐标；没有物理证据的 cargo 不再一律标 TRANSIT。机读原因与 ID 放诊断详情，CN/EN 成对。未改变的已交付物品不要求用户重新搬走。

日志仅在路线、等待原因或效果变化时记录 job/npc/item、old/new target、routeRevision、attempt、拒绝桶和核验结果，不每 tick 输出整份清单。按现有结清条件释放并回收 Job，不新增无限历史账本。

## 11. 建议模块边界与复用依据

| 模块 | 建议职责变化 |
|---|---|
| LogisticsPlanner / SortPolicy / SettlementMembership | 保留新货发现；提取可供持货消费的纯目标评估与排序，输入明确区分新取货和持货 |
| 拟新增 HaulManifest | 清单校验、逐原件状态、尝试/交付回执、未结声明集合；存储仍在 Job.payload |
| 拟新增 HaulRouting | 分站候选、路线版本、有限退避及等待结果；不驱动身体，不另建调度循环 |
| WorkAgent / WorkBatch | 执行当前站点与原件，消费清单，不再以单目标位置推导全部交付数；原 format=1 显式端点路径保留边界 |
| WorkTransfer | 复用原版 ISInventoryTransferAction 和原实例后置核验，捕获不可变 attemptSnapshot；执行验证与历史效果观察分开，不偷读私人库存 |
| LaborStore / LaborClaims | 当前站点容量切换、settleHaulLines/shrink 与镜像更新、派生未结声明及空集合边界，仍是唯一权威 |
| TaskRuntime / TaskBusinessStop / TaskResume | 保留停止和 Session；效果观察改为消费尝试事实，不将政策可用性当物理效果已知性的唯一依据 |
| PublicWork / LogisticsService / PlanningWake | 接同一责任恢复及共享预算；兼容旧入口时也复用该业务恢复，不另建一套自动重试 |
| BusinessJobs / TaskPersistence / TaskRetirement | 新 payload 校验、声明重建、结清门禁和有界回收 |
| OrderMonitorService / 现有 UI | 当前站点、多站完成事实和明确等待投影 |

成熟做法来自本项目已有 SortPolicy 选箱、共享资源声明、TaskRuntime 停止交接及其他业务的逐原件恢复思想；不能直接复制制作/借书的不同交付语义。没有第三方项目“多站搬运已成功”的查证，不拿参考项目名当验证证据。

## 12. 最小验证与交付门槛（均未运行）

只围绕故障边界补必要回归，不搭建独立模拟框架，不重复全历史替身测试。修改 Lua 后仍须项目规定 preflight；涉及 Java 才增加相关构建。本轮仅文档，不运行这些代码检查。

| 场景 | 必须观察的结果 |
|---|---|
| 原现场：1 件已交付、剩余持有/未取混合，冰箱全拒收，另有合格箱 | 旧交付仍计 1；未取行明确撤回；剩余持货改送；无复制、无重新取旧货 |
| 持货食物/工具须分箱；一个箱只能放部分；其中一件无目标 | 有目标的先交付，无目标的保留责任等待；不整批卡死，不超额占用 |
| 两 NPC 竞争同一容量，换箱申请失败 | 无两份过量预约，无丢失持货声明；失败者可退避重选 |
| PUT 排队后改规则、提交期间通知、停止同步回调、旧回调重复到达 | 只确认一次实际效果；新旧 Session 不并行，旧回调不清新队列/预约 |
| 规则恢复、箱子腾空、私人/未配置、角色改变、端点拆除/替换/未加载 | 合法变化可唤醒；非法容器不访问；未知观察不误报丢物；失败目标不无限循环 |
| 改道/等待中自理、跟随、USER 暂停、返回驻扎及正常保存重进 | 命令和身体交接正确，责任保留，自动恢复不覆盖人工暂停，回执不重放 |
| 当前有效 format=1 任务升级（仅批准后） | 同一任务逐 ID 核验，失败不半升级，未知与更早旧格式不被静默接纳 |
| 显式端点搬运、制作取料/成品、借书回归 | 不被自由选箱规则改送；原有业务限制保留 |
| 全拒收与私人/禁用分别触发停止 | 前者不凭分类拒绝推 UNKNOWN；后者不得绕过隐私读取，证据不足明确核对 |
| 逐件完成后暂停换代/重进、最后一件完成但身体尚未关闭 | 原计划分母不变，无 RESOURCE_SET_CHANGED、容量残留或空 token 复用；不提前回收 |
| 新容器配置、逻辑容量释放及旧动作晚回调 | 新目标可在预算内发现；旧回调不使用新 activeStop、不误释放新预约 |
| 原件只在局部扫描中未找到 | 不伪造全世界丢失证明、不增加交付数、不自动核销；显示核对范围与业务阻塞 |

R2 单独比较同负载下的总行走、有效交付量、持货等待时间、单次与累计 CPU，再决定是否上线初始多站混装。不能凭新增字段、替身通过或更少路线条数宣称实机效率提升。

## 13. 交给评审 AI 的问题

请先尝试否定方案，按严重度列出可触发的反例、违反的既有契约及更小替代方案；不要直接写代码。重点检查：

1. R1 是否足够解决原现场；原件清单与路线分离是否仍有更小且同样安全的实现？
2. 历史交付回执与当前可观察性分离，是否会在晚到回调、玩家移动原件或物品消失时误结清？
3. 单目标容量预约及逐原件声明释放，是否与现有 token/generation、暂停重建和持久镜像冲突？
4. 新旧路线交接顺序是否漏了“已产生物理效果但尚未 poll”的窗口，以及 stopAdapter 捕获旧端点的问题？
5. 无目标等待是否真正释放身体，并正确通过 SELF_CARE、FOLLOW/WAIT、USER 暂停和责任恢复入口？
6. 当前共享 Job 的 format=1 有界升级是否符合既有“不做旧档兼容”的范围决定；若不同意，如何明确处理原现场而不清任务或造物？
7. R2 是否应继续延期；当前站点之外不预约容量所增加的持货等待，是否值得换取更小的资源协调复杂度？
8. 预算、私有端点、跨层路径、部分交付 UI、Job 回收及其他物流入口是否仍有遗漏？

评审通过只代表设计可接受，不代表代码完成、原生动作通过或支持某个 NPC 规模。用户随后已确认R1实施，实际交付状态见BACKLOG和实施证据；R2及新增核销能力仍不自动进入实现。

|---|---|---|
