## 1. 已确认方向与授权边界

用户已暂定：

1. 汤、炖菜、炒菜等自由组合料理由厨师自主选择食物、配料和调料，玩家不用逐锅下单。
2. 指定成品可通过请求安排，固定配方及复杂料理走已适配的原版制作链。
3. 自由组合/固定配方是制作机制，是否需要学习是另一维；一切使用NPC本人真实知识与技能，不因“自主”跳过门槛。
4. 日常按人数提前维持少量餐食储备，人口变化自动调整。用户进一步明确“全员永久计入”：全部存活且正式归属据点的NPC均计入，跟随/外出或暂不可见不扣人数；死亡或正式移籍后更新。储备按制作出的食物实际饱食度及其剩余量计算，不按锅大小。
5. 区域随对应工种开发，本轮不先建个人工作区、居所绑定或厨房划区前置条件。
6. 用户在详细设计和评审修订后明确“开始吧。基础必须打好”，据此进入实施。R2强度与R3～R5按本稿初值执行，实际profile和动作必须通过原版接缝核验；不把开工授权当作玩法验收。

从属于[NPC唯一架构v1.2](2026-10-22-npc-behavior-architecture-design.md)和[统一任务协议](2026-10-23-unified-task-dispatch-design.md)。不更换架构、不另建厨师调度器、不引入逐小时排班。单人优先，保留未来权威命令边界，不宣称已实现联机。

## 2. 先排除三条不合适的路线

| 路线 | 价值 | 不采用的理由 |
|---|---|---|
| 每种菜一张最低存量单 | 沿用制作系统最省开发 | 玩家要分别管理汤、炒菜和炖菜；各自补满造成重复储备，不符合本轮自主厨师方向 |
| 完整照搬ProjectRemnants的求餐路线 | 居民能自行向厨师点餐 | 它以实际求餐和少量备用为主、按件计数；还包含居民走近厨师和送餐。本轮用户选的是提前备餐，不额外复制这些交互 |
| 全营养最优化与自由菜谱搜索 | 理论上可优化营养和效率 | 当前没有可靠消耗预测、任意配方效果模拟和成本证据；搜索复杂、难解释，也超出已批准架构 |

本稿采用：共享餐食缺口决定是否开工；厨师在有界、已适配的自由料理中选择；逐次读取原版准入和真实变化决定继续加料/收尾；指定成品请求独立表达。实际动作仍是现有BT动作叶与统一Session，不把这套决策做成第二执行器。

## 3. 玩家体验与需求对应

普通使用：开放合法食材/厨具/设备/成品仓储 → 在矩阵启用厨师工作 → 自主备餐。日常无需选择配料、指定执行者或维护每种菜的库存。设备与物品仍受既有私人/未登记保护，发现厨房不等于授权开箱。

指定成品：从既有仓储快捷入口或原版制作委托入口下单，选择成品及数量；有缺知识/技能/原料时显示具体原因，合法待领请求可以等待。自由料理同样可被指定请求，例如“再做两锅汤”，不按知识门槛决定是否允许点单。

## 4. 共享餐食储备：何时开工与停产

### 4.1 供餐人口

R1已由用户改定：计入全部存活、正式归属该据点的NPC。驻扎、等待、工作、睡眠、研习、跟随出行及在外远征均计入，不以位置或宏观命令扣除。“永久”指归属存续期间持续计入，不是死亡后仍占人数。玩家角色是否纳入不是本次明确决定，沿原稿不自动计入，不新增includePlayer配置或UI开关。

人口从持久成员账本按稳定npcId去重，按已提交成员事实更新；调驻处理中保留旧归属，提交后移至新据点，不同时计入两处。已确认死亡的当次成员事实即剔除；暂时失联/无法观察不等于死亡。人数下降只停止新批次，不删除食物、不撤销炉内收尾责任。

全员持续计入会为长期外出者继续备餐，增加本地存放与腐败风险，这是用户选择的成本。仍保留有限目标与冷藏条件，不据此增加远程送餐或无限烹饪。

### 4.2 计量单位与可计入物品

R2计量口径已由用户确认：按制作出的成品当前实际有效饱食度及剩余量统计，不按锅/碗件数或锅容量，不声称热量达标或可吃几天。确认计量方式不等于批准下述强度系数。

当前JAR核对：getHungChange()直接返回底层hungChange；getHungerChange()读取该值并应用熟食等原版状态修正，其中已熟分支为×1.3。IsoGameCharacter.Eat使用getHungerChange()改变饥饿。储备拟按F(item)=max(0, -item:getHungerChange())求和，显示时乘100转为饱食点，不能把原始值和显示点数混算。先过可食用与安全门，再计F，不能因为getter有正贡献就计入腐烂/烧焦物。

现有SelfCareActions用max(0, -item:getHungChange())追踪部分消费，这是原件效果核对量，不等于有效供餐量。本轮不顺带改自理算法；两种量明确命名/换算，部分食用的实际后置仍需验证。标准餐食单位u暂建议取现有吃饭进入/结束阈值之差0.25−0.10=0.15，仅供强度标尺，不改原版阈值。

计入自由料理/固定料理成品及已登记为餐食的安全即食成品，需满足：在授权仓储、非其他任务独占、当前消费者确实能食用、未腐烂/烧焦/污染，且该物品需要烹熟时已熟。存于冰箱但仍需解冻/加热才能被当前进食适配消费的物品，列待处理，不冒充即食。

半锅/半碗按实际剩余量计；同一itemId只计一次，锅与其料理不是两份库存。普通生鲜原料与战略罐头不计入“已备餐食”，但不禁止现有自理按安全规则食用；它们不自动被算成厨师已经完成的饭。

按锅/碗下的指定请求仍按成品件数结算，不能把一锅兑换成几份后偷偷改变请求数量。食物的热量、营养和原版身心效果保留，不在本阶段做营养优化或额外Buff。

### 4.3 上下限、在制与多人去重

R2实施初值：低水位L=N×u，高水位H=2×N×u。低于L才激活补餐，达到H停止新开工；激活后处于L～H之间继续补，避免每吃一口就开新锅。N为第4.1节人口。这是备餐强度初值，不是“每人一天两餐”的事实判断。

内部拆开三个量：

- S：真实可用成品的剩余饱食量。
- P：已取得批次/原件额度的在制料理预计可交付量，只用于抑制重复派发；UI不得把P显示为已经可以吃。
- C：已被指定请求/其他合法责任占用、不可供公共餐食使用的部分，从公共供应排除。

去重后缺口为max(0, H−S−P)。C在分类时排除，不能又在公式中重复扣减；P不能同时把同一批的生坯、炉内和待交付各算一遍。P无法核对时保留该批已签发Q作为有限的阻断额度，另列“需核对”，不声称它是预计可交付餐食，也不按0反复重做；调度计算额外扣除这份阻断额度，其余已确认缺口仍可评估。核对完成后由同一批的真实结果更新/解除额度，不由超时自动补做。

每据点一份供餐策略，以稳定policyId和revision生成有界内部补餐需求。复用公共Order/候选机制，只由符合厨师优先级的成员竞争认领；一个厨师不能自己算全据点缺口后直接开工。最先认领批次额度后，其余厨师必须重新读取缺口。

现有最低存量是“阈值＋单次量”触发器，不能静默改成新的通用追目标语义：本稿供餐策略作为专用Provider，在既有协议内签发有限补餐批次，并在每次新批前重验；既有物品补货规则保持原语义。

### 4.4 一批的目标

认领时确定这一批需要贡献的饱食量Q，受未覆盖缺口、原版料理容量、合法食材、携带能力和成品存放能力约束。Q是停止加料的软目标，不授权改原版配方消耗。

原版一份配料可能越过Q，最小合法料理也可能超过小人口H；不能为精确匹配Q改消耗，或仅因产出大于H就拒绝小人口开工。建议按最小合法批次处理，不给H增加未经实测的固定0.50～0.60保底：

- 优先选择产量更接近缺口的可完成小批料理；主料逐次加，原版槽位上限不是填满目标。
- S低于L、确有补餐需求且没有更小可行路线时，允许一个最小合法批次有界超过H，仍受真实食材/容量/有效冷藏约束。额度按预计实际成品贡献申请，不能只预约较小Q而放任多人各做一锅。
- S已达到L，但本周期余下缺口小于所有可行料理最小产出时，结束本周期，等S再次低于L后评估，避免为凑足H开明显过量料理。
- 超额仅限该候选最小合法批次的必要越量。没有物理存放能力仍等待；S达到/越过H停止新开工，已有炉内或持货任务继续收尾。

这不保证“一锅永远足够”：H=1.20、S=1.00仍有0.20缺口，是否再做取决于候选最小产出、已有P及周期状态；不采用“一锅汤通常0.8～1.1”作为未查证的通用产量。

预测必须来自已核对的原版配方/物品读数，不能对真实物品试调用addItem模拟。P预测采用该profile最终可交付状态的有效饱食量，与S同量纲，不把未熟原始值直接当熟食产出，也不在已经修正过的读数上重复乘熟食系数。预测不可可靠建立的profile暂不进入自主供餐白名单，不用虚构产出抵消缺口。熟化或实际加料导致P变化后更新同一批额度，后续批次再评估。

## 5. 日常选择什么料理

首批建议R4：普通锅汤Soup、普通锅炖菜Stew、普通平底锅炒菜Stir fry、普通碗沙拉Salad，以及已核验原料的直接加热。使用当前安装脚本查得的ID和profile，不凭中文名称匹配。

全部候选先过硬门：NPC真实知识/技能、现有宏观工作资格、安全、原件/工具/设备/纯水、合法路径及授权成品存放条件。缺水可以换炒菜/沙拉，不把所有厨师冻在汤上；需热加工的食材不能直接做沙拉来绕过安全门。

候选不做任意加权大评分，按以下有序比较：

1. 优先完成本项目已托管、仍合法且能供餐的未完料理，减少开新锅；不接管玩家私人物品或另一Job原件。
2. 在可完成的料理中，优先能够实际消耗临界生鲜者；仅“锅里可放蔬菜”不等于一定能消耗当前那份临界原料。
3. 选择产量适合Q、原件/厨具和仓储能够承受的候选。
4. 前述相当时，比较额外稀缺资源、加工步骤和行走成本，再用稳定profileId打破平局。

不固定汤永远高于炒菜；不为保持每日菜单轮换而强用耐存物资；不根据未实现的口味/营养系统声称“最好吃”。同一可行方案在一批开工后保持稳定，不能每次观察都换菜。

### 5.1 自由组合和知识的关系

每个profile分别声明原版机制（evolved / craft / legacy / heat）及知识、技能、设备门槛。“自由组合”只说明配料可变，不说明不用学。

日常自主优先选本人已可执行的路线；不会为每个未知菜谱同时生成研习。指定请求缺知识时复用现有实体书研习意图，书籍原件与阅读效果仍归原系统；书/技能不足显示等待，不能跳过学习。普通未知自由料理在支持其真实学习链路前保持不可选。

## 6. 主料：选什么、加几次

### 6.1 合法性先于偏好

每次实际添加前，由当前料理、NPC和具体原件重新走原版可用性检查，再附加本项目限制：

- 绝不使用腐烂、烧焦、污染/有毒、不获授权、被其他任务托管或受既有保护规则排除的原件，即使原版高等级烹饪允许使用腐烂食材也拒绝。
- 纯水门、原版冻结/解冻、需预煮、工具、重复和容量规则全部保留。
- 开罐头仍遵循在线战略储备规则，不因“自动配料”放宽。已确认存在可访问生鲜时不自动开罐；未加载未知不当作已确认全域无生鲜。
- 并非所有食物/液体能加入每种料理，调料也不能只凭物品类别判定。未知模组物品只有通过已核验profile和原版准入才可使用。

### 6.2 选择顺序

在合法候选内按：临界生鲜 → 普通生鲜 → 获准使用的耐存食材。临界门槛沿在线“剩余保质期低于30%”；适配层须区分原版新鲜/腐败终点、无限保质期和冻结影响，未核验的“剩余百分比”不伪装成准确剩余小时。

同一层优先剩余可保存时间更短者；观察不足时保留观察状态，不把未扫到原件当不存在。再比较已经在本批手中、同等可用食材的原版重复惩罚/收益和行走成本，最后稳定itemId打平局。

在同等防腐条件下，推荐避免明显重复惩罚、优先已有合法的不同配料；但不强制“必须三种颜色/两种肉”，不为凑种类等待缺料。

### 6.3 逐次推进

一次只准备并执行下一次原版添加，确认实际消耗、料理结果和知识/角色仍有效后再决定下一次：

观察料理 → 取得合法候选 → 申请本次原件/消耗责任 → 移动/取料 → 原版ISAddItemInRecipe → 核对料理和余料 → 更新Q/P → 继续或进入调味/加热。

原版每次添加的用量保留，不能把一次添加理解为消耗整件，也不能因为同一食材仍在背包就直接释放其未结责任。基底被原版合法替换时记录前后itemId及动作尝试证据，不能按类型随便认领别人的同类物品。

### 6.4 停止加主料

满足以下任一条件就不再追加：

| 条件 | 处理 |
|---|---|
| 实际/可信预测贡献达到本批Q | 进入可选调味，不强塞满原版槽位 |
| 达到原版最大主料次数或当前料理不再允许添加 | 按实际已有料理进入下一阶段 |
| 已完整观察，没有其他可用合法主料 | 已有可完成料理则收尾，空基底不当成成品 |
| 安全、权限、设备或保存屏障要求停止 | 正常收束并保留原件责任 |
| 只剩未知/未加载/未扫完候选 | 分预算继续观察；不是“已确认无料”，也不无限持有身体空等 |

建议R3：自由组合批次至少有一次真实主料添加、正的可用饱食贡献，并达到u/2的最小贡献，才作为正常备餐候选；直接加热现有食物按自身profile判定，不要求虚构加主料步骤。若合法原版小料理天然低于该阈值，由profile明确适用例外供审查，不直接修改原版食物效果。不能为达阈值吃掉受保护物资；材料不足则显示“食材不足以备餐”，现有安全自理不受阻。

## 7. 调料：可选改善，不是开工门槛

调料由原版可添加列表及isSpice/脚本属性判断，并区分“被该料理当主料使用”和“被当调料使用”的实际动作，不能只按盐、油等中文名字硬编码。

建议R3：完成主料后，最多执行2次不同合法调料添加；每种是否重复仍以当前原版isSpiceAdded及准入为准。上限用于控制耗材与操作成本，是建议值，不宣称最佳口味。

规则：

1. 缺调料就直接继续，锅里已有合格食物不因缺盐卡住；不为调料等仓储卸货或发动前置制作。
2. 仅使用本批已取得的调料或当前可直接交互的授权容器中的调料；不为可选调味新增独立取料寻路段，没有候选就跳过。这样不需要另定“附近几格”的隐性门槛，扩大主动寻调料范围需另经审查。
3. 已核验能带来正向原版效果、又不与禁用/安全规则冲突的调料才自动用。无法可靠解释用途的模组调味品不盲加。
4. 不为了多样性把所有调料轮流加一遍，不自动开战略罐头或稀缺材料包装来取得调料；玩家明确的指定配料意图不能被自动换掉。
5. 每次添加走相同的部分消耗、基底替换和回调核对协议。当前原版Food型useSpice除改变心情/无聊外，还转移热量、蛋白质、碳水和脂肪并消耗源物品，不能概括为“只影响心情”。成品饱食等效果读取实际原版结果，不人为剔除所谓调料贡献或额外虚增Q；若某调料不改变成品F，自然不增加供餐量。本模组不额外发放口味Buff。

## 8. 指定成品请求

请求表达“做什么和多少”，不绑定NPC；烹饪知识由被选NPC重验。固定配方不全都需要学习，自由料理也不保证无门槛。

| 请求类型 | 执行规则 |
|---|---|
| 指定固定成品，如已适配面包/蛋糕路线 | 固定输入和合法替代遵循原版；缺可制作前置时复用现有BOM规划；不自行发明新的全配方搜索器 |
| 指定汤/炒菜等自由料理 | 指定料理类别和成品件数，默认由自主规则选配料；可沿原版入口保留玩家已指定的合法配料意图，不新增逐锅必填表单 |
| 指定菜品最低存量 | 沿现有阈值＋单批量规则；与日常供餐目标共享已交付事实，避免重复补同一份食物 |
| 缺知识/技能/书或设备 | 请求可等待；状态明确，不伪装正在制作，不占身体持续空转 |

请求与日常供餐共用厨师工种和公共认领；请求默认在同等可行条件下优先于普通补餐，但已有炉具/原件收尾优先，危险及紧急自理仍更高。公共餐食低于最低储备且指定请求会长期占用唯一厨师时，供餐候选具有可解释的缺餐紧迫度；不以普通工作分数抢占生存等级。

当前批次到安全边界再切换，不因玩家新点一份蛋糕就遗弃热汤。同一实际产物只结算一个请求：已交付、不再被专用责任占用的餐食可满足公共储备；仍为请求保留的产物不重复算公共可用。取消请求保留已发生加工与待归还/炉具责任，不能删除记录冒充取消成功。

首批支持清单由profile给出准确recipe ID、输入输出及原版动作链；未适配菜品显示“不支持自动执行”，不保证所有食谱都能委托。评审推荐面包作为首批固定成品核验候选，本稿采纳为工作包A优先查证对象，不据此认定已经适配。

当前安装版Base.MakeBreadDough为NeedToBeLearn=true的AnySurfaceCraft，包含搅拌工具、保留碗、擀面杖、面粉、盐/调味盐、酵母与液体水输入。Base.BreadDough普通脚本声明可烹饪，当前读取段未声明ReplaceOnCooked变成Base.Bread；“面团烤熟”与“替换成另一实例的面包”不能混为一谈。先核对完整引擎/回调及参考goal的最终成品定义，再锁定请求名称、输入输出和工具要求，不以“材料比蛋糕普适”代替可行性证据。

## 9. 物理烹饪、设备与成品

共享步骤为：取料/厨具/纯水 → 必要前置加工 → 主料循环 → 可选调味 → 必要热加工 → 取出/关火 → 交付 → 工具余料收尾。沙拉等不需热加工时跳过炉具，不强制找台面或炉子。

原版旧配方ISCraftAction、B42制作ISHandcraftAction、自由加料ISAddItemInRecipe和温度过程分别适配，不能放宽当前ProductionRecipe对部分消耗、液体和回调的拒绝来假装全部兼容。当前JAR已核实hasMinimumWater检查Water类别和getFilledRatio，0.9是原版最低填充比例，不是0.9升；纯净水资格另按本项目政策检查。复合流体与动作细化见第21节。

建议R4首批热源仅普通有电IsoStove；只选已获授权、原来关闭、没有玩家占用/外来料理的设备。一个炉具同时一个批次、一个唯一监管责任。已有合法原版炉膛容量仍需实际检查，不能按“一个批次”绕过容量。

使用ISToggleStoveAction时，开/关是期望状态命令，实际执行前重验当前状态；Toggle不是幂等set，重复和过期回调不能再次翻转。原版若缺可靠的动作前重验接缝，必须先验证最小适配，不能裸调Toggle补救。

熟度根据真实isCooked、烹饪进度、烧焦及已核验原版替换结果判断。预测只决定何时复验、是否可安全离开，不直接制造熟食。冻结、断电或未升温给具体原因和复验条件，不通过固定等待时间判定成功。

冷藏是在线需求要求，建议R5保持：新的备餐必须有有效、授权、可达且有容量的冷藏交付目标。没有时换目标或等待，不以冰箱名称/贴图代替当前有效制冷。全图断电后若据点也没有其他有效供电冷藏，则自主新备餐处于“无有效冷藏”的预期阻断，不能误报为寻路/调度故障；有合法替代电源和冷藏则照常重验。这不停止已有炉内取出/关火、持货归还和未结责任恢复。首批不默许普通箱算冷藏，无冷藏现做现吃改变需求边界，需单独批准。

临时断电/满箱不允许遗弃炉内食物：先安全停止自有加热、取出并保留待交付原件；重找冷藏目标。无法冷藏显示“已完成，待冷藏”，S不计入正常有效储备，P保留同批去重状态并阻止因相同设施故障无限开新锅。

锅/碗如果仍承载食物，就是成品原件的一部分，不能把空锅当工具立刻归还；只有原版实际产生空容器后才按原件事实处理。刀具等耐用工具、未用完调料/原料沿既有授权归还选路结清，不复制或重造替代品。

## 10. 做出来之后，居民必须能吃

消费继续由SelfCare需求、自主选食和原版ISEatFoodAction负责；厨师不直接给居民扣饥饿，也不另造“吃饭完成”收益。

当前自理按比例吃食物并读取剩余getHungChange，但SelfCareResources会排除getRequireInHandOrInventory非空的食物。因此P4完成条件包含：对首批成品核对并补必要的原版进食工具适配，保证做好的汤/炒菜进入现有合法选食路径。改动仅限新成品消费接缝，不重写另一AI的睡眠/阅读或身体协议。

共享锅在某NPC取用/进食时仍只有一个原件责任人，其他人不能同时从同锅消费。吃到满足后按原版保留余量与容器，必要时沿现有责任归还；S只在原件回到公共可用状态后更新。两个人吃一锅不靠虚拟份数、两个并行Claims或删除复制实现。

首批不引入自动分碗、洗碗、摆桌、居民走近厨师点餐或厨师逐人送饭。如果某profile离开分碗就无法与现有自理可靠衔接，先报告这一技术依赖，不能一边延期一边把该菜标为已可供餐。

## 11. 炉具义务、中断与接管

炉具Duty独立于身体Session，以设备/批次为锚点；关联Order、Job、原件、唯一责任人、开火归属和下一检查条件。监督服务只产生责任候选，不在后台回调直接操纵身体/远程关火。

| 情况 | 约束与预期行为 |
|---|---|
| 普通新工/切换菜品 | 当前原件与炉具先到安全边界；不能遗弃热加工来追逐新评分 |
| NPC吃喝/睡眠 | 正常请求中断；优先确认可达合格成员接管，或在可安全操作时关闭自有炉具并保存恢复点 |
| 即时危险 | 按现有身体停止协议撤离，不要求冒险返回；保留无人监管风险，不能承诺零烧焦/零火灾 |
| 玩家放入食物/切换设备 | 重新判断控制归属，禁止无条件关掉玩家设备；取回本批原件须权限和实际动作允许 |
| 改厨师优先级/调驻/死亡 | 禁止新普通批次，但未结责任不能因工种关掉就消失；候选恢复或明确接管 |
| 设备拆除/未加载 | 区分已确认失效与不可观察，保存原件/效果事实，不能把未加载当已关火或空炉 |

接管逻辑：提出接管意图 → 重验旧责任/设备/原件/身体状态 → 预约接班者 → 唯一提交责任与Claims关联 → 允许接班者经自身Session执行。预约者不等于第二责任人，重复/过期回调不提交第二次；失败保留原责任与明确等待，不用超时删原件Claims。

首批等待加热时不领取无关远程普通工单，可继续有界观察/安全自理；不是设计每日班表。未来是否利用安全热加工窗口做邻近任务，须以到安全点时间与实际烧焦窗口测量后另行决定。

## 12. 实际效果与保存恢复

动作契约固定五要素：启动条件、效果发生时机、停止处理、成功证据、恢复方式。每次转移/加料/开关有稳定attemptId，绑定世界、批次、Job与Session代次。

加料之前捕获基底/配料真实状态和原版结果类型约束；之后确认原版实际余量、基底前后关联和所在容器。原版允许合法替换基底，本模组不删除重造。单凭完成回调、物品同类型或库存增减不够唯一确定效果时，该步骤进入核对，不重放或换料再试。

停止可能已经部分用料，取消不回滚食物数值。旧Session回调不能继续派动作或释放新声明，但它已发生的物理效果仍归原尝试记录。身体停止、效果已知性、设备可观察性分别保存。

正常保存沿既有屏障捕获身体、批次、物件链路和Duty；OnSave不推进加料、不异步等待关火。加载后先恢复任务/Claims/义务，重验真实料理、炉具和容器，再产生恢复候选。旧“打算开火”不等于实际已开，新鲜食材也不能按时间差直接变成熟食。

保存期间世界时间是否暂停由原游戏决定；业务停派不等于炉内停止加热。已确认的“原件仍在炉内且设备运行”恢复为监管责任，不强行标UNKNOWN，也不当作已完成。原件去向不明才隔离相关资产；已确认安全的撤离/自救仍允许。

不承诺强退/跨文件磁盘原子性、未加载区域后台烹饪或零损失。旧格式支持沿当前项目决定；新增字段须版本化、对当前有效记录有明确读取/拒绝/核对边界，不为本阶段全面迁移旧NPC或清除旧未知任务。

已接工位事实为payload.station（稳定设备ID/位置、leaseId、ownerId、RESERVED→ACQUIRING→ACQUIRED→RELEASED），使用现有craft-surface资源键；工位责任与原生UsingPlayer分别核对。已观察落地或去向不明的新原件仍持有声明，分别记WORLD/UNKNOWN，不冒充已入包或已交付；未核实原件状态不自动移动或重做。具体实现边界见同一专题证据。

首批数据结构不依赖单厨师；但不借本轮增加maxWorkers做同锅流水线。多个厨师可竞争不同独立批次，设施与缺口必须唯一裁决，单批配料原件同一时间仅一个实际执行者。

## 14. 观察、性能与失效

供餐库存、人口和设备按据点共享观察。库存消费/转移、烹饪完成、成员变化、工种优先级、权限、设备电力与容量变化只失效相关缓存。没有可靠事件的原生温度/老化/电力读数用有界错峰复验，不声称纯事件驱动。

原件遍历/跨箱聚合复用既有Java批量读取或在有证据缺口时扩展；Lua不写多NPC×所有物品×所有菜谱嵌套重扫。每个profile保留增量游标和全局预算，未扫描完为观察中，不误报缺料；UI只消费只读快照，关闭后业务继续。

炉具监管预算独立于普通发现休眠。临近熟成/烧焦窗口提高检查优先级，开工前验证当前倍速、途程和检查能力足够；固定现实500ms只是参考项目事实，不能照抄为本项目安全保证。没有足够监管能力时不新增热批次，保留冷菜/等待候选，不远程偷偷取出。

不预承诺设备/NPC规模或CPU预算。记录必要的共享扫描、规划与单次监管耗时，性能检查随真实风险运行，不能以新增Java类宣称降耗完成。

## 15. 产品入口与等待原因

人员矩阵增加实际接通的厨师列，0～4与既有工作规则一致。启用厨师后日常供餐不要求再设每道菜工单；据点显示自主供餐状态、按人数的当前目标与暂停入口。具体供餐策略UI只展示玩家需要理解的目标，不露内部Q/Claims等技术字段。

工单监控区分“日常备餐”和指定菜品，显示备料/加主料/调味/烹饪/待交付/收尾；共享餐食状态用可解释的饱食储备，悬停解释按剩余量估算，不标未经实测的“够吃一天”。

主要等待原因包括：无厨师可用、餐食充足、观察中、缺主料、纯水不足、缺厨具、无可用炉具、无有效冷藏、指定菜待研习、设备被玩家使用、待归还、原件需核对。等待状态不常驻重复Say，不逐次弹窗；CN/EN成对，沿既有组件和快照生命周期。

本轮不另建独立厨房/菜谱黄页/物流面板；具体UI布局在实施计划中复用当前组件，不在本设计中重做其他AI正在修改的页面。

## 16. 场景预期（设计目标，均未实机验收）

| 场景 | 预期 |
|---|---|
| 4名所属成员、部分外出，菜和肉充足 | 全部4名存活成员仍计入；厨师提前补共享饱食储备，不分别补满每一种菜 |
| 1人据点，最小合法料理超过H | 确有需求、无更小路线且物理存放允许时做一份最小批，按实际预计贡献去重；不因锅型大而停工，也不把全局H抬成固定锅容量 |
| 两名厨师同时空闲 | 先认领者占本批额度，后者重算缺口，不各自做足整个据点目标 |
| 有一锅被吃了一半的合法汤 | 按剩余量计，锅仍是同一原件，不算整锅也不算零；在别人进食中不重复计可用 |
| 无纯水但有适合炒菜的原料 | 合法时选炒菜；没有可行路线才等待，不为做汤建烧水流水线 |

## 21. 共享配方链与原版工序：0.4实施契约

### 21.1 来源、取舍与范围

用户要求保留家具索引、复用现有配方链，同时支持普通配方、自由加料、需要时取水和炉内加热。本节细化这些机制，不新增工种、自动建造设备、采奶、洗碗、烧水或解冻流水线。

本轮已读取AGENTS指定的[唯一需求](https://docs.google.com/document/d/1aTOBrzZvh_iCDkv045HNAV13i7vNf7OHk6E_sE7TWNM/edit)，并对照用户所指的[新版机制文档](https://docs.google.com/document/d/1Z6ZLMTmBBIAEY_4Nbh_bDvE0c9vHjfZGXbeyLvOM6tk/edit)。后者本轮读取的修改时间为2026-10-26T16:43:06.002Z；它与AGENTS指定地址不同，作为本轮评审参考，不擅自替换唯一需求入口。人口、有效饱食储备、纯水和冷藏等已确认决定继续有效。

| 路线 | 得失与决定 |
|---|---|
| 厨师独立实现一套配方链 | 初期少碰生产模块，长期重复解析、原件和恢复逻辑；不采用 |
| 把所有工序强塞成普通Recipe节点 | 表面统一，但原版加料会替换基底、液体会逐步转移、炉内加热由世界推进，执行语义不同；不采用 |
| 共享配方事实与有界依赖规划，按原生机制适配执行 | 推荐。保留现有生产能力门槛，逐项补齐流体和工位接缝；增加少量明确契约，避免复制第二套生产系统 |

维持两种制作机制：普通配方与自由加料。取料、取水、移动和加热是工序，不新增第三种菜谱系统。已有物品可直接加热，但不是靠虚构Recipe实现。

参考项目ProjectRemnants的当前根JAR已对照：其RecipePlanner也拒绝requiresSpecificWorkstation，不能拿它证明搅乳桶已适配；只借鉴阶段链与水容器解析。关键行为以下述当前安装版Lua/JAR为准，源码查证不等于NPC实机验证。

### 21.2 三层职责，沿用当前任务与账本

1. **读取事实**：从当前注册表、CraftRecipe/InputScript及EvolvedRecipe读取原始IO、知识/技能、工位、回调和产物规则。与“本项目是否能安全执行”分开，不再让不支持执行的配方直接消失于查找结果。
2. **规划依赖与工序**：ProductionChainPlan保持只读快照的纯计算，复用有界BOM、工具复用和候选分配，增加有类型的输入槽及前序结果引用；不操作NPC、原件或工位。下游原生机制适配展开Move/Fill/Add/Heat等工序。普通配方生产边继续消耗现有深度预算；物理工序不增加BOM层级，但受独立工序数/搜索预算约束。不存在可执行路线时返回具体阻断，不发半条假任务。
3. **执行原生动作**：共享可复用的制作/流体/工位适配，在现有Cooking Job与唯一Session内推进；不从Cooking中启动另一个Production身体控制器。炉具Duty仍归同一Job。原件、设备与容量责任继续由现有LaborStore/LaborClaims裁决，不另建库存或租约权威。

当前ProductionRecipe把读取与可执行筛选混在一起，Catalog生产索引也仅覆盖它允许的配方；不能只删除拒绝分支。先保留普通生产现有行为，再拆出完整事实读取与显式能力判断。未知回调、特殊输出或机器处理器仍可被发现，但不得自动执行。

下文契约名称是本项目拟议数据，不是原版API。持久记录只保存版本化普通数据：recipeId与定义签名、原版IO索引、数量及单位、实际itemId/facilityId、前序输出槽、Job/attempt/Session代次。原版对象运行时重新解析，不保存userdata或Lua谓词；定义变化则重新审查，不能拿旧输入映射直接执行。

### 21.3 复合输入槽：容器与其内部流体必须一起分配

当前原版`recipes_butter_churn.txt`定义`Base.churn_butter`：`item 1 [*]`下挂`-fluid 5.0 [CowMilk;SheepMilk] mode:mixture`，输出`Base.Butter`，Tags为ChurnBucket，category为Farming。Farming是分类，不能据此排除厨师；`[*]`也不等于任选空容器。

| 拟议输入事实 | 绑定与验证 |
|---|---|
| 原始父槽 | 保存CraftRecipe的IO索引；整件数量、Keep/Destroy等保留原版语义 |
| 子资源要求 | 保留consumeFrom父子关系、Fluid类型、原始流体过滤、mixture模式及5.0体积；不得拍平成独立库存数量 |
| 具体分配 | 父槽绑定实际容器原件，子槽检查该原件内真实混合物；同时通过原版canUseItem/isFluidMatch与最终制作合法性 |
| 数量单位 | 整件数、食物用途量、流体体积、填充比例分开；不把5.0当5件牛奶，也不把0.9填充比例当升 |
| 效果证明 | 分别观察容器存在/归属、液量与组成变化、工具保留及真实产物；Keep不代表内部牛奶不消耗 |

当前InputScript初始化会给consumeFrom父槽默认Keep，但显式Destroy例外，不能统一强改保留。当前CraftRecipeData.setManualInputsFor按Item父槽接收ArrayList并做实际接受判断；绑定仍以原版IO映射为准，不给Fluid子槽硬塞一份物品清单。

首条黄油原型要求单个容器具有至少5.0奶液，并满足原版流体过滤；当前固定父槽item 1不可直接绑定多个小瓶拼量。不足时返回MATERIALS_UNAVAILABLE，未经验证不自动增加倒奶拼装工序。不按某个桶的类型白名单代替真实液量与原版资格，也不把该限制泛化到所有流体配方。

### 21.4 前序结果绑定：继续用真正产出的那一件

用“前序步骤＋输出角色槽”描述逻辑依赖；步骤生效后，绑定本次实际观察到的一个或多个itemId、位置和状态，随后才分配给下步。原生输出类型/回调规则与观察结果共同决定角色，不能从全仓库搜一个同类型物品冒充。

自由料理`ISAddItemInRecipe.complete`把`recipe:addItem(...)`返回值赋回baseItem，合法添加可能替换基底。因此链路应为“锅槽→本次加料实际基底→下次加料/Heat”，不能从头到尾缓存最初空锅ID。原件未消失就保留其责任；出现新件先认领并核对，结果不明时同时保留相关新旧原件，禁止按类型补造。

普通制作也不能只看背包数量差。`ISHandcraftAction.performRecipe`先执行制作、取得created outputs并addOrDrop，再调用OnCreate和processDestroyAndUsedItems。必须包住完整实际效果区间，捕获最终状态。首批用容量预检降低落地概率；若实际仍落地或回调异常，只记录确认位置/原件，不能声称已入包或盲目重做。

工序中的“中间料/可加热/最终交付”由当前目标链和实际结果决定，不按全局物品类型硬编码BakeReady。某面团存在后续配方，不意味着任何目标都禁止烤它；当前步骤仍需它作输入时，也不能提前烤掉。熟度读取原版状态，不自行把面团改造成另一类型面包。

### 21.5 家具索引：提供候选，执行时再次核验

保留每据点共享的轻量设施索引，记录世界/楼层/位置、可重认的设备身份、已观察组件与能力、当前观察代次。查询按能力缩小候选，再按权限、路径、占用和距离选址；“按能力查表”不等于O(1)找到最近可用设备。

索引随已接入的对象变化、加载/卸载失效，并以有预算的低频补查修复遗漏。未加载记为不可验证，不是已销毁。原版未证明存在的事件不写成现成接口；具体订阅入口实施前逐项查证。避免每个NPC各扫一次世界。

ChurnBucket实体含`CraftBench`组件，组件`Recipes=ChurnBucket`。查询读取原版CraftBench提供的recipe query/recipes，再以实际Recipe合法性复核；不能说实体“继承CraftBench”，不能把其建造配方当生产配方，也不按家具中文名猜匹配。AnySurface/InHand按各自原生要求执行，不强制所有料理占一张台面。

物品绞肉机优先按目标配方InputScript的工具/标签/Keep要求选择真实物品；若具体模组使用家具、ResourceFluid机器槽或特殊处理器，则走相应能力判断。尚未给出绞肉机模组及配方定义，本稿不虚构物品ID、动作或“全部模组即插即用”的结论。

### 21.6 特定工位的完整占用协议

原版`ISHandcraftAction.isValid`在存在craftBench时检查`isoObject:isUsingPlayer(character)`；原版实体窗口构造/关闭时设置/清除UsingPlayer。NPC只借用必要原生占用语义，不打开UI，也不复制窗口无条件清空占用的退出实现。

执行顺序：

1. 重验设备原对象、组件、Recipe能力、权限及可达性；由现有仲裁取得工位责任。移动继续交给唯一Driver。
2. 到位后确认无玩家/其他执行者占用，带Job、attempt、Session代次设置并读回UsingPlayer。此步骤须早于入队后的首次有效性检查，不能等action.start才补。
3. 通过`HandcraftLogic.new(character, craftBench, isoObject)`配置当前recipe、输入容器和原版IO索引的manualInputs，调用canPerformCurrentRecipe形成实际应用缓存，再核对输入确实来自本次授权原件。原版手工输入设置失败可能只记日志，本项目不能据此继续自动搜包。
4. 已持久记录提交意图后，才允许原版制作效果。单人实际生效点是perform调用performRecipe；complete只在isServer分支调用制作。不能照搬只包complete的加料/Toggle适配。
5. 停止或完成后核对真实消耗、产物与动作退出。仅当世界、原对象、持有责任的Job/Session代次、原生使用者仍都属于本次执行，才清除UsingPlayer；确认物理占用解除后释放逻辑工位声明。

旧回调即使遇到同一个NPC，也可能属于上一Session，不能清掉新任务占用。动作退出和现有会话撤销/最终退出生命周期共用幂等清理入口；不依赖原版动作stop自动清空UsingPlayer，也不虚构OnSessionAborted等现成事件。加载后依据真实对象和现有责任恢复；缺乏原使用者已退出的证据时保留待核对，不按坐标或超时强制解锁。纯逻辑租约超时不证明物理动作已停，进程崩溃也不能靠退出回调保证清理。

GenericCraftStart/资源槽机器不自动纳入ISHandcraftAction适配。CraftBench存在不代表所有加工器共用同一执行路径；普通ItemContainer搬运也不能冒充机器ResourceFluid输入动作。

### 21.7 取水与倒液体：允许真实部分进度，禁止重放整份

当前安装版两条动作都有渐进效果：

| 原生动作 | 已查实际行为 | 本项目适配要求 |
|---|---|---|
| ISFluidTransferAction | source/target是ISFluidContainer包装；单人update按进度Transfer并sync，complete补剩余量；stop不倒回 | 保存两端原件/对象身份、初始量与组成、目标量；首个update前建立效果屏障；结束/停止读取实际差额 |
| ISTakeWaterAction | 单人update调用updateUse，complete再补足；构造按容器余量、水源可用量和负重计算waterUnit，没有任意目标量参数 | 以原版实际计划灌水量与实际结果为准，不宣称可精确只灌0.9锅；重启从当前容器余量重算，不沿用原请求量 |

同一次倒液体是一条attempt，不能每帧签发新动作或做完整持久写盘。首次不可逆更新前记录基线与授权，运行中保持当前原生活动和有界观察；结束、停止或恢复边界做完整核对。受控运行中的“效果可能发生”不应立即被通用叶子误判失败，仍按现有动作状态返回Running。

当前水源耗尽则将该候选标记为本次观察下不可用，保留锅内实际进度，按路径与搜索预算寻找下一个授权纯水源。无候选就等待，不在空水槽原地无限重试，也不无限扩大范围；水源状态或观察代次变化后可重新考虑。

取消时保留已倒入部分。可证明的部分结果记为实际进度，余量是新动作的依据；无法证明两端变化归属时保留相关原件待核对，不能恢复旧液量、释放后重做整份，或凭液体总数相同宣布完成。有限容器可比对两端变化；供水设施的补给语义必须按实际对象适配，不能凭“水龙头”名称假定无限或强套两端等量守恒。

汤/炖菜先选已有合法纯水锅，必要时再选择已适配的合法水源/取水动作。当前EvolvedRecipe.hasMinimumWater要求Water类别且getFilledRatio达到minimumWater；项目额外限制纯净水。观察达门后才自由加料，不为完成一锅自动新增烧水、净化或洗锅机制。冻结/预煮资格继续沿原版过滤，未知能力阻断，不静默扩范围。

2026-10-28实施细化：便携水源只从当前NPC与授权仓储读取真实纯水容器，纳入同Job的追加原件来源清单，使用后归还同一容器；不把倒水能力用于自动拼奶或绕过固定配方的单父槽限制。ISFluidUtil.validateContainer是玩家UI库存校验，NPC适配仅替换本动作的原件资格与构造字段/启动展示，不全局改写它、不借用玩家背包；液体生效仍调用安装版ISFluidTransferAction.update/complete。两端组成与体积按实际原件核对，渐进COMMITTING仅在本会话保留当前受控操作，停止边界再核对；脱离会话的UNKNOWN绝不续倒。

外接水槽使用只读WaterReads桥接读取原版已选中的实际externalWaterSource与isWaterInfinite事实，不用“附近找到一个桶”代替原版缓存源。有限外接源的水槽和背后原件使用同一Claims图，多个水槽指向同一桶时互斥。当前原版会把外接源中的TaintedWater转为Water、其他成分原样转移，因此只接受已完整读取为Water/TaintedWater的上游组成，并要求目标实际增加纯净水；本模组不另写净水效果。取空后即使原版自动切换缓存，当前动作也只核对已声明的旧供水端，下一次动作重新声明新源。桥接不可用、上游不在授权据点、组成未知或混入其他液体时阻断，不依赖主液体名称判断纯度。

### 21.8 热加工与完整链实例

**黄油链**：找到可执行的Base.churn_butter → 按父子槽绑定真实奶容器 → 找到原版确实提供该Recipe的ChurnBucket → 认领/移动/设置原生工位占用 → 精确手工输入 → 原版制作 → 核对奶液减少、容器保留或销毁、实际Butter原件 → 交付与条件释放。它验证复合输入和工位接缝，不额外承诺自动采奶/建桶。

**自由炖汤链**：绑定真实锅 → 必要时原生取纯水 → 重验最低填充比例 → 逐次添加真实主料并更新基底绑定 → 可选调料 → 放入已认领普通通电IsoStove → 按原版热度和熟度观察 → 取出/条件关火 → 冷藏交付/器具收尾。沙拉跳过热加工；物品可烹饪只是能力，是否应热加工由当前链目标决定。

热加工仍是世界温度过程，不伪装成定时Recipe回调。原版Food熟化速度依赖温度等状态；预测只用于安排下一观察，不直接写Cooked。首批保留近炉监管、不接无关远程任务；不存在“瞬时必起火”或“绝对零火灾”的已验证保证。设备被玩家关闭后按已有责任安全取出，不自动重新点亮。

正常熟成优先先取出、后条件关火。取出受阻或紧急撤离时允许先关闭自有设备，但保留取出责任与余温风险，关闭不等于结清。开工容量按实际器皿、液体增重、配料与中间产物计算，不增加固定空闲承重8.0的玩法门槛；无法可靠估计时阻断相应能力。

### 21.9 适配边界、实施次序与审查出口

| 原版/模组定义 | 发现与执行边界 |
|---|---|
| 已支持的普通物品输入/工具配方 | 继续复用现有生产解析与动作，保持现有拒绝保护 |
| 原生父槽＋consumeFrom流体 | 完整读取；补齐精确绑定、部分消耗与原件观察后，按通过核验的形态启用 |
| 原生CraftBench配方 | 自动发现候选设备；原生占用/输入/退出完整核验后启用 |
| EvolvedRecipe自由加料 | 用原版资格与addItem结果，接共享资产和前序结果绑定 |
| 特殊回调、自动处理器、机器资源槽、未知输出 | 能解释缺少哪种适配；不因配方可见而默认可执行，按机制注册适配 |

实施顺序固定：先拆清事实读取与执行能力，并加入复合槽/输出绑定；再用黄油打通一个特定工位最小闭环；随后接纯水渐进动作与汤链，最后合入共享选菜、Agent、Duty恢复与公共派发。保留已有生产链预算与普通配方行为，不进行通用制作系统重写。

验收只围绕关键接缝：父子槽不得误选空容器；原生手工输入不能偷换未授权物品；加料替换后的下步必须使用真实新原件；中途取消取水不复制液体；旧Session退出不清新占用；产物落地/回调异常不重放；普通生产旧路线不被扩大放行。基础实现及宿主检查见[同一专题证据](../../reviews/2026-10-26/p4-cooking-foundation.md)，以上新组合均未实机验证，不把底座模块或替身测试当作已启用功能。

用户已确认按上述架构开工。核心设计保持“同一条有界配方链、按原生机制执行、按真实结果续接”；不把评审建议中的无条件释放、超时清账、全局禁止烘烤或新增处理流水线写入实施范围。实现和原生验收分开记录。
