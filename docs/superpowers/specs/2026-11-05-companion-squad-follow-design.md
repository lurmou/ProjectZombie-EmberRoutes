## 1. 已确认方针与实施范围

用户本次确认：可维护性、已确认需求下的可扩展性与性能优先；额外安全工程靠后。业务记录和派生状态以最终一致为目标，正常执行仍须保证唯一身体执行者、物理效果不重复提交。故障无法可靠核对时，明确停止相关业务或要求重载最后存档；不承诺任意崩溃下零损失。

只做单人；保留既有联机适配，不为新功能设计联机接口。只实现当前正式契约，无旧接口别名、旧格式迁移、双轨读写或兼容 fallback。多 NPC 使用稳定 npcId，不能把生产跟随做成单例。

本轮启动范围为基础跟随链的设计与实施准备。首期软件交付目标：最多三名同伴的显式槽位、连续跟随、过弯与门口让路、楼梯通行、WAIT/RETURN、自理交接及正常保存恢复，组成一个可操作闭环。热路径接线须先做当前引擎原型，不能仅靠数学模型承诺同帧效果。

车辆同乘、完整战斗和完整 HUD/轮盘按独立交付推进。用户本轮进一步明确：ProjectRemnants 的小队同伴系统（跟随、战斗、载具、指挥、自理）是最低功能对标目标，首期三人不代表最终人数上限。参考正式小队能力须逐项对照并纳入后续交付，不因分期而永久省略；建筑搜刮已有正式链路线索，列入对标，战利品一键卸货等仍按参考审计结果及明确需求确定。没有双方同场景实测，不宣称功能/性能已经追平或人数上限已经超过。未修改在线唯一需求。

## 4. 一致性与失败边界

| 对象 | 要求 | 失败处理 |
|---|---|---|
| 身体授权、Session 代次 | 执行时唯一且有效；停止前禁止新派发 | 走现有停止确认；不清空内存冒充释放 |
| 物品转移、消耗、攻击效果 | 以世界原件和实际效果为准，不盲目重放 | 结果不明停止该操作，保留已有责任；必要时提示重载 |
| 工单进度、库存索引、HUD 快照 | 允许滞后，按已有事件/有界刷新收敛 | 标脏并重新观察；UI 不是第二权威 |
| 正常保存与恢复 | 保存标量意图及现有责任，重建会话和导航缓存 | 不恢复旧原生队列、Key、闭包；不支持格式先拒绝且保留原数据 |
| 崩溃或跨文件提交失败 | 不新增任意崩溃一致性保证 | 明确故障并重载最后存档；不新增补偿事务平台 |

最终一致必须有收敛依据，不能将“转移结果未知后再执行一次”称为收敛。现有业务资产契约不在本轮全库放宽；只限制本轮新增安全工程的复杂度。

## 5. 执行架构与选择依据

采用现有 Membership → 分级仲裁 → TaskRuntime → TaskController → Driver/Java 身体出口。跟随与据点按领域分文件、按数据特征安排节拍，不创建第二个仲裁器或身体执行权威。

比较：保留现状不能满足连续伴随；仅提高 Lua 重寻路频率会放大 JNI、table 分配和完整停止成本；复制参考独立控制器会破坏唯一身体协议。推荐在现有 Java 身体出口内增加会话受控的持续跟随能力，Lua 保留命令、成员与自理交接。是否减少耗时必须由原型和后续游戏采样验证。

持续跟随与完整停止分开：同一会话内可更新目标/移动意图，不借每次更新执行 StopAllActionQueue；WAIT、自理抢占、保存、死亡和退场仍完整停止。新会话不得继承旧避让、旧寻路回调或旧 Key。

高频工作直接读取已绑定角色和小队成员，不扫描全 NPC、全容器或全建筑。队长轨迹每队共享一次；跟随者只保存槽位、路径游标、避让侧与进展状态。主线程内更新，不引入线程池、通用调度框架或持久化导航账本。

## 6. 连续移动、轨迹与通行

- 编队由玩家显式指定槽位，最多三人；不按装备自动重排。开放地形使用需求中的侧后方约 1.5 格扇形；窄路临时列队，恢复开阔地形后回到指定槽位。
- 优先采用当前可达的编队目标；需要转弯时沿队长历史路程选中间目标；目标或下一段不通行时交由原生寻路和已适配交互处理。导航算法后备路线不属于旧契约兼容 fallback。
- 轨迹使用固定容量环形数组是本项目候选实现，不冒称参考原实现。按累计路程选点，保留急转弯；容量需覆盖三人队列和原型采样密度。换层、队长切换或位置跳变时断开片段，不能跨楼层线性插值。
- 历史不足时走当前可验证的目标/原生寻路，不从墙外强拉，也不永久 BLOCK。路径不可达可有界重试并给出原因，不能无限提交相同失败路线。
- 输入镜像只提供尽早同向响应的提示，位移服从原生碰撞与动画。引擎更新顺序和动作适配未实测前，不把同帧响应列为已实现。
- 追赶采用进入/退出滞后，结合负重、受伤、姿态和通道约束；不无条件强制 Sprint。禁止视距内传送、关闭碰撞或直接写坐标纠偏。

避让采用短暂固定侧、局部可通行探测及可观察进展。前进/侧移均不可行时，检查后方退让位置；玩家停在门口时不反复顶门。两名随从竞争同一窄口时作局部次序协调，不为所有世界门建立持久锁。

楼梯先复用原生跨层路径；队内排队不能限制玩家自由通行。按实际时间和位置进展判断停滞，不能直接把参考帧数当毫秒。脱困方向须验证通行，失败保留可诊断状态，不传送、不穿墙。

## 7. 背包与自理

普通随行物资进入随从背包即是最终交付，不自动产生入仓工单，不因进入据点自动收缴。玩家用原版 ISInventoryTransferAction 双向取放，执行前仍检查距离、容器有效性和原件位置。

物理转移期间的短期协调、已借用的据点工具/材料责任与普通战利品分别处理。MembershipService.advance 当前会因 TOOL_CUSTODY 阻止 FOLLOW，这个既有契约不因“自由背包”被绕过。需要改变它时单独说明交接后果，不按容器整体宣告零 Claims。

沿用既有 SELF_CARE、MedicalCare 与 TaskResume 接缝；只有当前物品不受其他业务托管时才可消耗。饮水走对应原版饮水适配，不能用 ISEatFoodAction 代称全部吃喝。安全间隙由已有威胁和动作条件判断，8 格只是候选阈值；不能据距离单值保证安全。

## 9. 保存与生命周期

Membership 是归属和宏观命令权威；Companion 意图记录用于业务恢复，不能倒过来覆盖较新的成员命令。队长身份使用稳定 ID。WAIT 停止跟随并保持原地上下文；RETURN 走真实返回任务，抵达后再交接据点。

新增槽位的存放位置、正式格式及全部读取方在实际接线任务一次确定，先核对现有格式门禁；禁止随手把原稿字段加入 format=1 并默认为兼容成功。本轮设计更新不修改任何运行存档或格式门禁。

运行缓存只保存当前绑定世界/会话；停止完整注销持续跟随，释放小队共享缓存引用；最后一个跟随者离队时可清除轨迹。保存不等待未来 tick；恢复复用现有入口建立新会话，不自行清理其他业务队列。

## 11. Task B 详细设计（1.2）

### 11.1 三条引擎事实决定策略

以下以当前安装 `projectzomboid.jar`（SHA256 `E1A69EB7…`，与构建基线一致）的字节码核对，不是推断：

| 事实 | 证据 | 后果 |
|---|---|---|
| 重定向会丢弃在途寻路，不是“改个目标” | `PathFindBehavior2.pathToLocationF` → `setData`（偏移 0–124）：`cancelRequest` + `targetXyz.resetQuick()` + `pathIndex=0` + `stopping=false` | 每次重定向都是一次全新搜索，前一次结果作废 |
| 寻路是异步的，等待期不沿路径推进 | `update(float)` 在 `progress==notrunning` 时 `addRequest` 后直接返回 `Working`；`notyetfound` 时只调用 `updateWhileRunningPathfind`，其内部仅当 `pathNextIsSet` 才 `moveToPoint` | 搜索未完成时反复重定向，角色原地走步且永远拿不到路径 |
| 原生路径跟随自己处理门、窗、围栏 | `update` 内 `checkDoorHoppableWindow` → `IsoDoor.ToggleDoor`；`nativeTraversal` 已覆盖 `ClimbOverFence/ClimbThroughWindow/ClimbOverWall` 状态 | 开门与翻越不属于本任务实现范围；只需让角色处于路径跟随态 |

因此本任务的第一性能变量是**寻路提交节拍**，不是单次计算快慢。当前每 200ms 重定向（`CompanionNavigation.java:52-54`、`:84`）在长路径或多跟随者时会让搜索持续被打断；这是必须先修正的缺陷，不是“再调小一点”的调参问题。

### 11.2 方案比较与裁决

| 方案 | 转角/门口 | 成本 | 与现有架构 | 裁决 |
|---|---|---|---|---|
| A 提高重定向频率 | 目标点直连队长，易切角 | 每次重定向一次全量搜索，且打断在途搜索 | 复用现有 | 拒绝：事实 11.1 已证伪 |
| B 轨迹分段流式（目标点取自队长真实路程，段末续段） | 目标点本来就落在队长走过的折线上 | 每段一次短距搜索，约 1.8 次/秒/3 人 | 仍走 `PathFindBehavior2`，无第二位移提交者 | **采用** |
| C 逐帧直接操控（输入镜像/转向） | 需要自建避障、门、动画处理 | 每帧计算，无搜索 | 等于复制参考控制器，破坏唯一位移出口 | 本轮不做，仅保留“以后作为提示”的未验证假设 |
| D 迁入参考 CQB/Formation 体系 | 参考已实现 | 与黑board、威胁、战斗耦合，分支量大 | 引入第二套调度 | 拒绝 |

B 的关键不是“有轨迹”，而是**段末续段**：路径自然走完再要下一段，任何时刻最多一次在途搜索，取消只发生在真正需要换向时。

### 11.3 槽位数据契约（已决策）

| 项 | 决定 |
|---|---|
| 位置 | `npcMembership.byNpc[id].followSlot`，整数 `0..2` |

`companionIntents` 不存槽位：它是业务恢复记录，成员行才是宏观命令权威，两处都存会形成第二权威。

### 11.4 轨迹（`LeaderTrail` + `SquadTrail`）

| 项 | 值 | 依据 |
|---|---|---|
| 采样间距 | 0.25 格（平方 0.0625） | 1/4 格足以在门框内插值取点。参考用 0.08 格精细采样、64 点仅覆盖约 5 格，靠 350ms 权重衰减回落到队长相对几何；本项目按 4.5 格需求取 0.25×96，结论不依赖参考点数 |
| 容量 | 96 点 → 24 格 | 最远槽位 1.5+2×1.05≈3.6 格，加急转与折返余量取 4.5 格上限，容量为其 5 倍；按覆盖距离核算，不假定 64 够用 |
| 断段 | 单次位移 >2.5 格、换层、队长切换 | 跳变与跨层线性插值会穿墙，必须断段 |
| 采样 | `sample(backDistance)` 结果写实例标量字段，返回 boolean | 10Hz 采样不得按次分配对象 |
| 归属 | 每队长一份，`SquadTrail` 以引用计数管理，最多 4 条目；最后一个跟随者释放时移除 | 满足“每队一次采样、最后成员退出清共享引用”，不做全局扫描 |
| 每帧成本 | 一次距离比较（`moved²<0.0625` 即返回），同帧重复调用用时间戳去重 | 常驻成本应接近零 |

历史不足（`backDistance` 超出现有路程）时退回队长身后的直接几何目标，即当前可验证行为，不从墙外取点。

### 11.5 状态机与节拍

| 状态 | 进入 | 每帧/每拍动作 | 退出 |
|---|---|---|---|
| `HOLD` | 槽位点在 0.55 格内，或队长静止且距 1.2 格内 | 不请求路径；`holdFollowMovement` 已执行一次即可 | 槽位点移动 >0.95 格或换层 → `SEEK` |
| `SEEK` | 需要位移 | `movement.active()` 时什么都不做（不重定向）；段末立刻提交下一段 | 段末 → 立即续段；REACHED → `HOLD`；失败/超时 → `PROBE` |
| `PROBE` | 位移 1.2s 内 <0.12 格，或路径失败 | 侧移 → 后退 → 报告，见 11.7 | 成功 → `SEEK`；三级失败 → `BLOCKED` |
| `BLOCKED` | 队长丢失/超 16 格/动作占用/三次失败/8s 无进展 | 保持身体授权，不再请求路径，写状态码 | 队长移动 ≥1.5 格、换层或新宏观命令（沿用现有失败缓存） |

节拍表：

| 动作 | 频率 | 说明 |
|---|---|---|
| 轨迹记录 | 每帧，位移 ≥0.25 格才写 | O(1) 比较，无分配 |
| 授权校验 | 每帧 | 现有 `followAllowed`，不变 |
| 目标采样 + 通行探测 | 仅 `SEEK` 段末或 `PROBE` | 约 1.8 次/秒/3 人（1.5m/s÷2.5m 段长） |
| 路径提交 | 段末一次 | 一次性取消 + 新搜索，无重叠 |

段末**不调用** `holdFollowMovement`：当前实现对每个非 `MOVING` 结果都清零速度，造成走-停-走的抖动；只有 `HOLD` 与 `BLOCKED` 才清速度。

### 11.6 编队与窄道

| 槽位 | 开放地形 | 列队（窄道） |
|---|---|---|
| 0 | 队长后方 1.5 格，居中 | 后方 1.5 格 |
| 1 | 后方 1.5 格、左 0.9 格 | 后方 2.55 格 |
| 2 | 后方 1.5 格、右 0.9 格 | 后方 3.6 格 |

- 开放/列队判定：侧向目标格可站立且当前位置到该点无遮挡（`lineClearCollide` 严判）→ 用槽位；否则用列队点。每段最多 2 次探测，不逐格扫描。
- 侧向偏移沿轨迹切线垂直方向，不是沿队长朝向，避免队长急转时目标甩到墙里。队长静止超过 400ms 后不再用轨迹取点，改按队长相对几何落槽（对应参考的 350ms 权重衰减），否则随从会停在转角外的旧轨迹点上。
- 出通道复位：列队期间每段重判一次，可站立即回槽位，不设驻留计时。
- 不按 NPC ID、装备或入队顺序自动分配槽位；槽位只来自玩家命令。

### 11.7 让路、门口与队内次序

三级响应，均有界：

1. **侧移**：沿垂直方向 0.9 格（保持同一后退距离），固定一侧保持 1.5s，防止左右摆动；该侧连续两次不可行才换边。
2. **后退**：轨迹上再退 1.2 格的位置，用于窄口对向或前路被占。
3. **报告**：`FOLLOW_BLOCKED` 进入 `BLOCKED`，保留授权，不传送、不关碰撞、不顶人。

门口与玩家：队长静止且未能解析合法落槽、同层距跟随者 ≤1.2 格时 `HOLD`；合法落槽仍需执行，不能仅因接近队长永久停住——这就是“玩家停在门口不反复顶门”的实现，不需要额外门锁或预约。

队内次序：若 0.8 格内前方是本队成员或队长（单位置接近且其朝向点积 >0.5），判为排队而非受阻，重置停滞计时并等待，不触发侧移。这是局部判断，不建立持久门锁或全局仲裁。

### 11.8 楼梯与换层

- 跟随者处于 `ClimbOver*` 或楼梯格时，不重定向，让原生通行走完（现有 `followTraversal` 保留）。
- 队长换层：断轨迹段，目标改为队长所在层的位置，由原生跨层路径处理；不跨层线性插值。
- 层差 >1 或落点不可站立 → `BLOCKED`，不无限重试。
- 队内楼梯排队不限制玩家通行；判定用实际时间与位移进展，不照搬参考的 90/24 帧。

### 11.9 性能预算（待实测项）

| 场景 | 预期 |
|---|---|
| 三人静止 | 每帧 3 次位置读取与 O(1) 比较，0 次寻路 |
| 三人直线移动 | ≈1.8 次寻路/秒总计；每段 ≤1 次 `lineClearCollide` 级别探测 |
| 三人受阻 | 每 1.5s 一次试探，两次失败后停止请求 |

对照基线是当前实现（5Hz 重定向，最坏 15 次/秒且多数打断在途搜索）。**未实测不宣称提升**，只记录提交次数与帧耗时。

## 12. 技术路线：复用引擎寻路，自研行为层

### 12.1 分层与归属

| 层 | 归属 | 内容 |
|---|---|---|
| 路由与通行 | 引擎 `PathFindBehavior2` | 静态几何寻路、开门、翻窗、翻围栏、楼梯、动画与根运动 |
| 行为 | 本项目 Java（`CompanionNavigation`/`LeaderTrail`） | 编队槽位、轨迹取点、分段节拍、排队、让路、失败有界 |
| 命令与责任 | 现有 Lua 链 | Membership 命令、槽位、Session、停止确认与恢复 |

这不是"不设计"，而是把设计放在行为层。参考项目把设计放在导航层，是因为它在同一层同时承担战斗协同、车辆协同与过门纪律；本项目这些能力在需求内但属后续交付（§8），控制层的引入时机与替换边界见 §12.5。

### 12.2 首期不做（不是永久放弃）

下表三项是实现战斗侧移、门纪律、大规模同屏的**必要条件**，最终必须由本项目接管；这里限定的只是首期的范围，不是永久结论。分档与成本见 §12.7。

| 首期不做 | 为什么首期不做 | 什么时候必须做 |
|---|---|---|
| 逐帧写 `playerMoveDir`/`strafe` | 会与现有原生根运动修正、动画方向、停止掩码形成第二个位移提交者，需先证明独占交接 | 战斗协同或车辆同乘开工；或人数 >6 |
| 接管门/窗交互 | 需要执行器自己决定开不开，等于不跑引擎路径 | 出现"关门夹队友"实测证据，或人群规模让门成为瓶颈 |
| 自研 NavGrid/A* 与全局预算 | 参考 8 类合计 8137 行，其中 `NavGrid` 851、`NavInteract` 1125、`NPCPathfinder` 348；3 人跟随用不到其大部分分支 | 人数目标 ≥8，或引擎请求队列实测成为帧耗时瓶颈 |

### 12.3 升级门槛（实测触发，不是预留接口）

以下阈值是决策门槛，不是性能结论；未测量前不实现对应能力。

| 门槛 | 触发条件（游戏内实测） | 对应最小改动 |
|---|---|---|
| G1 门礼仪 | 同一门 3 秒内被本队重复开合 ≥2 次，或队列等待单次 >5 秒频发 | 记录本队通过的门 6 秒，期间不重复主动开合；不做 1125 行交互栈 |
| G2 侧移不足 | 恢复/排队/受阻阶段累计时长占活跃跟随累计时长 >5%（NPC 时间比例） | 独占的逐帧提示：取消路径 → 写 vars ≤30 帧 → 回路径；必须先证明无第二提交者 |
| G3 追赶不足 | 落后 >4 格且 10 秒内未收敛出现 ≥3 次 | 先用现有走/跑开关与段长调整；无效才考虑速度微调 |

三条门槛都未触发时，保持 12.1 的分层，不提前引入参考的导航栈。

### 12.4 超过三人时的扩展路径

先看代价结构，再决定改什么；不预留接口，只保证改动量可控。

| 维度 | 随人数增长 | 依据 |
|---|---|---|
| 每跟随者状态 | O(1)，无随人数增长的每帧计算 | 轨迹每队一份共享；`CompanionNavigation` 只存标量 |
| 寻路提交 | 线性：N × 速度 ÷ 段长。6 人约 3.6 次/秒，12 人约 7.2 次/秒 | 段长 2.5、速度 1.5；引擎寻路队列承受力**未测** |
| 身体争用 | 超线性：窄口串行，过门时延 ≈ N × 单人过门时间 | 物理与动画，不是算法可优化项 |
| 队内判定 | 仅阻塞时扫 N 个载体 | `ProbeRuntime.squadAhead`，非每帧 |

扩展需要的改动，都是常量与表，不是重构：

1. 槽位上界三处：`ProbeRuntime.followWithControl` 校验、Lua 成员行校验、右键菜单项数。
2. 槽位几何已改为按 rank 的格点：`slotBack/slotSide`（`CompanionNavigation`）。rank 0..2 与原布局逐值一致；3 以后按“同一排左右成对、下一排后退 1.05”自动延展，不需要知道总人数。
3. 轨迹容量复核：rank 11 的第 6 排 back = 1.5+5×1.05 = 6.75 格，96 点 ×0.25 = 24 格仍有 3.5 倍余量，无需扩容。

换层的临界点（判定标准，不是承诺）：

| 规模 | 结论 |
|---|---|
| ≤6 | 当前架构 + 段长与队列调参；先测提交次数与帧耗时 |
| >6 或 G2 触发 | 逐帧提示层成为必要，否则窄口退化为停走长队 |
| >10 且多门并行受阻 | 才考虑参考的自研导航与门纪律；仍不继承其战斗/车辆分支 |

能力扩展（战斗、车辆、搜刮/卸货）各自独立交付，跟随层只负责“到达并保持队形”。不因为未来可能加更多同伴或更多能力，就把跟随层提前做成通用调度器。

### 12.5 控制层（逐帧矢量）的引入时机与替换边界

先纠正一处表述：战斗协同（逐帧侧移、NPC 互避、开火角度）、过门纪律、车辆同乘都在需求内，本文 §1 与 §8 把它们列为独立交付，这是**分期**，不是放弃。首期只用路径执行，不影响这些能力最终要做。

替换边界——这才是"可扩展"的实际抓手：

| 层 | 位置 | 换执行器时 |
|---|---|---|
| 目标生成 | `CompanionNavigation.tick` 前半：轨迹采样、槽位格点、列队判定、排队判定、失败分档 | 保留，不重写 |
| 位移执行 | `retargetFollow` / `ended` / `pathReady` 三个调用点 | 替换为逐帧方向提交 |
| 命令与责任 | Lua Session/Controller/Driver、`body.follow` 语义 | 不变 |

即换执行器约动 150 行执行段，规划与责任链不动。引入时必须同时满足：单一提交者（取消路径后才写控制变量，回收前不再提交路径）、重新验证现有原生根运动修正与停止掩码、重新验证停止/保存顺序。

参考项目还有一项本项目目前没有、人数上去后必须补的能力：**全局寻路预算**。`NavMover.reserveSearchSlot` 以 16ms 窗口只放行一次搜索，其余按 FIFO 排队、超过一个窗口即淘汰（`NavMover.java:377-415`），且直连可通行时完全不寻路（`directPathClear`）。引擎寻路的请求队列不归我们管，N 人同时请求时无法限流——这条比 G2 更硬：人数上去后要么接受抖动，要么把执行层换成可控预算的实现。

引入时机（任一成立即做，不等 G2）：

1. 战斗协同进入实现阶段；
2. 车辆同乘进入实现阶段（座位预留与接近角度本身需要矢量控制）；
3. G2 触发或跟随人数 >6。

### 12.6 上限由约束保证，不由预留接口保证

担心"延后做会锁死后续上限"成立与否，取决于三件事是否成立；这三件与人数无关，现在成本为零：

| 约束 | 现状 | 一旦破坏的后果 |
|---|---|---|
| 导航请求单点 | 导航请求收敛在 `CompanionNavigation.submitSegment`；物理根运动仍经 `ProbeNpc.doDeferredMovement`，替换执行器须核对身体交接 | 若规划里散落 `pathToLocationF`，换执行器要改满篇 |
| 路线是数据，不是控制流 | 轨迹与采样结果只是坐标，不含引擎对象或路径句柄 | 若路线依赖 `Path` 对象，换执行器即重写规划 |
| 能力归层 | “该不该开这扇门”属行为层，“怎么走/怎么开/什么时候搜”属执行器；当前没有门逻辑，故无耦合 | 若把门状态存进执行器，换执行器即丢状态 |

迁移成本（将来需求 → 改哪里 → 不动哪里）：

| 将来的需求 | 改动 | 不动 |
|---|---|---|
| 逐帧执行（战斗 / 车辆角度） | `submitSegment` 内换成写控制变量，并补该执行器自己的 `ended/pathReady` 语义（约 150–250 行） | 轨迹、槽位格点、列队、排队、命令链 |
| 自研搜索与全局预算（十几人） | 在 `submitSegment` 之下接自己的搜索、配额与失败缓存（约 300–600 行） | 同上 |
| 门纪律 | 行为层决定时机，执行器提供开门能力（约 150–250 行） | 同上 |

真正会锁死上限的写法只有三种，本项目都不采用：规划里直接读写引擎路径状态；把路线/门状态存进执行器；把人数上限写死进产品契约且无处可改。

当前唯一写死的是产品契约：槽位 `0..2`、菜单项数、成员上限 512。这属于产品决策而非架构死角——槽位几何已按 rank 参数化为格点（`slotBack/slotSide`），扩到 N 人只需同步改三处常量与契约校验，不触及导航实现。

因此结论是：延迟实现控制层不会限制上限，只延迟成本；是否值得提前付，取决于实测数据与目标人数，而不是架构可行性。

### 12.7 分档接管：不是"要不要自研"，是"分几档做"

三项能力（战斗侧移、门纪律、大规模同屏）确实都要求接管，但接管是三个独立档位，不是一次性重写整套：

| 档 | 接管什么 | 解锁什么 | 估算 | 前置 |
|---|---|---|---|---|
| D1 执行 | 逐帧方向提交（写 `playerMoveDir`/`strafe`/速度变量），路线仍取轨迹，跟丢时回落引擎路径 | 逐帧侧移让路、速度匹配、战斗队形、车辆接近角度 | 400–600 行（执行 150–250 + 队伍级避让 200–300） | 独占交接验证：取消路径后才写控制变量，回收前不再提交路径 |
| D2 交互 | 执行器自己决定并执行开/关门，不做引擎路径的被动跟随 | 门纪律（全队过完再关、不夹队友） | 150–250 行 + 门记忆 | D1；否则引擎路径会自行 toggle |
| D3 搜索 | 自研网格 A* + 全局预算（每窗口一次、FIFO、失败缓存） | 十几人同屏稳定帧耗时 | 400–700 行 | 人数目标 ≥8，或引擎队列实测成瓶颈 |

D1 一次解锁三项里的两项（侧移与速度），是性价比最高的一档；D2 必须在 D1 之后，因为只要引擎路径还在跑，它就会自己开关门；D3 只与人数有关，与前两档解耦。

参考项目 8137 行与本估算（约 1000–1500 行）的差额，主要不在能力，而在它的架构选择：CQB 战斗决策 2438 行、完整门窗交互 1125 行（含车辆、尸体、多种窗口与关闭条件）、通用化 `NavGrid` 缓存 851 行，以及为多 NPC 场景准备的通用失败/预算/等待机制。我们按实际需要实现子集，而不是复制其结构。

落地顺序建议：首期闭环实机通过 → D1（含独占交接原型）→ 按交付顺序做 D2 → 人数目标确定后再评估 D3。

### 12.8 结论

1. 路线是**分档接管**：引擎负责路由与门窗动画，本项目负责编队与路线；D1 接管腿、D2 接管门、D3 按人数接管搜索。不存在"永不自研"，也不存在"一次重写参考"。
2. 顺序固定：首期行为层（已落 Java）→ 实机闭环 → D1 执行器（同时解锁侧移与速度）→ D2 门纪律 → 人数目标确定后再评估 D3。
3. 三条硬约束不可破坏：位移提交单点、路线是纯数据、门与搜索的决策权归对应层。破坏任一条，后续就从"加实现"变成"重写"。
4. 人数上限不是架构决定的：3 人现有方案够用；6 人要 D1；8 人以上要 D3。扩人数只需改契约常量与格点，不需要换架构。
5. 本节所有行为效果均未实机验证；D1/D2/D3 的估算行数是工作量级别判断，不是已完成事实。

## 13. 按功能增量补全：受阻后退（2026-11-06）

用户要求每项先设计、逐项补全，并明确持续执行；常规设计和实现顺序在本会话完成，不逐步骤要求确认。本节是既有“侧移→后退→报告”的缺陷修正，不改变分层或存档契约。

### 问题与取舍

`CompanionNavigation.tryBack` 原先采样队长轨迹 `1.5 + slot×1.05 + 1.2` 格。队长 x=10、NPC x=0、slot=0 时，轨迹目标 x≈7.3，截段后仍向前。保留轨迹并增加方向筛选虽能修复，但保留两个参照系；整体重写避让执行器扩大本片范围。采用 NPC 当前受阻方向的负向 0.9 格，方向已经由 probe 归一化。

参考基线为当前根 NPCFW.jar（SHA256 `5229EB5A6871514DE274FEB91E8DB353FDBDE8FB42FD9741493D40CDE85BA19E`）：FollowLeaf.beginStairRecovery 按自身位置与当前运动方向求恢复方向；NPCMovementUtil.manualMovement 在提交前接 PlayerAvoidanceSteering，候选检查与身体执行分开。本修正采用自身参照系，不复制其控制器或宣称已实现主动避让/楼梯恢复。

### 行为、所有权与边界

- 两侧候选不可用或侧移后仍受阻时，后退目标为 `(x-forwardX×0.9,y-forwardY×0.9)`，与槽位、队长距离、轨迹历史无关。未跨层；目标或直线不可通行就沿现有分支报告 BLOCKED，不扩展扫描或重试。
- 仅改变后退目标计算。排队时限、侧移优先、有界探测、恢复步完成不能证明原路畅通、正常段续接和失败唤醒均保留。
- 创建/认领：TaskController.attachDriver → ProbeRuntime.followWithControl → ProbeNpc.beginFollow；本功能复用已授会话，不建立新任务/资产认领。
- 正常结束：导航 ended 正常段重置探测状态；后退完成只恢复 SEEK，不释放会话，后续仍试原跟随目标。
- 异常打断：导航每帧 followAllowed；WAIT/自理/保存沿 TaskController.stopOnce，ProbeNpc.stopProbe → closeFollow 清派生轨迹并停止原生移动，再确认释放身体。后退不保存为旧动作，不重放。
- “后退”是相对受阻方向的位置目标。动画和转向仍由原版处理，不承诺始终背朝目标倒走。

### 验证

源码核对归一化输入及负向点积；Java 真实编译和既有移动/轨迹/控制权检查。该局部公式不另建模拟执行器或复制公式测试。游戏由用户集中观察落后队员的受阻后退、转角背墙拒绝、WAIT/自理中断；未实机不记体验通过。

## 14. 按功能增量补全：追赶与潜行姿态（2026-11-06）

### 依据与取舍

当前安装 JAR 的 AIComponent.postUpdatePlayer 实际消费 AIBrainPlayerControlVars.running，调用 IsoPlayer.setRunning 和 updateMovementRates；参考 NavSpeedPolicy.apply 也写同一原生输入。FollowLeaf.applyMove 同步队长潜行、调用 NavSpeedPolicy；shouldCatchUpToLeader 用距离平方 64/36 滞回。故 §12 中“速度匹配必须等待 D1”对本片过强：**只接原生姿态**可留在现有身体拥有者和根运动链中。本节明确收窄该前置，不接手方向、门或搜索，不等同完成 D1。

比较：仅保留步行无法跟上跑动队长；整体切换 D1 会混入路线/位移交接。本片选择在 CompanionNavigation 内计算速度意图，由 ProbeNpc 写已有原生 AI 姿态字段，继续让原版决定实际速度、转向及位移。无性能改善承诺。

### 行为规则

- 一个会话一个 FollowLocomotion，只存追赶滞回和转弯减速标量，不存档/分配逐帧结果表。距离 >8 格进入追赶，≤6 格退出。队长跑步或冲刺时可请求跑步；本片不写冲刺意图、不保证匹配玩家冲刺速度。
- 同步队长潜行；潜行时禁止跑步，不以追赶覆盖潜行。停止/自理交接/保存结束该跟随会话时清理本会话的跑步和潜行姿态，不把姿态泄漏给后继任务。
- 只有已有路径正在移动的 FOLLOW_ACTIVE 正常段允许跑步；搜索等待、HOLD、排队、侧移/后退、跨层、翻越均请求步行。当前/向路点前方 0.4/0.8 格的三次有界格点读取发现楼梯或未加载格就请求步行。
- 路点运动方向归一化点积 <0.82 时，650ms 内步行后再评估，采用参考阈值/时长；本片在所有急转保守降速，未宣称与参考完整速度策略等价。姿态最多 10Hz 派生；停止分支直接清运动，不能等待下一次派生。
- 本片保留同层/跨层的16格距离门禁。接线复核发现 CarrierRuntime.restoreCheckpoint 还会拒绝距玩家超过16格的实体恢复；只放开活动导航会产生“能跟随、正常重进却恢复不了”的契约缺口。距离放宽必须另做已加载实体恢复与保存闭环，不能只删导航判断。
- 已有范围内仍走最多2.5格终点跨度、已加载/可通行检查、失败探测与失败缓存。不强制加载区块/传送/直写坐标。完整远距离追赶、楼梯恢复和卸载区块追随不在此项完成范围。

### 所有权和数据

创建仍由 TaskController.attachDriver / ProbeRuntime.followWithControl / ProbeNpc.beginFollow；仅当前 followAllowed 的导航调用姿态适配。正常 HOLD 清移动，closeFollow 清本会话姿态；异常停止、WAIT、自理、冻结/世界替换仍走 stopProbe 与原停止确认释放。旧回调不得新增姿态写入口，无新公开桥/存档字段/兼容链。

### 验证

FollowLocomotion 定向测试直接验证生产策略：8/6边界及滞回、队长跑步、潜行优先、急转650ms、精细通行与暂停。真实Java构建验证引擎输入签名，既有控制权/跟随/保存接缝保持。跑动追赶、潜行视觉、楼梯降速、停步/自理清姿态仅用户实机可验；未验不宣称功能对等或速度收敛。

## 15. 已加载区域内的远距离跟随与原位恢复（2026-11-06）

用户已授权逐项先设计并连续实施。本节明确改变活动同层跟随及实体恢复的距离接受范围，不作为等价重构夹带；保持存档格式、原件和唯一身体控制。

### 依据、方案与范围

现有导航超过16格终止；CarrierRuntime.restoreCheckpoint也按16格拒绝已校验的保存点；Persistence.tickWork自动恢复仅一次。由此即使队员/保存格仍在已加载区域，自理停留或跑动落后也会失去跟随/正常重进。

参考当前根NPCFW.jar的 NPCManager.restoreLoadedNPC(NPCData,boolean)实际先查询保存格，普通分支在格未加载时推迟，加载后才创建载体并恢复快照；本片不使用其强制分支，也不引入其池化/后台实体架构。根JAR哈希同§13。

比较：把16改为32/64仍是与加载情况无关的新硬门槛；无限追随/强制加载则扩大到后台实体系统。选择**已加载区域内**原生追赶及原保存格恢复。尚未加载的实体仅保留记录，既不移动存档坐标也不重造物品。跨层且距离>16格的路由暂保持原拒绝，留楼梯专项；本节不承诺任意跨区块/跨层召回。

### 活动跟随

- 同层取消16格终止，继续使用已加载/可通行落点与2.5格终点跨度，重用8/6格追赶姿态；近点不可通行走现有探测/失败缓存，不增加全图搜索或每帧重定向。
- 不改变身体/队长同一世界、存活、实际方格存在及有限坐标检查。NPC方格卸载后仍沿既有停止/错误边界，不伪装后台移动。
- 不放宽普通move/spawn的距离契约，也不修改既有联机接口。

### 实体恢复（契约变化）

- CarrierRuntime.restoreCheckpoint 对当前正式检查点，不再以到玩家距离作恢复前置：世界/版本/身份/原件校验通过，且原保存格已加载、有地板、非实心并空闲时，按现有顺序载入原生快照、发布唯一SESSION、附着原坐标。FOLLOW/WAIT/自理/驻扎共用此恢复机制，避免WAIT或自理保存时丢失远处载体。恢复身体不授权跟随，宏观命令仍由成员行与TaskPersistence.candidate验证。
- 原保存格不可用返回既有 RESTORE_TILE_UNAVAILABLE，在构造载体、SESSION发布和原生load之前退出。读档不清空/转换/迁移任何数据，ProbeCheckpoint及原生封包不变。
- 正常释放/一次性消费由ProbeRestoreGate保持：附着后ACTIVE，部分附着异常LOST，死亡/移除REMOVED，不得利用重试构造第二副身体。

### 有界启动重试

- 复用Persistence原启动恢复队列，每tick最多一次恢复；只对RESTORE_TILE_UNAVAILABLE加入下一轮，每轮结束后等2秒，每ID最多3次（含首次）。其他结果不自动重试；成功ID不再进入队列。
- 等待/重试仅为本世界派生队列，不保存；世界根替换或reset撤销。到达三次上限后停止自动尝试并保留原检查点，后续沿现有显式恢复入口重试，不无限后台解码扫描。日志保留失败原因，不追加高频UI或新状态枚举。
- 不在OnSave等待/重试；未恢复的有效记录仍由既有CHECKPOINT_RETAINED保存，不清空原件责任。没有新增计时器/全局恢复平台。

### 验证与限制

定向Lua用真实Persistence队列+符合当前契约的native替身验证：逐tick一人、两秒间隔、三次封顶、成功不重复、硬失败不重试、换世界/reset撤销、结束后空闲无native调用。真实Java编译及已有恢复门/原件归属/检查点和跟随交接回归。仅删除距离拒绝不能作为原生恢复成功证据；20–30格同层追赶、自理落后、远处WAIT/自理/FOLLOW正常重进及保存格暂占用须用户实机。
