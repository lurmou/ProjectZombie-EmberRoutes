## 1. 已确认范围、依据与真实性结论

### 1.0 本轮确认的模型修订（优先于下文旧表述）

用户已确认：先做最小功能子区；活动策略指NPC可进行的行为，采用禁用/允许/优先三档；参考模拟人生俱乐部，以“日常公共生活＋聚会偏好覆盖”为主。公共区平时可使用，普通聚会中的个人自主选择不要求全员执行相同步骤；演讲/仪式才使用共同阶段。此决定细化已确认分级效用架构，不增加身体执行器或后台库存。

下文0.3的共同阶段、必需角色和共同回执适用于SCRIPTED模式；新增FREE模式在共同召集/结束边界之间持续提供行为候选，不为每次换聊天对象/座椅推进全场stageEpoch。原先强制单个“主讲＋听众”验证内容由此更新为先形成日常公共区配置，再接可自由交流的聚会。音乐、进食、并行动画等逐能力接入，不因规则列表存在而可用。

区域规则、临时聚会规则、实际候选是三种对象：区域提供范围/长期规则；聚会只在其成员与期限内覆盖行为偏好；个人仍按需求/能力/资产/同伴/距离与连续性选择。优先不是强制，禁用只影响普通娱乐，不阻止紧急自理/原件归还/安全撤离。重叠或活动结束均不注销实际原件责任。

本期先接现有READING/SOCIAL/SIT/SMOKE/FITNESS/STROLL/OBSERVE等已实现行为，设置规则不保证存在资源或成功动作。轻量交流与主行为并存仅在有明确适配时启用，不能把“生活感”变成两套身体控制。小团体仅承诺后续在同一活动内独立加入/退出/切换，首批不引入关系网络、个性喜好、自动招人或积分俱乐部。

空间基线与最小实现见[公共生活子区基础](2026-10-28-public-life-zones-design.md)。实施优先级：区域与规则闭环→复用现有闲暇选择消费规则→FREE聚会/小团体→SCRIPTED环节。具体未实现边界仍以BACKLOG为准。

用户要求完整细化 A3/A4、先搭建活动框架，以环世界为玩法参考，并开展源码级评审。2026-10-28 用户进一步明确：**指定名单内 NPC 在安全收束普通工作后参加**。危险、急救、紧急自理、身体停止和未结责任的约束不因此放宽。

### 1.2 先排除三种不合适的路线

| 路线 | 好处 | 不采用原因 |
|---|---|---|
| 仅把双人社交扩成多人 | 改动少、容易展示 | 无法表达必需角色、异步消费、跨阶段位置和独立早退 |
| 独立活动 AI/身体队列/库存服务 | 局部开发方便 | 与统一仲裁、原件权威和保存屏障冲突，长期成本高 |
| 任意脚本工作流或预建大型仪式引擎 | 表面扩展范围大 | 隐藏副作用、难限预算，超出当前明确需求 |

推荐采用：**只读活动定义＋持久活动实例＋逐人出席握手＋现有 Session/微型行为树**。新增模块只承接活动业务，不替换架构层。参考事实及不可照搬项见[源码评审](../../reviews/2026-10-28/activity-framework-source-review.md)。本体 LordJob_Ritual、UE 引擎实现仍未完成源码核查。

## 2. 玩家可观察结果与边界

玩家选择地点、活动、组织者和参加名单，查看必需条件，再发起。居民依次安全结束当前事务、前往各自位置、参与共同活动。面板能解释某人为何仍在还书、交货或监管炉具；到场不足时显示原因，不凭邀请数开场。

已在名单中的普通工作不再次打断获准参加者；危险/紧急需求可令个人提前退出。取消后立刻停止新增邀请与活动动作派发，正在起身或归还物品的人显示“收束中”。玩家关闭面板不影响活动。

本期不增加信仰、丧亲心理模型、关系网络、活动图形编辑器、逐小时排班、全局 GOAP、传送到场、自动点火、跨据点召回、玩家角色自动身体控制或完整联机。已有双人社交不整套迁移，只接入参与互斥与安全收束门。

活动内容是 A5 的独立适配。A3/A4 开发交付必须至少带一个经用户确认、具备真实动作和停止证据的端到端活动闭环；若所有类型都因缺适配被禁用，只能称框架接通，不能称可玩活动完成。

## 3. 模块及现有系统接缝

第一版按五个内聚单元实施，不按0.1的十个职责名机械创建十个服务。以下均为拟议内部模块，不声称当前已存在；一个单元可以有纯函数辅助文件，但不因此新增生命周期、tick、事件总线或独立存储。

| 模块 | 输入/输出与唯一职责 | 依赖及禁止事项 |
|---|---|---|
| ActivityRegistry | 注册、校验、冻结 ActivityDef；按 ID/version 查询 | 不存运行字段；不派动作 |
| ActivityStore | 持久实例、角色/参与事实、事件版本、结果引用 | 与既有世界数据根同生命周期；不另存物理库存 |
| ActivityService | 权限、幂等命令、预检、定时触发、阶段推进、结果编排及只读投影 | 活动业务唯一写入口；不移动 NPC、不清队列、不消费物品 |
| ActivityAttendance | 纯资格查询、出席请求与逐责任握手、退出恢复 | 读现有业务权威；不维护第二份“NPC总状态” |
| ActivityParticipant | 每人 Job、行为子树、位置/动作回执 | 唯一 TaskRuntime/TaskController，不能控制别人 |

原 ActivityCoordinator 是 Service 内的纯状态转换；ActivitySites 是共享设施/Claims上的位置辅助；ActivityResults 是纯评估与已有适配器调用；ActivityTriggers 是Service的到期入口；ActivityProjection 是按订阅构造的查询。后文出现“协调器”“结果处理”等称谓均指职责，不另设运行服务。

依赖方向：UI/Boot→Service；Service→Registry/Store/Attendance；Participant→Registry和现有任务/动作系统。Service与Participant之间传带代次的意图/事实，不相互同步调用推进或在停止回调中启动后继。Attendance通过明确的业务适配表读写原拥有者；原业务不require活动Service，只接收标量原因/令牌。定义与存储层不反向依赖UI、Service或引擎动作。

拆分新运行单元必须有实际理由：独立权威/生命周期，或至少两个真实消费者需要不同变化节奏；“可能有插件”或函数数量增加不是理由。纯逻辑变长可拆辅助文件，不用增加管理器。Service只编排，不把寻路、库存、配方及原生动作细节收进一个大文件。

统一任务关系：ActivityInstance 是活动业务根，不伪装为制作 Order；每个获准参加者的 `ACTIVITY` Job 进入现有 JobStore/TaskJobs，payload 引用 eventId。Job 使用已有 PREPARING/RUNNING/STOPPING/SETTLING 等生命周期，活动业务相位放 payload/实例字段，不改全局 Job 状态枚举。

活动参加属于 PERSONAL 候选，绑定指定 npcId；物品归还和监管仍为 RESPONSIBILITY 候选。不得将参加者伪装成公共工种或新建 0～4“娱乐工种”。当前 PublicWorkProviders 是普通工种注册表，不直接塞入活动。

当前 TaskResume 针对 SELF_CARE 及特定前任原因，不能直接改名复用。活动需新增独立原因与收束适配接缝，复用已批准停止事实/命令代次协议，不改动自理恢复语义。JobStore 现有 512 普通 Job/256 SELF_CARE 额度须尊重；活动 Job 占现有普通额度，预检不足时拒绝或等待，禁止另开无界任务存储。

### 3.1 状态只有一个当前权威

| 数据 | 唯一当前权威 | 活动侧允许保存的内容 |
|---|---|---|
| 活动相位/角色/名单/参与累计/出席意图 | ActivityStore | 活动独有事实及版本 |
| 参与者Job生命周期、动作尝试与执行恢复点 | TaskJobs内ACTIVITY Job | event仅存jobId和完成/停止证据引用，不镜像一个可写Job状态 |
| 身体授权/停稳 | TaskRuntime/TaskController及现有原生核验 | 引用带代次的已确认事实；每次新授权仍重验 |
| 原件位置、Claims、持续义务、原工作恢复 | 原业务及共享资源权威 | ID/版本/结清证据引用，不写第二份余额或责任拥有者 |
| 成员归属/玩家命令版本 | Membership及现有命令代次 | 准入时快照用于失效核验，不覆盖原值 |
| 当前人数/阻塞文案/进度展示 | 从以上事实派生 | 可丢弃只读缓存，恢复时重建 |

event中的attendanceState表示业务准入/参加关系，绝不表示原生动作正在运行；执行状态从Job/Runtime投影。执行回执先按稳定attempt在Job/原业务确认，再由Service幂等归入活动事实。event尚未收录回执的窗口不得补发动作；正常恢复先核对已有Job事实。未创建Job的邀请不伪造PREPARING Job，不为展示建独立状态账本。

## 4. ActivityDef 与扩展契约

### 4.1 注册与结构

需求指定的对外名称保留为 `EmberRoutes.registerActivity(def)`；首轮仅作为内置活动的受控注册入口，不先承诺长期schema/回调兼容。公开schema与文档须通过§4.4的不同用例检查后再冻结，不取消第三方扩展目标。

入口只在定义加载期接受，所有定义装载后统一验证引用，再随世界启动冻结；不要求模块加载顺序刚好先注册所有依赖。重复 ID、未知引用、版本冲突明确拒绝，不静默覆盖。定义按值校验并形成只读内部副本；执行现场绝不写回调用者的定义表。

| 分组 | 必需字段及语义 |
|---|---|
| 身份 | namespaced id、整数 schemaVersion、definitionVersion、CN/EN名称/说明键 |
| 能力 | requiredCapabilities：已登记动作、设施、资源/效果适配 ID；supported/unsupported/unknown 明确区分 |
| 场地 | siteTypes、必须/可选设施、角色位置策略、可达与可观察条件 |
| 角色 | roleId、min/max、eligibleRuleId、countsForQuorum、countsForQuality、positionPolicyId；required 由 min>0 推导避免矛盾 |
| 流程 | 有序 stageId 列表；每阶段角色行为、准入/完成/超时/失败与退出规则 |
| 参与 | 最大人数、最低到场、截止规则、迟到/重入策略；人数不超过实际合法位置 |
| 资源 | requirementId、资源适配 ID、数量单位/必要性/使用时机；只声明需求，不传写库存函数 |
| 结果 | 个人完成度规则、质量因素 ID/权重/适用阶段、效果适配 ID、冷却策略引用 |

所有 ID 均限定长度、数量和嵌套深度，注册校验与 JobStore 可序列化边界一致；不存在无限阶段和递归引用。第一版阶段是有限有序序列，可明确跳过可选阶段，不提供任意循环/并行 DSL。物理上多人同时参与不等于行为树引入任意 Parallel 节点。

### 4.2 阶段描述

每阶段指定：`stageId`、`roleBehaviorIds`、`entryRule`、`completionRule`、`durationGameMinutes`（有时长才填）、`requiredReceipts`、`lateJoin`、`missingRolePolicy`、`observationPolicy`、`timeoutPolicy`、`watchdogPolicy`。

支持的完成模式为有效时长、指定回执集合完成、二者同时满足。注册拒绝没有可达结束条件的阶段。可选阶段跳过要写 SKIPPED 原因，不能当完成计分。超时只能明确跳过可选段或结束为不完整/失败，不能返回成功继续假定物资已交付。

扩展者增加活动通常只组合既有角色、阶段与适配 ID；新增原生能力须独立登记五要素（启动、效果、停止、成功证据、恢复）及预算。纯资格/质量扩展返回标量读数与原因，禁止副作用；缺测量或原生验收时能力标为未验证。开放模组接口不等于能沙箱隔离任意恶意 Lua，本框架不作此保证。

不为eligibleRule、positionPolicy、qualityFactor分别提前建立公开注册平台。第一版由一个内部能力表承接确有调用者的处理器，使用固定输入/输出和有界预算；新活动只组合现有能力，新原生效果只增对应适配。受信任扩展可登记新的能力，但不能替换活动状态机、权威存储或准入检查；对外稳定范围随真实用例验证逐项公布。

### 4.3 A5 接口边界

动作适配返回 RUNNING/SUCCEEDED/FAILED/CANCELLED/UNKNOWN 及 actionAttemptId、bodyStopped/effectsKnown、原件变化引用。行为树仍只消费 Success/Failure/Running，UNKNOWN/STOPPING 由控制协议持有，不能通过 Fallback 越过清理。

资源适配只返回已有 Claims/义务引用及核验结果；质量适配只读参与事实；效果适配提供 prepare/apply/observe/reconcile 四类语义。接口名可在实现计划中映射到当前模块，所有拟议接口都不能写成已有引擎 API。

### 4.4 用不同用例检验抽象，而非堆接口

| 校验用例 | 应当只新增/变更 | 如需改核心，说明什么 |
|---|---|---|
| 主讲＋听众，无耗材 | 活动定义、已有手势/气泡/有效参与适配 | 基础角色/阶段协议尚未闭合 |
| 聚餐，有部分消费和原容器归还 | 活动定义、资源/消费/归还适配；复用原件权威 | 若需修改核心以知道锅/食物类型，资产细节泄漏；若需独立库存，权威分层错误 |
| 座位/设施质量变化（只作设计推演） | 对应位置/因素能力 | 若重写召集与参与生命周期，扩展点过度绑定具体场地 |

首个用例按D7由用户决定；第二种差异用例未实际验证时，不把公开API标为稳定，也不为验证之名擅自实施聚餐。源码接缝/静态推演能发现问题，不能替代实际消费、停止与重进证据。新增真实需求超出有限阶段/能力契约时，先评审版本化扩展，不承诺所有未来活动零核心改动。

## 5. 命令、权限、幂等与定时

| 命令 | 核验与结果 |
|---|---|
| preview(defId,siteRef,organizerId,roster) | 只读可行性/资格/预期因素范围；不占身体、角色位置或资产 |
| start(requestId,expectedPreviewRevision,...) | 重验世界、阵营/据点管理权限、定义版本、名单、场地、能力与额度；创建唯一 eventId |
| amend(eventId,expectedRevision,...) | 仅 PREPARING/GATHERING 允许调整名单/角色；受影响旧意图失效并安全退出，不能直接清旧参与状态 |
| cancel(eventId,expectedRevision) | 立即转收束、禁止新派发，随后逐人结清；重复取消返回当前状态 |
| create/update/cancelSchedule(...) | 校验同一权限与定义，变更 scheduleRevision，未触发时不预约身体/场地 |

start 的 requestId 绑定世界、调用方、命令类型和参数摘要；相同请求返回同 eventId，不同参数复用 ID 拒绝。源码核对表明当前128条requests属于PublicWork专用记录，并非可直接复用的全局命令服务；活动不写入或复用其签发令牌。拟在ActivityStore复用其“有界签发/消费回执＋过期拒绝”的协议，暂按最多128条技术回执控制，不另建通用消息框架。实现须明确world/签发代次及高水位或等价证据：未见token不能当新请求，否则回收后会重复创建活动。活动活跃期间由实例关联确认原结果，已退休且回执过期的token拒绝重放；定时请求由持久occurrence身份核对，不混用UI令牌。

创建只发布完整关联，不同步启动身体；重入期间不能递归创建第二实例。预计人数、物资和空位是预检，最终执行必须重验。

定时方案（建议，见 §17）：持久 scheduleId/revision、世界游戏时间 dueAt、可选 recurrence、组织者/名单快照、defVersion、siteRef、上次 occurrenceKey。每次到期形成唯一 `scheduleId+revision+occurrenceIndex` 请求。修改/取消定时不自动取消已发起活动。

暂停不计时；加速按游戏时间到期。读档/大跨度越过多个时段时建议只在已配置 graceGameMinutes 窗口内尝试最近一次，不补办积压场次；旧场未结时跳过本次并保留原因。无资格组织者、场地或人数时记录未发起，不无限循环催人。定时不会复活已死亡/迁出的原名单，也不把不在名单中的 NPC 自动补入。

### 6.1 持久事实

| 参与记录 | eventId/npcId、participantEpoch、memberRevision、commandEpoch、roleId、attendanceState、jobId、原任务/恢复引用、已到场及有效参与累计、退出原因 |
| 阶段现场 | stageEpoch、entryFacts、requiredActorSet、开始/有效时间、动作回执集合、跳过/失败原因、已冻结结果 |

### 6.2 身份与互斥

组织者是活动指定的稳定 NPC；实际 speaker/performer 等角色单独分配，不能由“组织者”推导全部身体行为。组织者必须是名单中的合法成员，并分配定义所要求的角色；组织者与主持者可同人，但不强制所有活动如此。

每人同时最多一个已接受的群体活动出席承诺；与双人社交接受态互斥。重复受邀幂等，不新开第二 Job。冲突报告当前活动，不抢占另一场已承诺活动；未接受的邀请不抢身体。没有后备役、囚犯、奴隶或信仰角色模型，不为模仿环世界引入这些系统。

角色槽、实际位置、身体授权三者分开。角色接受不会自动取得座位；位置预约不等于到场；到场不等于已执行角色动作。运行中的必需角色不静默换人，替补需旧人停稳、角色代次提升及新任明确接受；第一版默认不运行中替补，作为 §17 的拟议限制。

## 7. 出席仲裁与原任务收束协议

### 7.1 已确认的选择规则

指定名单是玩家的 PERSONAL 参加意图，不给普通闲暇分数加一个足以压过全部任务的常量。成员保持原 SETTLEMENT 归属/上下文；FOLLOW/WAIT/RETURN 或正在调驻者不被活动暗中改为驻扎。

当活动、场地和必需角色预检可行后，名单中的合法成员建立有截止期限的出席承诺。自此暂停其新普通工作认领，当前工作由原拥有者安全收束；已有归还/监管恢复继续。确认停稳、效果已知且责任已结清/明确转交后，才开放 ACTIVITY Job 的身体授权。

普通工作 READY 不得反复收束已获准活动。危险/自卫/急救/紧急自理始终可抢占；普通饥渴尚未紧急时根据当前自理策略判断是否能参加，不能由活动随意提高其阈值。缺必要接缝时拒绝参加并显示原因，不临时绕过业务模块。

### 7.2 拟议握手接口与事实

| 操作 | 语义 |
|---|---|
| inspect(npcId,eventId) | 纯组合查询：成员/命令版本、当前身体、Job、Claims、义务、效果状态、能力；返回 READY/WAIT/REJECTED/UNKNOWN 及原因/依赖版本 |
| requestQuiesce(intent,expectedFacts) | 在原拥有者登记与 event/participantEpoch 绑定的收束请求；冻结旧普通续工，不消费活动资产 |
| observeQuiesce(token) | 返回仍在执行/正在收尾/安全可交接/阻塞；附 bodyStopFact、effectFact、未结责任引用及恢复点 |
| acceptAttendance(token) | 同一正常仲裁周期重验上述事实/版本，提交角色及参加 Job 关联，再排入后续 Session 准入 |
| withdrawIntent(token,reason) | 取消尚未启用的参加意图；保留原清理，原任务仅按仍有效的恢复意图恢复 |

`bodyStopped`、`effectsKnown`、`obligationsSafe` 是独立字段，不能以 Job.state==SUSPENDED 或“队列空”代替。安全回执不能由活动协调器伪造，包含旧 jobId/业务版本/stopAttempt/commandEpoch，过期即重新查询。

ActivityAttendance只统一请求/观察结果，不统一各业务的收束算法。采用固定业务适配表，不能用“遍历所有有stop函数的模块”发现能力。适配能力分别为只读识别、请求安全收束、核验安全结果、按原规则恢复；缺哪项就返回具体UNSUPPORTED/BLOCKED，不以pcall吞错或按函数存在推断支持。

准入的`obligationsSafe`须逐一处理该NPC所有仍相关的Job/Claims/义务，而不是只检查当前身体任务。无Runtime当前任务仍可能有暂停持料Job；没有Job也不证明没有独立监管义务。适配表必须覆盖：制作、HAUL（包含配送）、SELF_CARE内的阅读/生活、COOKING；未来业务在明确提供契约前拒绝参加。

同一参与代次最多一个有效收束令牌；先提交出席意图/旧任务引用，再交原业务发停止。原业务负责安全收尾的身体执行；活动不能在QUIESCING中先起自己的移动。接到停止通知仍核验原件/义务事实；只有全量相关责任通过后才提交准入。最后准入与后续Session启动均重验命令/成员/Claims版本，避免读取后世界变化。

当前停止回执经Boot的`taskStopped`链进入自理等业务，恢复经TaskPersistence固定入口处理。活动接入必须保留已有回调顺序/失败返回，增加单次幂等参与处理；不能覆盖成自己的唯一处理器，也不为此引入新的全局事件总线。单个活动结果未知应隔离该参与者/资产；已有保存屏障本身失败仍遵守现有全局保护，不能冒充局部错误放开。

收束过程中玩家新命令提升现有命令代次，旧出席意图失效；不得在命令结束后自行恢复旧活动。无进展看门狗撤销此次参加，不释放旧 Claims，不把它记作已安全退出。

### 7.3 各责任的明确准入条件

| 原状态 | 原拥有者必须做的事 | 可以参加的时点；失败处理 |
|---|---|---|
| 无任务/原地观察/闲暇 | 正常停止，完成家具起身及双人社交释放 | 身体停稳及相关位置声明释放后；不能跳过起身 |
| 自主睡眠/休息 | 沿当前自理策略与安全退出协议，不因邀请直接清疲劳/强行起身 | 能正常结束且无紧急恢复需求才参加；强制叫醒策略未授权 |
| 制作未取料/未启动 | 撤销无效果准备，保留可恢复业务安排 | 身体停稳、无未结原件后可参加 |
| 制作已持料/工具/产物 | 到安全边界核对已发生效果，将原件交付/归还或按业务已支持协议唯一交接 | 不能只暂停 Job 携料去活动；无法结清则退出本次名单 |
| 搬运/配送 | 已取原件沿现有交付/返仓收尾；未取部分按业务撤回，订单剩余量仍由原权威处理 | 携货及容量责任结清、身体停稳后；不额外复制或重开原单 |
| 读书/研习 | 原版停止、核对页数与效果、归还同一原件、释放借阅责任 | 书已归还后；知识与已读页数不回滚 |
| 做饭/炉具监管 | 完成本批安全收尾，或现有接管协议确认新唯一责任人/设备/原件关联；自有炉具停火也须实际复验 | 无待监管、持物及未结义务才参加；仅预约接班者不放行，不能擅关玩家炉具 |
| 已有归还/恢复义务 | 完成当前责任，不领取无关普通单 | 无法结清时保留原因与原责任，不让活动锁住其身体 |
| 效果 UNKNOWN | 原业务隔离核对 | 不参加普通活动；身体已停可进行已获准的撤离/自救 |
| 危险/紧急自理 | 立即按当前身体协议停止/避险/自理 | 本次参加取消；不自动补进活动 |

普通收束不是取消整个公共订单。原 Job 可安全挂起或结清，后续继续/重领由原业务决定；活动不能擅自设订单 DONE。烹饪/搬运/阅读适配器由对应模块提供，需与另一会话正在修复的代码接口对齐，不并行重写其业务。

### 7.4 完成/取消后的恢复

活动退出时先停稳本人的动作、结清活动占用与物资，再撤销出席承诺。若原恢复引用仍合法且命令代次未变，发布原 Job 的恢复候选；若该 Job 已被结清/合法交接给他人，仅回普通仲裁，不能抢回同一原件。活动不直接恢复旧动作队列，不复活过期意图。

恢复引用只保留原jobId/版本、原拥有者签发的恢复资格及命令代次；原业务仍是恢复的唯一裁决者。活动不再保存一份材料manifest、炉具恢复步骤或订单完成量。收束失败也只撤销参加意图，不能调用一个通用resume把仍在归还中的Job重新开工。

邀请失效/召集取消也走相同规则。原业务收束已产生的进度和物理效果不回滚，已经归还的原件不能为了“恢复原状”重新强取。

## 8. 场地、容量和预约

场地使用共享设施观察，活动类型可引用 CAMPFIRE/DINING_TABLE/GRAVE/MUSIC_PLAYER/OPEN_YARD 标签；标签表示候选能力，不代表对应动作已经支持。站位候选来自据点范围内已加载、安全的同层有效位置；楼层间移动沿已有路径，最终共同参与必须满足该阶段的同层/视线/距离条件。

角色位置策略可以是主持位、环绕站位、合法家具座位；第一版只启用已具备完整进入/退出适配的策略。不得按一个圆圈的几何面积承诺容量。位置选择复验门口、路径、占用、设施隐私/专用策略、对象部件/整件身份及现有 Claims，不能占用其他活动或床位预约。

资源申请顺序固定为场地用途槽→必需角色位→普通位置→该阶段资产/容量声明；有界批次失败时只撤销本次尚无物理效果的申请。场地用途槽不等于独占整间房，玩家仍可走动/改设施，到场和消费前复验。

等待原责任收束时只保留有期限、无物理效果的准备预约；未赴场者超时可撤销。人已坐下或原件已交入活动托管后，租期到期不能替代身体停稳/责任结清。人数变化优先补空位，不重排已到场全员；相同失败位置沿现有对象/版本退避。

UNKNOWN/UNLOADED/STALE/UNAVAILABLE 分开。召集期未知等观察且不计人数，至截止不足则取消；进行中失去可观察性按阶段策略停止有效计时并请求安全收束，不把目标当空地/原件丢失，也不远程销毁/释放责任。

## 9. 活动状态机

| 相位 | 允许行为与退出条件 |
|---|---|
| PREPARING | 预检和准备无效果预约；不足则明确取消/拒绝，不先中断所有人的工作 |
| GATHERING | 登记名单、收束原工作、逐人赴场；收集到场事实，按已配置开场规则进入 RUNNING |
| RUNNING | 有限 stage 序列；按角色事实、有效时长和动作回执推进；本阶段不满足则有界等待/失败/收束 |
| WINDING_DOWN | 拒绝新加入、冻结各人的有效参与终点；各自停止与收尾，结果可核对，不再开新表演/消费 |
| SETTLING | 参与执行已停止；核对/提交收益、未结责任、恢复关系；UNKNOWN 保留隔离引用 |
| CLOSED | 只在身体、Claims、义务、效果与恢复关系均已结清后可达；再按回收协议退休 |

outcome 单独存 COMPLETED/INCOMPLETE/CANCELLED/FAILED，不因选择 outcome 就删记录。参与者的效果核对阻塞可令活动留在 SETTLING，但已安全退出且无自身未知责任的人可继续普通生活，不全员冻结。任何相位发生保存屏障都禁止新派发，按 §12处理。

### 9.1 开场、阶段交接与人数

开场至少满足：组织者与全部必需角色已接受、实际到场且身体在合法执行会话；有效人数达到 quorum；地点与必需物资事实新鲜；没有保存屏障/活动取消。角色 min 人数和 quorum 分别校验，不能让十名观众替代缺席主持。

建议默认“名单中全部邀请均已有明确接受/拒绝决定，且所有接受者已到场，则可提前开场；到召集截止时只要满足必需角色和 quorum 则开场，否则取消”。资格观察/原工作收束仍未决定者属于未决，不能只因已到一人而触发提前开场。这是 §17 的玩法提案，不从“参考环世界”推导成用户已批准规则。截止与目标时长由具体活动定义，不给所有活动写死同一秒数。

进入下一阶段前：旧阶段不再派新动作→核对旧动作已完成或停止→关闭旧阶段代次→按新阶段角色和资源重新验证→授权各自新行为。坐姿连续等适配若能证明同 Session 安全延续，可以保留姿态，不必每阶段强制起身；未验证组合不能默认连续。

必需角色中途退出建议结束为 INCOMPLETE；非必需者退出不必取消全场，后续人数按定义持续门判断。迟到建议仅在标记允许的阶段边界准入，不补之前时长；已退出者第一版不自动重入，避免工作/活动震荡。

## 10. 参与者状态、时间与回调

参与业务状态：INVITED→ASSESSING→QUIESCING→ADMITTED→TRAVELLING→READY→PARTICIPATING→LEAVING→SETTLED。邀请拒绝、名单撤回、超时均附终止原因；尚未执行者可直接结清无效果预约，已执行者必须经过 LEAVING。停止未知和效果未知作为独立维度，不造“失败即释放”捷径。

每人以自身 ACTIVITY Job 创建微型行为树：验资格→接近→复验到场→等阶段许可→执行角色动作→退出/归还。协调器仅投影期望角色阶段，由本人适配器消费；不得一个人的回调直接移动/清理另一个人。

通知必带 worldId、eventId、controlEpoch、npcId、participantEpoch、stageEpoch、jobId、actionAttemptId 及适用的 Claims 版本。eventRevision 用于命令乐观校验，普通参与计数变化不能令其他人的合法回执过期；controlEpoch 仅在取消等控制失效边界提升。阶段进入时冻结 requiredActorSet；迟到者不会追溯扩大已签发必需回执集合，新需求只能显式形成新阶段代次。控制通知失配拒绝；旧动作已实际发生的效果通知仍交原业务按 attempt 归账，不能简单丢弃事实，也不能推进新阶段或释放新预约。

游戏时间用于活动期限、持续参与和冷却；未暂停现实时间只用于无进展/原生动作看门狗。现实看门狗重进后重建，不保存绝对墙钟。有效参与仅累计“本阶段有授权、实际到场、角色条件成立”的游戏时间；缺观察、暂停、停止中不计。

倍速下按已确认连续执行区间计时；无法证明某跨帧区间持续有效时不补发收益。一次时间推进最多跨一个需新动作/资源确认的阶段，其余须下一正常预算轮，不能一次跳时补完多段消费。

## 11. 参与完成度、质量与效果

三类数据独立：个人参与记录、全场质量、实际原版消费/生理效果。框架不以“动画播放过”结算食物，也不因活动取消回滚原版已吃/已喝部分。

每阶段记录个人有效参与时长、目标时长、角色完成回执、参加资格和结束原因。有时长阶段的完成比例为 clamp(有效时长/目标时长,0,1)；动作阶段由声明的必需回执决定完成；二者兼有必须同时满足。跨阶段按定义的非负权重归一汇总，未进入/跳过阶段不记完成；分母使用开始时冻结的应参与阶段，不因早退缩小分母获取满额。无有效参与者为0。

质量因素读取实际角色完成、有效人数/时段、设施及活动消耗事实，各因素返回数值、单位、上下界、证据状态和原因。必须因素未知则结果待核对，不填0冒充已知；可选未知因素显示“未计入”，不能伪装完整预估。预览与实际结果分开，预览不给成功保证。

效果使用稳定键 `eventId+npcId+effectId+ruleVersion`，全场一次效果使用明确 event scope 键；不能包含会因重试变化的 Session token。先冻结个人结束事实和结果版本，再准备效果回执、执行、观察提交。APPLIED 重复请求只确认原结果；APPLYING 中断且效果无法辨认则 UNKNOWN，不重放或反向补偿。

当前“持久化标记→写角色属性→完成标记”不具跨文件原子性，框架不宣称 exactly-once 生理效果；目标是已确认不重复、未知不自动重复。有原生进食恢复已产生的收益时，额外活动效果不得再次按同一消费重复发放。

推荐先实现有界、可解释的质量评估及效果协议，不默认随机抽坏结果/负面心情，也不默认每次叠加永久 Buff。具体品质公式、最低收益门槛、冷却、士气模型和持续时间属于 A5/用户决策，不在此草案偷偷批准。

## 12. 保存、恢复、失败与清理矩阵

首版策略（§17已确认）：保存暂停活动派发，继续游戏与重进均收束原现场，不自动续演。普通保存不强制提前归还所有原件，不阻塞引擎保存。可准备的退出沿现有 prepare/stop/capture 屏障；原生 OnSave 只捕获当前事实，不能等待后续 tick。

持久化：活动业务事实、各人实际参与、角色/阶段代次、已知消费/效果、剩余责任与定时 occurrence。读档顺序：校验格式/定义版本→重建共享声明与义务关系→核对原生/原件事实→生成收束或责任恢复候选→正常仲裁授予新 Session。未知定义保留实例与责任、禁新执行；通用停止可用则安全停止，专属资产恢复缺失则隔离，不静默删除。

当前格式继续支持正常恢复，旧格式无显式支持时明确拒绝自动启用；不得伪造旧活动兼容。开发阶段不承诺崩溃恢复；正式发布须另定义检查点/数据丢失窗口并验证，不能以存入 ModData 宣称零损失。

| 事件 | 活动/个人处理 | 不得自动做的事 |
|---|---|---|
| 玩家取消/召集超时 | 停新派发，逐人停止/归还/恢复，保留已发生效果 | 删除携货责任、回滚消费 |
| 单人迟到/早退 | 取消其准入或冻结完成度，按角色要求决定全场是否继续 | 补全程收益、挪用其他人的角色位 |
| 组织者/必需角色死亡 | 全场不完整收束，死亡资产沿既有责任处理 | 删除尸体库存声明或自动指定新人 |
| 名单成员调驻/跟随新命令 | 失效出席意图，按命令代次退出 | 自动改回驻扎并拉回活动 |
| 设施拆除/改私有/同坐标替换 | 禁新用，逐人安全退出；原对象身份仍据实核对 | 按坐标继承原预约或原件 |
| 场地卸载/观察过期 | 停有效计时、等预算内复验/收束，保留责任 | 把未知当空位或丢失物品 |
| 据点撤销/权限丢失 | 禁新发起/参加，保留必要收尾权限与责任 | 顺带实现整个据点解散系统 |
| 身体停止超时 | 留停止阻塞及诊断；核验安全后才可新授权 | 将超时当 stopped=true |
| 效果未知而身体已停 | 隔离个人/资产或相关结果；允许已确认安全的自救 | 自动重试消费或冻结所有无关成员 |
| 定义/适配器缺失 | 禁新执行、保留未结数据、报告依赖 | 降级成计时成功、换类型重造物品 |

安全参与互斥在本人停止与活动责任结清后解除；活动整体 CLOSED 更晚，不阻止已结清成员继续生活。实例只有所有 Job、声明、义务、效果与恢复关系结清才退休，保留所需有界技术回执；没有永久完整活动日志这一新增功能。

## 13. 性能与诊断

活动服务复用既有 Boot 生命周期、轮转/PlanningWake/任务预算和 RuntimeMetrics 采样，不开每 NPC 定时器。按 scope 索引活动和名单，按 npcId 查唯一出席；变化只置脏和排队，事件回调不寻路/消费。

每轮分别受候选、资格、场地观察、位置分配、寻路请求、参与者推进及结果处理额度约束，额度使用既有全局预算剩余额；无余量续接游标而非本轮补做。不得建立 event×全员×全场地的逐帧扫描，也不一次校验完整大名单阻塞帧。

实例可承载多 NPC，但数量同时受名册、可用位置、JobStore 与全局预算限制。超额明确拒绝/等待，不抛弃未结实例或承诺某个规模。UI快照仅有订阅时按变更合并，不轮询所有人原生属性。

实施计划必须写清event/participant/action-receipt/schedule各表上限与回收条件，并区分技术容量和玩法人数；本草案不擅自提高现有容量。无未结记录可回收时只拒绝新活动。每阶段只保留恢复所需结果与累计，不把每帧观察或每轮气泡永久写档；实例按角色集合/阶段查结果，不复制完整历史以方便UI。

诊断按 Activity/Attendance/Sites/Results 分桶，复用按需采样；记录阶段原因、收束等待、路径失败、过期回执、重复请求、UNKNOWN及参与计数。详细日志默认关，诊断只放原版 Debug 子菜单。性能验收复用现有场景与50ms/秒口径，单次尖峰单独测，不因设计写“可扩展”就判达标。

## 14. A4 玩家流程与投影

发起草稿字段：活动类型、地点、组织者、角色分配、参加名单；名单支持从当前据点成员一次选择并排除个别人，不要求逐人点击才能组织群体。发起时固定名单快照，不把以后加入据点的成员静默补入本场。时间方式可为立即或已批准的定时。显示硬阻断、可等待项、预计参加范围与质量因素；NPC 参加原因使用真名和本地化文案，不露出内部技术ID。预览不为玩家扫描/保证无限远未加载世界。

运行详情显示活动阶段、实际到场/参加/收束人数，个人的还书/交货/监管/路上/参与/退出原因，必需角色缺口、召集截止和结果核对状态。只对活动时限显示倒计时，不编造整段归还/寻路 ETA。取消按钮消费命令返回，关闭窗口释放订阅但不取消活动。

UI完全遵守[当前UI基础契约](../../ui-architecture.md)，复用 State/Layout/Text/CachedList/主题和原版输入；长名单滚动、失效选中和取消结果可见，关闭/换世界释放订阅。具体线框/尺寸不在本轮定稿，无新增浏览器界面。

## 16. 验收与实际接入前置

设计审查先确认：定义/实例隔离、状态与回执一一对应、资源唯一权威、已确认出席政策、责任处理不依赖未实现接口、用户可理解阻塞和结果。

开发只保留风险相关的最小回归，不为每字段写镜像测试：

1. 两场活动争一人/一座位、双人社交冲突、重复发起及旧代次回执：不双领、不清新会话。
2. 搬运持货、借书、炉具监管与制作提交中受邀：责任未安全处理不参加；召集取消后旧任务恢复不丢失/重放。
3. 必需角色缺席、迟到/早退、阶段超时与部分消费：完成度/结果据实，超时不冒充成功。
4. 保存/重进及效果提交中断：不续演旧动作、未知不重放、定时不重复触发，旧定义缺失保留责任。

集中实机只验收完整体验：多人实际到场和站位、原生动作/退出、工作安全让位与恢复、真实消费/效果、正常保存重进；再以现有性能场景采样。未运行分别写未验证，不要求用户逐内部模块测试。

开始实施前须核对另一会话最新 P4/搬运/生活接口；现有源码评审中的哈希只代表当时截点。缺少业务安全收束能力先明确阻断/适配，不能为赶活动功能复制其控制器。A1/A2剩余协议常量集中与设施观察计时仅在活动接缝需要时收尾，不借机大改闲暇选择策略。
