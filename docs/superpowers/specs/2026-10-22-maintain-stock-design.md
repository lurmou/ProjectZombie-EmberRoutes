首版单人、本地世界执行者裁决；只支持现有已适配的固定物品配方，使用[按需配方链](2026-10-22-production-chain-design.md)。不新增自动伐木/采集、采购、跨据点调拨、全工种调度、离线宏观生产或行为树框架。最低存量不是锁住物资的保护线，其他合法任务仍可取用。

每条规则显式绑定据点、产品fullType、根配方、NPC和可选根平台；同据点同产品最多一条未删除规则。NPC用稳定ID。首版不自动更换NPC、配方或根平台；配方链内部的既有替代材料和前置路线选择仍按原设计执行。NPC忙时等待，不能调用cancelAll抢占其任务。

## 3. 方案选择和核心不变量

采用“持续库存规则 + 一次有限补货周期 + 现有生产父单”。不把永续规则本身当可无限续长的生产单，也不在每次盘点回调里直接发一张新单。

比较：反复生成普通定额单虽然改动小，但易重复和读档失配；立即建设脱离NPC的通用工单中心会扩大本轮范围。选择小型需求监督器，现有生产和物流继续拥有执行与资产权威。

必须保持：

1. 同一规则最多一个尚未收束的周期；同一周期最多一个生产父单，链子节点不另占补货周期。
2. 规则只能提交需求，不能直接移动角色、入队动作、扣库存、释放别人的声明或凭汇总重造物品。
3. 周期关闭以执行器已确认收束、资产义务可解释为条件；暂停、异常、NPC离线、取消请求均不等于已关闭。
4. 有未知库存、未知提交、孤立订单或不一致关联时停止新派单，不能按零库存重新补货。
5. 库存变化只置脏；统一调度中重新校验后决策，防止同步回调重入建单。

## 4. 库存口径与覆盖要求

沿用[仓储读取契约](../../settlement-storage-architecture.md)：库存P为本据点已登记、当前有读取权限的容器直接层内指定fullType的InventoryItem实例件数。错放物品计入；不扣其他任务预留；不把工具的剩余次数、液体体积或重量换算为件数。

不含玩家或NPC背包、未登记箱、容器内的背包内容、地面物品、未加载物资。NPC搬运途中暂不在仓内的物品不计P。由补货周期自己持有的产物不因此另建周期；其他普通物流的在途物品首版不预测计入，因此允许其随后入库带来额外库存。界面必须说明这一口径，不承诺绝不超量。

只接受当前世界、当前settlementRevision下READY且complete=true的视图。WarehouseIndex.candidates的complete要求unloaded/private/missing/limited均为0；READY本身不够。UPDATING、ERROR、NOT_REQUESTED、库存不稳定或旧代次均显示待盘点/受阻，旧数只可展示为过期值，不参与派单。

私人、停用或其他状态的成员如何被查询层列入覆盖检查，遵循现有成员和权限契约，不自行改变“complete”的含义。无法取得完整视图时宁可等待，不按局部已知数补满。数据刷新必须有界，不因规则要求完整就扫描未登记地图或强制加载区块。

两个据点可能共用容器。首版同产品的已启用规则，其当前登记成员容器集合不得相交；启用时验证，范围/登记变化后再次验证。相交时相关规则全部进入SCOPE_OVERLAP并停止新派单，现有周期安全暂停。不能只按不同settlementId就当成独立库存。检测包括未加载成员ID，不仅当前可读来源；同一物品被重复发现仍沿用仓储拒绝汇总的处理。

## 5. 缺口、手动工单与数量

没有活动周期、没有同据点同产品未收束的生产父单，并取得完整新盘点后：D=max(0,M-P)。M为目标，P为仓内实物数。D=0进入SATISFIED；D>0才准备新周期。规则存在但禁用时不派单。

M必须是1～9999的有限整数；删除或禁用用显式命令，不用0表示隐藏状态。根配方必须以该fullType为现有执行器认定的主产物；首版不依赖副产物维持另一目标。

每周期requested=min(D,32*yield,9999)，限制为最多32个根配方批次。按现有根配方yield向上取整实际target，不得超过当前记录及链规划器的上限；超过时返回明确限制错误，不截断成别的含义。若一个完整原版批次产量为y，差1也要做一批，界面显示预计多出y-1；不会拆毁或丢弃多出的原件。

同据点同产品的手动父单（含以该产品为根目标的配方链）未结束时，规则进入WAIT_EXISTING_ORDER。运行、缺料等待、用户暂停、待交付和需核对的单都算未收束，不另开补货单。只统计根目标，不能将链内木板节点当成“给仓库补木板”的独立承诺。手动单结束后等新盘点再计算D。首版不预测手动在途数量、不做P加承诺量的混合公式，以避免交付前后双计。

已有自动周期时，不因P再次降低就扩长原单或增加第二张单；该周期有限完成，再新盘点补剩余缺口。其他NPC后来启动同产品手动单时，自动周期在下一个安全批次边界进入WAIT_EXISTING_ORDER；手动单收束并新盘点后再决定继续或收尾。手动单不被自动规则取消。

## 6. 周期执行与安全边界

新周期继续通过现有Production/ProductionChain取得原件、完成真实前置制作并分类入库。父单只由绑定NPC顺序执行；保持现有四层链和有界搜索限制。不因为“自动”就绕过技能、已学配方、平台、负重、权限、容器过滤或容量检查。

在新周期开始、每个原版批次开始之前、后继链节点开始之前检查规则和可用盘点。检查发生于安全边界，不打断同步提交。若P>=M，停止派发下一批/节点，执行器完成已发生效果的交付及材料/工具归还，然后以TARGET_REACHED收束。前置节点已制成的中间品作为真实库存保留，不逆向回滚。

若0<D小于原父单剩余产量，不修改已持久化的父单目标；每批边界重验，达到M后提前收束。新一批开始前P还不足时允许完整一批，外部同时送货可能造成更多富余，不能许诺严格M或只有一批富余。

如果库存正在更新，只暂停新取料/新制作/新节点，已开始动作沿原协议完成或安全停止；确认的产物交付、必须的归还与安全清理仍允许进行，防止“等待盘点”阻止盘点所依赖的交付而死锁。

必须增加执行器专用的“需求已满足，收束剩余工作”入口，不能假装父单已经做到target，也不能由规则直接把状态改DONE。收束记录真实produced/delivered、结束原因和remaining；部分完成记录需在CraftRecord中有版本化合法表达。订单量未完成但规则目标已满足与用户取消必须可区分。

## 7. 持久化、去重和创建协议

在现有Registry世界根下增加maintainStock={format=1,revision,rules}，沿用当前世界保存体系，不另建定时文件或平行资产账本。规则标量字段固定为：

| 字段 | 契约 |
|---|---|
| id, settlementId, fullType | 稳定ID及唯一业务键 |
| recipeId, recipeSignature, npcId, surfaceId | 显式执行配置；手持配方surfaceId为空 |
| minimum, enabled, revision | 目标、启用意图、乐观修改版本 |
| nextCycle, activeCycle, deleting | 单调周期序号、未收束周期、删除墓碑 |
| activeCycle内容 | sequence、taskId、ruleRevision、phase、requested、snapshotRevision、settlementRevision |

phase仅允许PREPARED、ATTACHED、SETTLING、RECONCILE_REQUIRED。运行展示状态由规则、盘点和真实父单投影，不作为第二份执行状态机持久化。父单增加可选origin={kind="MAINTAIN_STOCK",ruleId,cycleSequence}，普通手动单保持原义。持久记录不能保存actor userdata、回调、快照全文或运行闭包。

创建必须顺序执行：

1. 集中命令入口重新验证世界、权限、ruleRevision、库存代次、唯一键、NPC是否可授予执行权；仅空闲时进入，不以Production内部的cancelAll代替仲裁。
2. 分配稳定taskId，持久记录PREPARED关联；同规则在此刻即不能再申请周期。
3. 将taskId和origin传给生产创建入口。入口验证taskId尚未使用，先建立双向关联和记录，再允许认领后的真实动作启动。
4. 已有相同taskId且origin完全一致时返回该单，不能再次run；同ID异来源直接冲突。关联成功写ATTACHED。
5. 确认创建前失败且不存在父单、原件声明或效果时可撤销PREPARED；创建返回错误不等于未创建，必须按taskId找回真实记录，不能清空关联后重试。

现有Production.execute会在内部生成ID，且可能记录建好后规划失败。必须扩展受校验的创建上下文及查询入口，实现上述协议，不能仅在返回STARTED后才写rule.activeTask。任何未知创建结果进核对。

加载时校验双向关联、唯一业务键、序号、绑定NPC和目标产品；PREPARED无单且能确认无声明/效果才可撤销，否则核对。父单有origin但规则缺失或关联错乱时隔离父单，不悄悄重新建规则。一个周期发现多个父单、版本不支持或字段非法均明确报错，不能丢记录“修复”。

已DONE/CANCELLED或需求满足收束的单，只在义务已释放后关闭周期。关闭后先请求一次新的WarehouseIndex.refresh；必须等该请求之后的完整READY，再允许下一周期，避免旧库存触发补做。刷新代次通过查询服务显式返回/通知，不能拿readAt当现实时间或事务序号。恢复后无条件丢弃运行时快照，重新订阅、核对和盘点。

此协议保障正常运行与正常保存的幂等续接；现有跨文件持久化不具备崩溃事务，不宣称强退零损失。uncertain或COMMITTING沿原门禁核对，不能补做或自动换NPC。

## 8. 命令与用户操作语义

对外只经StockService.command(actor,settlementId,command,payload)修改；payload提供ruleId和expectedRevision。create提供完整配置；update只允许minimum；enable/disable、retry、delete各自独立。绑定NPC/产品/配方/平台首版创建后不可修改，需安全删除旧规则再建新规则。校验失败不部分写入。查询/订阅返回脱离持久表的只读DTO；未来MP沿命令边界重验，首版明确SP_ONLY。

| 操作/事件 | 固定行为 |
|---|---|
| 创建 | 默认启用；需要明确点击确认，保存规则后盘点，不能由UI直接run |
| 禁用 | 立即禁止新派发，活动周期按生产停止协议安全暂停；保留原件、关联及归还义务 |
| 启用 | 先核对旧周期和盘点，再继续同一父单；不是另开一单 |
| 提高目标 | 更新revision；旧周期仍有限，不扩目标，结束后新盘点再补 |
| 降低目标 | 下个安全边界按新M判断，满足则交付归还后提前收束；不能强制撤回已开始提交 |
| 删除 | 先禁用并置deleting；无活动周期可删，有活动则按取消/归还协议收束，未知效果保留墓碑供核对 |
| 用户暂停自动父单 | 同时将所属规则禁用；避免监督器自动恢复用户刚暂停的单 |
| 用户取消自动父单 | 同时禁用规则并走归还收束；不立即生成替代单 |
| 缺料/工具、空间不足 | 保留同周期等待；对应库存/设施事件唤醒，不能循环run |
| NPC离线/受伤/忙、平台失效 | 等待/阻断，显式原因；不替换NPC或平台、不抢工作 |
| 配方签名变化 | RECIPE_CHANGED，停止新派发；旧物资按原记录恢复，不自动换配方；重建规则前先收束 |
| 权限丢失、据点删除/范围变化 | 停止新动作，按既有权限与资产恢复协议收束；恢复权限后重验，不沿用旧来源 |
| 世界切换/读档 | 取消运行令牌、释放订阅、丢快照；旧世界回调无权唤醒或修改新世界 |

retry只重开可恢复的检查，不能清除uncertain、跳过归还、放宽配方支持或伪造完成。删除后仍有不可归还原件时必须显示待处理，不吞掉记录。

## 9. 调度、生命周期及预算

监督器是后台业务服务，关闭制作/仓储窗口不会停规则；窗口只消费DTO。每据点至多一个后台WarehouseIndex.watch，由启用规则或未收束周期共同持有；最后消费者退出、世界切换时释放。禁用但仍有资产义务的周期可保留必要读取，不能因UI关闭停止归还。

复用现有tick服务入口，单一全局轮转队列，禁止每规则/每NPC新建计时器。每tick最多评估4条脏规则、提交1次创建或恢复请求；外部事件合并为脏标记，不同步派发。仓储沿现有全局预算128推进，不因规则数量乘倍；配方链沿既有规划预算。

成员重叠检查也有界：每tick最多处理64个containerId，完成前阻止启用/新派单；不在按钮或render里一次扫描所有规则。首版每据点最多32条规则，全世界最多128条；达到上限明确拒绝，不隐式替换旧规则。已删除且无义务的条目可清除，不保存无界历史周期列表。

事件来源：完整盘点发布、LaborSignals、规则命令、成员/权限变化、NPC可用性、设施登记变化、正常保存完成。缺少可用事件的条件用统一低频复验：每条等待规则最短60个未暂停游戏秒，轮转有界；禁止按OnTick次数换算秒，接现有可靠游戏时间适配或新增单一时间适配。游戏暂停时不得推进派单或重试。手动retry受每规则1个未暂停游戏秒节流。库存ERROR按查询层契约保持显式，需用户retry，不无限refresh。

同NPC多规则按最久等待先服务、ruleId打破同序；只在可授予工作时竞争，不抢手动工作。每周期至多32个根配方批次，按第5节计算，避免单规则长期占用NPC。完成后该规则排到队尾。整个链所需前置工作不承诺32批内完成。等待顺序为运行时轮转信息，读档后以ruleId稳定重建；饥饿时间不伪装成持久时钟。此处是首版后台补货公平性，不替代未来效用仲裁；统一任务控制器接入后沿同一候选边界迁移，不再建第二个执行权控制器。

## 12. 保存屏障与恢复顺序

保存开始先停StockService派发，再沿现有生产保存协议停止/核对动作，记录规则与周期。保存失败不清activeCycle、不开始新单。保存成功后先恢复生产记录与原件声明，再恢复规则关联，完成新盘点后把旧周期继续请求交给同一执行入口。

读档时enabled只表示用户启用意图，不等于直接重放run。user禁用、deleting、需核对的规则不能被自动恢复。活动单已完成但规则尚未更新时，通过双向链接确认收束，再刷新，而不是补做。NPC尚未绑定、操作者未就绪或世界身份不符时等待，不借用玩家索引或偷偷改requester。
