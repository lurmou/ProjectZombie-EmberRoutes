# 仓储配送执行链重构设计

日期：2026-10-27。状态：对话中确认方向；细节待核实。此文是既有 NPC 架构的从属设计，不修改在线需求。

## 范围与依据

保留仓储选货、购物车和呼叫配送入口，重构其后台执行链。当前单人本地世界唯一裁决；未来多人只保留适配边界。在线需求于本轮读取，要求统一身体会话、物理库存、按负重分批与原件责任；没有规定本功能的追送距离或僵尸观察规则，以下按用户本轮决定执行。

已确认：配送员可跟随玩家到据点边界外 50 格；玩家超出时停止追送，携带原件安全返回据点并归还；无法安全返回时保留责任并等待恢复。配送员在据点外看到僵尸时蹲行；不再看到时或回到据点时退出蹲行。玩家移动时不交付，玩家停下并确认接近后才交付；玩家背包放不下时采纳选项 1（等待玩家腾空间），物品保留在配送员身上承担责任，暂停交付并向玩家提示，待玩家整理出空间后继续交付，避免未经玩家选择丢在地上。蹲行不覆盖危险仲裁，不保证安全。50 格沿现有据点区域边界的平面距离计算；楼层不能用于绕过取货、交付接近性检查。

## 方案与契约

- 订单使用稳定 ID 和版本化、可持久化的业务事实，持久数据不保存 Lua 闭包或引擎 userdata。提交订单不指定 NPC；公共候选由统一派工与 hauling 优先级仲裁。订单已接受不等于已分配或已送达。
- 单次配送段只有一个执行者与结算者，保留订单、Job、Session 和资源声明的不同职责。经现有 TaskRuntime/TaskController 获得身体能力；不直接调用旧式移动、停止或绕过控制修改姿态。
- 复用现有搬运原件声明、原生转移动作及效果回执，先验证目标为移动玩家时的契约；必要时扩展适配器，不能假定现有固定容器终点直接支持玩家。按照实际可承载重量分批，单件无法搬运时阻断并反馈，不虚报完成。
- 取货与交付前重新验证世界、成员权限、据点、源容器及物品实例、目标玩家、同层和可达性；每件确认转移效果后结算。玩家或其他任务已移动原件时，不重新创建；无法确认效果时保留声明并待核对。
- 玩家位置变化或路径失败才有限度更新目标，禁止每 tick 重发；到达判定必须考虑同层、接近与实际停稳。玩家移动时不开始交付；每次转移前复验，若玩家再次移动则暂停余下交付并保留未交付原件责任。背包放不下时暂停交付，物品保留在配送员身上承担责任，向玩家提示整理空间；玩家停稳且空间充足时继续交付；若玩家离开或超限则走安全返仓。寻路失败、安全抢占和正常任务切换进入统一停止协议，不把原件责任随 Session 释放。
- 看到僵尸的实际观察语义、有效时效及蹲行原生调用，实施前先追踪 ProjectRemnants 对应完整链路并核对当前安装版 Lua/JAR；仅观察到有效威胁时进入蹲行，观察不可用不能伪称看见或安全。原生适配未证实时标记阻断，不猜接口。
- 超出距离撤回未取部分；已取部分由原责任 NPC 经正常路径带回可重验的允许存储点。退库受阻时保留原件、声明和待恢复状态；仅实际确认归还才结算，不做远程瞬移回箱。不得因失去 NPC 绑定而删除责任。
- 保存、世界切换、死亡、取消、陈旧回调和未知动作效果均走现有停稳与持久恢复协议；读取不支持的旧格式时保留数据和实物，不推测位置、不自动迁移。旧 DeliveryService 内存订单无法假定跨世界保存；上线前核查正在执行订单的安全处置，不能靠 reset 丢弃责任。

## 交给执行者的具体设计

### 一、对象及唯一归属

| 对象 | 保存内容 | 所有者与不变量 |
|---|---|---|
| 配送 Order | 稳定 orderId、据点 ID、请求者稳定身份、物品类型和请求数量、已确认交付/撤回数量、版本及状态 | 订单不指定工人；它记录需求，不等同原件声明；只保存标量及可序列化表 |
| 公共 Offer | 订单 ID、版本、据点、hauling 类别、可分配段 | 派生索引，可重建；同一订单段同一时刻最多一个活动 Job |
| 配送 Job | 稳定 jobId、orderId、执行 NPC ID、代次、阶段、已选原件 ID 与来源 ID、收尾方式、逐件效果和恢复事实 | 唯一执行者；执行会话中断后 Job 与携货责任仍存在；稳定 ID 不使用玩家槽位 |
| Session | 任务控制器的代次、身体能力和停稳证据 | 同一 NPC 同时仅一个身体会话；新会话不得复用旧回调能力 |
| Claim / 逐件事实 | 具体 item ID 的唯一声明、来源、位置阶段、最后一次动作 ID 与效果 | 共用 LaborStore/LaborClaims；声明只在效果确认后的结算步骤释放，UNKNOWN 不释放 |

Order、Job 与 Claim 是不同对象；不可另建一个在 DeliveryService 内自行裁决的库存账本。下单时按类型和数量表达需求；取货前选择并认领具体原件。可用数量包括其他任务声明在内统一计算，库存快照仅作提示。提交下单、成功认领、实际收货是三个不同事实。

### 二、接线约束及当前源码

1. `UI/WarehousePage.lua:dispatchDeliveryCart()` 经 `PublicWork.createDeliveryOrder(actor,scope,items)` 提交；保留这个入口。`ORDER_CREATED` 仅代表需求已接受，失败时不要清空购物车。调用方需读取当前版本的真实返回码和翻译。
2. `PublicWork.lua` 已注册 `haulingProvider`，`PublicWorkProviders.lua` 按 category 单项注册，同 category 的后注册会覆盖前者。配送必须并入现有 hauling provider 的发现、领取和释放路径，或在不覆盖现有 provider 的前提下明确拆分实现；不能简单注册第二个 `hauling` 覆盖物流，也不能另开选人 tick。
3. `Work.assign(actor,npcId,intent)`、`WorkAgent.lua` 和 `HaulAgent.lua` 当前按 `producer='LOGISTICS'` 路由，且现有 `HaulManifest.valid()` 强制 `AUTO_STORAGE` 和固定 source/destination。配送不能伪装成普通仓储目标；应沿统一执行入口增加明确的配送类型、持久 payload 校验与恢复注册，或者有证据地扩展既有协议，确保物流既有任务仍按原格式工作。
4. `WorkTransfer.item` 当前以可重验的实体容器端点验证接近、原版动作、转移结果；玩家背包与地面并不自动满足该契约。设计专用受控交付适配：仍使用原版/已核实的转移入口、身体能力、逐件效果回执和实例位置复验。脚边地块实际效果无法判定时进入待核对；禁止假造容器 ID、绕开回执或远程放回。
5. `TaskRuntime` / `TaskController` 负责唯一身体会话与停稳屏障；`BusinessJobs` / `TaskJobs`、`LaborStore` / `LaborClaims` 与 `TaskPersistence` 的当前格式共同承担持久责任、恢复与退休。实现者先检查真实接口和格式，再做版本化变更与重进校验；不能只把字段写入 ModData 就宣称可恢复。
6. 旧 `DeliveryService.tick` 的选人、移动、转移、归还和姿态旁路须在新链路完整接管后停用，不能两条执行链同时消费订单。切换时检查运行中的旧内存订单：未取得原件可安全撤回；已取得或状态不明的现场须先核验并保留责任，不能由 reset 清空或假定可迁移。

### 三、状态与结算

以下是行为契约，状态名字可以与现有状态模型适配；不得创建第二套独立控制器。

| 阶段 | 进入条件 | 退出或失败 |
|---|---|---|
| 待领取 | 订单有效、需求未满足 | 公共派工领取；无人可用则等待 |
| 准备/认领 | 重验订单版本、成员资格和本批原件 | 共享声明成功后准备执行；冲突则安全退回待领取，不能占有部分声明 |
| 取货 | 持有效 Session、声明和源容器权限 | 同层、真实可接近后逐件原生转移并确认来源→NPC；容量不足本批先交付，单件不可搬运则阻断 |
| 追送 | 有已取原件，玩家及世界有效 | 到玩家所在层并接近；目标移动时只做受控有界重规划；超出边界 50 格转归还 |
| 交付 | 玩家停止且同层、接近，配送员停稳 | 每件复验玩家停止、原件归属、目标与背包容量；成功实际转入背包后写回执并结清该原件；玩家再次移动暂停交付；背包放不下时暂停交付并提示玩家腾空间，货物保留在配送员身上；空间就绪且停稳后继续交付 |
| 归还/等待恢复 | 超限、取消或无法继续，且存在已取原件 | 按真实路径回可重验允许存储点，逐件确认后结清；失败、NPC 不可用、效果不明则保留持货责任和声明 |
| 完成或部分撤回 | 所有段已确认交付或安全撤回，且无未结责任 | 订单按实际结果结束；Job 的 Session 停稳、效果已知且无声明后才能退休 |

处理跨楼层：目标与 NPC 不同层时继续向目标楼层寻路；相同 XY 不意味着可取放。到达还需真实可接近与停稳。当前随从 `FollowPolicy` 可参考其节流/重发条件，但随从的 16 格阻塞距离不适用于配送；玩家追送范围依用户决定按据点边界的 50 格判定。

### 四、风险场景与验证目标

- **重复请求/资源争用：** 两个 Order、物流与配送或两名 NPC 同时竞争同一原件时只能一个认领；已分配段不得重复分配。旧请求/旧回调不得结算新代次。
- **多批次：** NPC 按实际可用负重取货、送达、再领取后续未完成数量；背包放不下时暂停等待玩家腾出空间，不随意丢地，不改变其他原件。单件超过 NPC 负重须显示阻断，不假报完成。
- **玩家移动：** 停下条件沿已有逻辑至少 0.5 秒；一旦移动停止交付剩余件。状态持续时不频繁重发路径，不在楼层不同时交付。玩家死亡或消失时停止追送并保留责任。
- **观察与蹲行：** 据点外看见僵尸蹲行，不以全局附近列表替代看见。依据参考项目与安装版证据定义可观察目标和失效条件；观察未知不假装安全。危险仲裁优先，不把蹲行当战斗/避险完成。
- **落地/转移异常：** 原件不在 NPC 身上、目标地块失效、转移中断或效果未知时保留声明并等待核对；不能先移除原件再无条件 AddItem，也不能以类型重建。
- **保存和退出：** 只在身体停止与效果持久化确认后交出控制；读档先重建声明，再核对实例位置并安全恢复。世界切换不能让旧回调操作新世界。只承诺经实测的正常保存恢复，崩溃一致性另行验证。
- **现有代码状态：** 0.29.13 的旧代码仅有三处移动去重日志与同层门；未接统一任务，未修复旁路及归还问题。标准 Lua 替身 37 项通过不代表玩法或真实存档验收。不可将其误记为本设计已完成。

## 待用户决定的业务细节

多批次执行时的取消入口和用户可见反馈只复用已批准界面能力；若需增加新交互，先向用户确认。

## 验收

订单可见等待、领取、取货、送达或安全收尾；不同任务不能同时占用同一 NPC 或原件。验证跨层、移动目标、容量、抢占、退库、玩家死亡、旧回调和正常保存恢复。区分宿主替身与真实游戏；无实机证据不宣称寻路、原版交付、蹲行动画或崩溃安全已验证。异常恢复以未知保留为原则，不承诺零损失。
