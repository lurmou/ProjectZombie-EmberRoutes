# Phase 0 首个 NPC 载体探针设计

> 日期：2026-10-19｜状态：用户已批准；0.1.0 首切片已构建，MP 入口未实现，实机未验证

## 目标与依据

将 [v3.1 原文](../../requirements/2026-10-19-v3.1-original.txt) 的 Phase 0 拆成独立关口，先证明一个人类 NPC 能被正确构造、驱动、观察与清理。先看 [当前 NPCFW 参考评审](../../reviews/2026-10-19/npcfw-reference-review.md)，不重复探索已能由源码解释的机制。

本设计只覆盖首个载体探针；不是全量 Phase 0 实现规格。吃喝/搬运、完整战斗、持久化恢复分别形成后续切片。所有候选引擎接入点在实现前查当前 JAR 和原版 Lua；本设计不预先断言专服能运行 IsoPlayer 的普通更新环。

## 路线选择

推荐参考 NPCFW 的载体、输入和注册机制，以 ZombieBuddy 为目标接入基础，独立实现最小探针。备选是以 NPCFW 为运行依赖；整体移植不进入首轮。参考原理不要求将上游包安装到玩家环境，也不同时启用两套未知兼容的 NPC agent 补丁。

SP 与 MP 共用稳定 probeNpcId、命令和观测结果格式；世界驱动及客户端表现适配分离。SP 的成功只计作 SP 成功。

## 首包范围与组件

- **版本与环境诊断**：唯一版本来源，首个测试包拟定 `0.1.0`；每次交付补丁递增，统一 `[EmberRoutes v版本]` 日志。打印运行域、实际环境指纹与探针能力状态。
- **命令入口**：spawn、move、stop、inspect、remove。最多一个探针 NPC；重复 spawn 返回已有对象信息；重复 remove 返回已清理，不重新创建。
- **载体适配**：构造人类实体、设置已验证的 NPC 控制入口、加入必要世界集合；记录每步成功与失败，支持按逆序清理本次已获得的资源。
- **世界驱动**：同一时刻一个位移提交者，正常动作与碰撞路径推进；只接受已加载且可用的出生点和目标。不可用时明确拒绝，不强制加载世界。
- **观测**：稳定身份、运行角色、位置、当前方格/世界注册情况、驱动方式、清理状态；足够定位“未生成/未注册/未更新/未显示”，避免每帧日志。
- **测试说明**：安装与卸载、命令、环境准备、预期结果、日志位置和结果记录表；CN/EN 测试提示成对。

本包不接入招募、创角、经营 UI、生产、真实车辆和完整 AI。完整角色持久化尚未建立，探针实体为临时测试对象；不允许宣称其已具备存档恢复能力。

## 数据流与权威

SP：本地测试意图进入同一业务裁决入口，经检查后修改世界。

MP：客户端只提交测试意图；服务端验证测试开关、操作者权限、位置、数量上限与请求编号。服务端持有唯一探针身份和状态，客户端表现代理不得提交伤害、物品或 NPC 真值。拒绝未知命令、非法数值和重复创建请求。

第一关先建立构造与移动的 SP 证据，再验证专服模拟入口。若服务端驱动尚不可行，明确报告未通过；不能用客户端自行生成两个 NPC 冒充同一权威实体。

只在服务端实体驱动成立后增加最小创建/移动/销毁同步，验证两个观察者。协议优化、16 字节目标、AOI 分级和航位推测延后；首包优先可诊断、可核对。

## 错误与清理

初始化前检查必要方法和签名，无法满足时禁用相应能力并打印具体原因。不要用大范围异常吞噬继续更新失效对象。

出生点不可用、初始化失败或移除请求发生时，按已登记资源清理；只移除本探针创建的对象，不清空世界列表、不修改真实玩家槽位，不把 playerIndex 作为长期身份。注册、清理和失败分支必须有可观察结果。

专服上的普通玩家更新环、相机与本地 UI 假设必须逐项核对；未经确认不能直接调用上游同名方法作为默认解法。

## 首包验收

| 检查 | 通过条件 | 证据来源 |
|---|---|---|
| 构建与适用检查 | Java 构建成功；新增 Lua 跑项目 preflight 并处理命中项；输出保留 | 本机工具 |
| SP 生成 | 一个可见人类 NPC，真实玩家镜头与控制正常 | 人工实机 |
| SP 移动 | 受控移动、转向、停止；障碍前不持续穿墙或仅原地动画 | 人工实机 |
| 生命周期 | 重复 spawn/remove 不产生额外实体；失败初始化能清理本轮资源 | 逻辑检查及人工实机 |
| 专服驱动 | 无真实玩家槽位/伪连接，服务端持有可运行的实体模拟 | 源码与专服实机 |
| 双客户端 | 两端看到同一身份对应的创建、移动和销毁；退出一名观察者不影响另一名的实体 | 专服双客户端实机 |
| 兼容底线 | 不通过关闭全服反作弊达成；不影响本地相机 | 配置核对与实机 |

未运行项目统一记为“未验证”；源码成立、编译通过、SP 通过、MP 通过分列。首包通过不等于整个 Phase 0 通过：仍需僵尸识别/受击、吃喝搬运白名单、中断和跨生命周期恢复验证。

## 后续关口与停止条件

1. 载体成立后，验证碰撞、僵尸识别/攻击、基本跟随与多观察者。
2. 然后分别验证进食、实际饮水、物品实例转移及动作取消；保留材料/效果单次提交证据。
3. 再建立持久化恢复、断线与显隐交接测试。

若主候选被当前引擎的专服更新假设阻塞，记录具体方法、哈希和阻塞条件，评估 IsoGameCharacter 备用载体，不能无界增加 Hook。需要改变为 SP 首发时，提交具体证据与范围变化，由用户决定；本设计没有预授权自动放弃 MP。
